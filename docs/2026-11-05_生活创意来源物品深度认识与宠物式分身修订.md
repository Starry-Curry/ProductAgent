# 物间生活创意来源 物品深度认识与宠物式分身修订

日期：2026 年 11 月 5 日。依据用户本轮粘贴的生活妙招文章、附件全文和明确反馈，修正前一轮创造力研究的重心。本轮进行了公开来源研究、少量无认证公开 API 读取、当前代码与主数据库只读检查；没有修改应用代码、迁移数据库、安装采集器或调用付费模型。

后续补充：用户进一步强调创意不限于废物利用，并授权尝试 MediaCrawler。多类型 B站案例及隔离试跑的最新结果见[后续研究记录](2026-11-05_B站多类型创意案例与MediaCrawler试跑.md)。本稿“未安装/未试跑”等表述记录的是上一轮状态。

## 1 创意方向的修正

用户强调的是日用品的跨用途使用、替代、组合和旧物再就业。物间要更容易发现一个平常物品原本没有被注意的价值，并判断这些玩法是否适用于用户手上的这一件。

蛋糕刀塞床单、挂条收纳饰品、带吸盘锅刷转为晾晒支点、旧衣做纪念被等，比科学研究创意和论文新颖性更能代表这里的目标。此前 SciMON 等科研创意方法不作为物间创造功能的主路线；相关研究记录保留，不等于接入计划。

目标规划、自由灵感、单物新用、多物组合及可授权设备调整仍全部保留。日常创意既可以实用、省钱，也可以好玩、好看或留下记忆，不被收纳一个类别限制。

## 2 从用户例子里看见什么

下表是对用户提供案例的机制分析，案例来自转载文字或个人分享，不表示物间已经验证实物效果。粘贴文本中只有图片占位的地方，不当作已看过图片。

| 用户提供的例子 | 值得认识的特征或关系 | 迁移时真正需要知道什么 |
| --- | --- | --- |
| 蛋糕刀用来塞床单 | 薄片与伸入狭缝的动作可能匹配 | 实际厚度、边缘、材料刚性，是否可能伤及布面 |
| 超市挂条收纳发饰或帽子 | 多个悬挂点、间距与空间组织 | 挂条怎样固定、目标物如何挂、是否需额外杆或夹子 |
| 带吸盘锅刷作为晾晒支点 | 吸附底座、柄与所挂物的接触关系 | 这一款是否真有吸盘、墙面是否适合、原帖与实物差异 |
| 纸筒分隔收纳 | 中空形状、分格与归拢 | 尺寸、湿度、是否需要底盒或固定 |
| 饼干盒与内衬做首饰盒 | 容纳与防尘，内衬提供整理方式 | 内部尺寸、边缘状态，绒布泡沫胶等是否已有 |
| 旧衣制作纪念被 | 可用布料与保留图案、记忆的结合 | 用户是否愿意改、需要的技能时间与材料，不默认会缝纫 |

不能只提取旧名称到新名称的映射。知道一款带吸盘的刷子有这种玩法，不等于所有锅刷都适用；知道某个盒子可装东西，也不等于它适合直接接触食物或装土种植。

文章中的零过敏、普通手套可承受某一高温等绝对说法先作为待核主张，不能直接进入已验证知识。涉及身体处理或旧电器拆改的内容，须另外判断是否适合提供，不作为普通生活妙招直接照搬。本轮不就这些做操作指导。

## 4 成熟采集工具的角色

[Crawl4AI](https://github.com/unclecode/crawl4ai)可作为动态页面读取与内容抽取候选，仓库当前元数据为 Apache-2.0。它负责取得可访问内容，不自动解决物品理解和创意质量。当前静态读取失败的真实页面可以作为比较样本，本轮没有安装或运行。

[MediaCrawler](https://github.com/NanmiCoder/MediaCrawler)说明支持小红书、B站等平台的搜索、帖子和评论采集。本轮读取其 [LICENSE](https://github.com/NanmiCoder/MediaCrawler/blob/main/LICENSE)，是非商业学习使用许可证，不是可默认嵌入产品的宽松开源组件，也不允许据此承诺大规模采集。当前仅列为机制研究参考，没有登录、导入账号或采集。

还检查了 Nemo2011/bilibili-api 的仓库元数据，本轮显示已归档；不能仅按以往知名度列为当前成熟首选。具体平台适配需要版本、可访问性和维护情况一起验证。

因此可按顺序选择：现有搜索与读取 → 对确实失败的公开页面比较成熟抽取器 → 针对必要平台再研究合法可用适配。工具许可证、内容使用条件和平台访问能力是不同问题。

## 5 怎样更深入认识物品

### 5.1 五类依据互补

1. 标准商品的准确型号、官方说明、适用版本和关键图示。
2. 当前实物照片能直接支持的外形、部件与可见状态，保留视觉不确定性。
3. 用户提供的实际位置、材料或改动、损坏、配件与不可改造要求。
4. 具体社区案例中展示或声称的动作与条件，区别原案例和当前实物。
5. 用户真正试过后的反馈，影响相应条件下的认识与下一次建议。

这五类不是每次全部读取。当前帮助需要什么就查什么，未知关键参数阻止下一步时再自然补问。

### 5.2 超越商品类别的表达

逐步认识形状、可见尺寸、材料依据、软硬、容纳方式、可接触表面及可用的连接部位；由此理解覆盖、分隔、悬挂、夹持、吸附、支撑、回弹等可能动作，以及适用条件。

这些是可按需扩展的认识维度，不要求为每件物品填上千属性，也不先建一个刚性通用物理模型。照片不能确认的材质、耐温、承重和内部结构保持未知；相关正式性能依据型号资料与实际验证。

### 5.3 Skill 认识数据和实践循环各做什么

- Skill 保存通用方法：看形状部件与动作，按目标和结构找案例，对照差异，选中后检查关键条件。
- 数据保存这件物品或适用型号实际知道什么、依据、条件与当前状态，以及来源独立的案例。
- 主模型负责理解和开放联想，可以按需要补查，不被固定点子模板限制。
- 实践循环将真的做了什么、失败条件与用户选择绑定原方案，修正适用认识。

已有 `creative-use` Skill 和 `KnowledgeUpdate` 已覆盖部分语义，但实际遵循与知识积累仍不足。不能继续只加长提示，也不能把已有框架删除后假定换工具就会自然变聪明。

### 6.2 主库现有内容与规模

在读取本地配置确定数据库路径后，以 SQLite `mode=ro` 检查，不调用写入或迁移，不输出用户私人正文。

本次主库聚合：8 件物品、3 个商品记录、2 条知识、5 个来源、3 条个人理解、6 段经历、2 个持续任务。2 条知识中，1 条标记为 capability，1 条标记为 case。

这些是当次应用主库数量，不含 `var/evaluations/` 中隔离的测试数据库，不能用来判定历史开发成果消失。数量也不能证明单条内容质量；但不能把当前主库称为已经丰富的生活创意案例库。

### 6.3 已有的关键数据

- `products`：型号资料概况。
- `items`：具体实物身份、状态、照片、归属与版本。
- `knowledge_claims`：认识内容、条件、依据、来源、适用型号或实例与状态。
- `sources` 和 `assets`：原始来源、网页/PDF 内容及媒体。
- `experiences`：主动记录的照片文字和多物关联。
- `memories`：有依据、情境与时效的个人理解。
- `tasks`：目标、相关物品、约束、方案、反馈和版本。
- 另有分身档案、共享、好友、赠礼、提醒、设备目标与观察。

代码证据为 `wujian/database.py`、`config.py`、`knowledge.py`、`learning.py`、`retrieval.py`、`agent_runtime.py` 与前端文件；本轮没有执行新的模型质量测试。

## 7 数据库要升级什么

需要增强知识与案例表达、检索和更新机制，目前没有证据表明换掉 SQLite 引擎是创意质量的主要解法。未来多人线上部署与并发再独立评估数据库服务。

### 最小候选改进

1. **物品能力认识更具体。** 从大段描述逐渐形成来源明确、可按动作与条件找到的性质、部件、能力和限制。尽量沿用现有知识机制，查询或维护有需求再拆结构。
2. **案例有独立身份。** 从挂在某件物品下的一段 case 文本，发展为能查重和复用的案例：来源作者与时间、原物品、目标效果、动作与步骤、原理、额外材料、条件、相关媒体、作者声称或实际反馈。具体字段和拆表方式在架构阶段确认。
3. **案例与当前实物的适用性分开。** 按当前任务匹配，说明相同点、差异、未知和不可用原因；不预计算全库每个案例乘每件物品，也不把案例内容直接提升为商品共性。
4. **实践反馈继续利用任务。** 反馈绑定被尝试的方案版本及物品条件，复用已有任务与来源机制，避免再造一个独立反馈系统。

搜索既支持名称，也能找形状、连接部位、动作和目标。例如不只搜锅刷，还能沿吸附、支点和晾晒找到相关参考。现有 BM25 与语义检索可以继续作为基线，其中文短词和结构属性召回需要真实比较，暂不为此先引入图数据库。

照片理解、用户纠正、来源更新和物品损坏应影响相关适用判断。私人案例、公共来源和用户经历有不同访问范围，不因可复用而统一公开。

## 8 测试语言与方法的修正

测试输入优先模拟真实人会怎样说，短句、指代、漏信息、插话和实际反馈都要包含。测试脚本可以在内部维护明确事实和验收条件，但不能把它们全部塞成一段用户不会说的话。

可用的自然表达例子：

- 我有个空饼干盒，还挺好看的，扔了可惜，能干嘛？
- 这刷子底下能吸住，除了刷锅还能咋用？
- 别让我买东西啊，家里有啥用啥。
- 这个杯子是朋友亲手做的，别给它打孔涂胶，弄坏了心疼。
- 刚试了一下，根本挂不住，一会儿就掉了。
- 上次说的那个办法不行，还有别的没？
- 我不太会做手工，最好几下就能弄好。
- 这些孩子的小衣服不舍得扔，也不想一直堆着。

以上是设计用表达模板，不是已冻结验收题。后续测试按真实国内商品型号或明确非标物建立事实，区分用户已知道和模型需要发现的内容。不能只用整理精确的完整条件验证理想输入。

需要同时看：点子是否有意思和实用、是否用了真实资源、是否误读物品、是否带来额外成本、是否遵守用户心疼或不愿改造的边界，以及失败后能否换机制。用户提供的文章可以作开发参考，不能把同样例子作为独立盲测并靠背答案过关。

## 9 分身参考转向电子宠物与盲盒的体验

### 值得参考什么

[Finch 官方说明](https://finchcare.com/about-finch)将个人活动、记录和小鸟成长联系起来；[创建流程](https://help.finchcare.com/hc/en-us/articles/37779580853005-Creating-Your-Birb)提供名字、颜色和初始特点。适合学习相处反馈与角色连续性，不代表它是开源组件。

[拓麻歌子 Uni 官方产品与说明](https://tamagotchi-official.com/us/series/uni/)可以学习小角色的可辨认外形、个性、配饰与阶段变化；不复制其角色资产，也不把传统喂养压力直接搬入物间。

[Habitica](https://github.com/HabitRPG/habitica)提供公开的孵化、喂养与成长实现。本轮读到 `hatch.js` 把种类与外观组合成具体宠物，`feed.js` 根据偏好和成长状态改变宠物状态。值得学习数据与状态怎样驱动画面，而不是由大模型每次随意编造一次成长。

Habitica 代码为 GPL v3，部分自身美术为 CC-BY-NC-SA 3.0，其他资产也有不同许可；机制参考和直接复用代码、图片分别评估。本轮未复制资产或接入。

### 用于物间的方向

- 全局物伴保持一个稳定形象；具体物品分身按需开启。
- 分身保留原物的辨识特征，少量有设计的五官、表情与动作，避免所有物都机械套人脸。
- 先统一比例、色彩、材质、眼睛和动作语言，再逐步增加个性。
- 物品的真实经历可形成新的配饰、姿态和称呼，保留原身份；变化频率低且可调整。
- 盲盒感可以来自初次见面的少量惊喜与慢慢解锁的细节，用户可以选和改；暂不增加复杂抽取、经济或强制打卡系统。
- 拟人程度与对话风格由用户选择。平时主要帮助使用的物品不强迫陪聊；礼物与纪念物可以更有陪伴感。

## 10 当前向日葵为什么不像一个分身

`frontend/src/Views.tsx` 的 `ObjectArt` 在有照片时显示照片；没有照片时，根据名称正则选择 Lucide 图标。名称命中画或向日葵时显示 `Flower2`，加颜色、光晕和阴影。它没有独立设计的花瓣比例、面部、表情、动作或角色资产。

`AvatarSpec` 当前核心输入只有昵称、性格和颜色，成长主要是文字笔记和依据；不存在完整的外观生成和成长表达管线。`domain.accept_gift` 还会清空物品主照片，可能让接收后的物品退回默认图标；具体用户看到的那张卡片需结合实际记录核对。

因此当前的花朵只是图形占位，不应称为已经实现的数字角色。修正需要角色资产与呈现机制，而不仅换一个色号。

向日葵首个设计候选：保留花盘、花瓣、叶片和可选小花盆的植物轮廓，采用与用户草图物伴协调的柔和风格；先完成安静、倾听、回应等少量自然状态，再考虑真实经历形成的小配饰或姿态变化。最终审美用实际样稿比较，不把文字设想当作已经好看。

实物照片与分身形象分别保存与展示，赠礼时明确选择携带的图像资产。不能通过清空实物照片来冒充创建了新角色，也不能未经范围确认把其他私人图片一起送出。

## 11 建议的下一步

本轮不启动实现。后续先比较来源清楚的小批量生活案例能否在自然表达下改善真实建议，再决定案例结构、检索与读取工具的最小改动；同时用实际物品证明深度认识是否有效。

分身先做少量一致风格的角色样稿与轻量状态，独立验证审美和相处感，再接真实经历与成长。它不能替代知识、记忆归属和共同任务的正确性，也无需等待每件物品都拥有角色。

这些修订服务现有共同底座，不改变兑现、创造、延续、传递四类价值，也不要求四个栏目各建自己的案例、事实与人物认识。
