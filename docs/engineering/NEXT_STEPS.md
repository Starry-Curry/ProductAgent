# 下一步研发规划

日期：2026-11-05。以下是**建议的后续顺序**，不是已经完成的功能，也不自动启动新的开发或付费测试。当前事实只看 [CURRENT](CURRENT.md)，产品范围仍以 [产品定稿](../product/PRODUCT_FINAL_V1.md) 为准。

## 1. 先让团队用同一份底座开始工作

当前阻碍：最新底座在独立分支，develop 还是较早版本；[PR #1](https://github.com/Starry-Curry/ProductAgent/pull/1) 有成功 CI，但还没有组员独立审查。

- 本轮文档整理先以团队集成分支为目标提交小型 PR，不重复提交 PR #1 的业务差异。
- 一名组员审查公共接口、权限、Task/Outcome 与迁移影响；若候选 HEAD 更新，重新检查该 HEAD 的 CI。
- 按团队规则合入 develop 后，新任务统一从 develop 创建功能分支，停止长期依赖临时候选。
- 组员按 [接入指南](TEAM_INTEGRATION.md) 运行独立 Mock 示例，通过公共 `services.ts` 读取物品、Context 和 Task；不各自建立模型循环或知识库。

完成标准：团队成员能从明确基线运行项目、接入一个最小功能并提交 PR；CI 和一名组员审查都完成。**这不是 Core Foundation 的智能质量验收。**

## 2. 优先修好“资料找到了，指导仍说错”

当前已有依据：陌生品牌能自主取得官方 HTML/PDF；J01 曾混淆左右、关机限制并补写没有依据的细节。缓存复测改善，但没有证明陌生商品可靠。原始失败和复测见 [CORE_REVIEW](qwen-foundation-2026-11-02/CORE_REVIEW.md)。

下一轮只做一个连续任务：陌生物品 → 官方资料 → 完整操作指导 → 追问 → 用户反馈 → 新会话复用。先从真实调用链定位是原图读取、章节选择、Context 传递还是最终生成丢失条件；依据复现做最小修改，不再用品牌特例或增加审核模型掩盖问题。

完成标准：在真实 App 中逐项核对指导与原文/图示；已知项完整回答，未知不补写；改状态、纠正、遗忘、撤权后后续结果正确变化。保留首次和复测，不用 Mock 或接口成功替代真实 Qwen。当前历史额度封存，**新增付费测试须另行明确授权**。

## 3. 底座质量稳定后，再交付一个有实际价值的组合任务

优先选择用户已有物品完成明确生活目标，复用同一 Task、Reality 和获准经历。当前曾出现“没检索到托盘就说不拥有”，修复后发现资源，但承重、摩擦、净尺寸等仍未实测。

下一步验证：自动找到相关资源；清楚说明利用的特性、实际动作与关键缺口；用户否定或报告失败后改变路径；获准反馈能影响新任务。先把一个用户愿意尝试的闭环做好，不开启创造力 V3/V4 或新框架研究。

完成标准：用户能从目标走到可核对方案、确认反馈和后续复用；资料事实、条件假设、用户报告与实物验证清晰分开。创新价值需人工判断，不能只靠模型自评。

## 4. 再按共享基础延伸专业体验

数字分身、故事、家庭、赠礼和 REA 保留产品地位与已有代码，当前不主动扩展。底座达到对应质量门槛后，由产品负责人选择一条优先：物品个性化，或官方设备接口优先的能力探索。REA 实体设备、额外费用和高风险操作须独立授权；已有软件实验不等于硬件能力已验证。

历史分支清理另行安排：先确认 PR #1 合并、无人使用且完整 SHA 已保存，再整理祖先分支候选；有独立提交的分支和本地未发布恢复点继续保留。历史模型原文、费用与失败证据不在本轮删除范围。

## 决策与停止边界

- **现在需要团队做的事：** 指定一名组员完成 PR #1 和文档 PR 的独立审查；不是让作者自己批准。
- **下轮启动前需要确认：** 上述可靠指导专项是否为第一优先，以及具体真实模型预算。当前无新增费用权限。
- **本轮到此为止：** 文档、规划与 GitHub 可审查提交交付后停止；不顺手开发专业功能、重构智能执行器或清空远端分支。
- Core Foundation V1 仍为 **NOT_ACCEPTED**；Full Foundation 的原 18 题首答和四旅程标准保留，不因团队已能接入而改写为通过。
