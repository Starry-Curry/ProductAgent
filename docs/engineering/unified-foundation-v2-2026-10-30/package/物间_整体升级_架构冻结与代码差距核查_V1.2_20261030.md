# 物间｜整体升级：架构冻结建议与代码差距核查 V1.2

**日期**：2026-10-30  
**依据**：物间产品理念 V1.0、RFC V1.0、实施级评审 V1.1、`Starry-Curry/ProductAgent` 分支 `codex/wujian-product-foundation-v1@d8eee9306e8eb53975e80eb98d3b1ace812777b7`、85 案测试集。  
**文档状态**：面向下一轮整体开发的**实施建议**；尚未修改代码、跑本地工程测试、批准真实费用或实际部署。

## 1. 建议冻结的产品原则

- **产品终点**：释放人与物的价值；人际价值的延伸必须与物品、共同任务、使用经历或物品流转有真实联系。
- **认知范围**：理解物 → 物与物 → 物与人 → 人与人；不是 UI 流程。
- **价值机制**：兑现、创造、延续、传递；允许同一功能贡献多种价值。不得把旧版三类价值当作产品最终定义。
- **统一体验**：同一物间 Agent 面向用户；多个专业执行器处理不同复杂度任务；跨入口共享任务、物品及已授权上下文；不要求简单问答都生成长期任务。
- **入口数量**：**未决**。3/4/现有多入口原型只用于评估；工程上把主导航配置化，先采用不破坏既有任务入口的可逆方案，最终由真实任务测试决定。

## 2. 推荐的工程架构（冻结候选）

```text
输入端（物品详情/从目标提问/故事/家庭/赠礼/创意）
  → Identity & Policy（会话身份、关系、权限、撤权）
  → TaskService / TaskRun（目标、关联实物、阶段、上下文引用、任务连续性）
  → ContextResolver（按用户、任务、物品与权限最小化选取资料）
  → 专业执行器：快捷事实问答｜操作指导｜创意规划｜记忆与分身｜家庭交接｜赠礼｜设备软件实验
  → EvidenceService + CapabilityRegistry（型号证据、主张语义、能力可执行性）
  → ToolReceipt + Outcome（可追溯的调用与实际结果）
  → 经用户许可与纠正机制沉淀经验，不擅自把推断升格为事实
```

`Next.js + SQLite + LangGraph` 可保留；复杂路径用 LangGraph，快速资料问答不需完整 Agent 循环。`TaskService/ContextResolver/PolicyEngine/EvidenceService/CapabilityRegistry/OutcomeStore` 是模块边界，不强制微服务或新数据库。

## 3. 依据现有源码核对的关键断点（不是已复测的运行故障）

| 位置 | 可复核事实 | 升级约束 / 验证方法 |
|---|---|---|
| `src/lib/domain.ts` | `Person` 同时包含 `lin/dad/friend` 演示角色与 `u_${string}`；Item 用 `owner/shared/sharedWith` 表示用户关系与共享 | 身份命名空间和授权判定分离；所有新真实账号操作仅信任服务端 session；演示兼容由 adapter 承担；全量权限负测 |
| `src/lib/domain.ts` | 核心 `State` 将 `items/tasks/memories/gifts/plans` 混合保存；`saved` 使用按人物索引的旧结构 | 逐步分离实体与状态写入；严测多账号同事务并发、丢更新、`undefined` owner-index 等边界；不直接删除旧 JSON |
| `src/lib/agent/graph.ts` | `young-apartment-v1` 直接进入专用 `executeHomeTask`，普通物品另走主图 | 模拟公寓作为 fixture 而不是生产逻辑分支；同一个任务协议适用于陌生 SKU、真实账号和模拟案例 |
| `src/lib/agent/grounded-answer.ts` | 自由资料综合直接生成答案并附来源列表，未见逐条事实主张的语义核验；当前实验开关默认关闭 | 引入 `supported/refuted/not_found/conflicting` Claim；引用存在不代表结论为真；重新评测 ANC、维修政策等旧错误前不得默认启用 |
| `src/lib/collaboration.ts` | 邀请/共享/事项操作通过整份 `workspace.body` 更新；本机独立账户已可注册 | 核查多个并发请求在 SQLite 事务中的更新一致性、撤权后一切上下文的失效；必要时调整事务边界和版本 |

| `src/lib/devices/software-lab.ts` | 实际 REA 只分析固定自有 JS 灯，支持授权、写入幂等、软件回读 | 可复用执行回执，不默认扩大成任意设备控制；候选能力与已验证硬件严格区分 |
| 旧 PRODUCT_NORTH_STAR | 旧项目北极星文档仍以三类价值概括 | 开发时以 V1.0 产品定稿的四种机制为上位，更新仓库内文档并标明来源，不修改项目 Instructions |

以上均为**静态源码/交付材料检查**，不代替下一轮本地复跑。不得声称这些都是已证实的用户端故障。

## 4. 必须先锁定的接口契约

详细 TypeScript 示例和状态机见 V1.1，以下为跨模块最小一致性要求：

1. **`ProductModel` 与 `ItemInstance`**：官方通用资料与用户实物分别建身份；同款两件实物 ID 不同。型号/地区/固件/版本必须在获取知识前核对。
2. **`Person` / `Relation` / `Grant`**：参与某故事、属于某家庭、使用某物 ≠ 获准访问其私人数据。任何副作用都在动作前重新计算有效授权；撤销必须影响已有任务。
3. **`TaskSpec` / `TaskRun` / `ContextRef`**：同一目标跨页面有稳定任务 ID，执行尝试有独立 Run ID；简单问答可临时 Run；任务级 Context 保存**引用与依据**，读取时重新鉴权，不复制全部记忆。
4. **`KnowledgeDocument` / `EvidenceClaim`**：来源身份、适用版本、有效时间、对应片段；四态 `supported / refuted / not_found / conflicting`；模型推断不得自动升为权威事实。数值/否定/售后/维修等关键事实在展示前校验。
5. **`CapabilityRegistration` / `ToolReceipt` / `Outcome`**：文档写了支持≠设备可调用；发现接口≠执行成功；模拟回读≠硬件验证。先持久化动作意图，再执行，超时不盲重试；`user_report` 与 `hardware_readback` 有独立证据等级。
6. **`Outcome` 的个人价值**：故事保存可以是有意义的结果；用户报告、真实设备读回和第三方验证分开，不以所有动作都是技术 API 为前提。

## 5. 一轮整体升级的执行顺序（必须可恢复）

| Gate | 应交付的代码与测试 | 守门问题 |
|---|---|---|
| G0 | 新隔离工作区；仓库现状与不改动清单；领域 ADR、迁移脚本和回滚策略；权威产品文档 | 能否在不破坏旧数据的情况下切换新模型？ |
| G1 | PolicyEngine、ItemInstance/Relation/Grant 基础与数据适配；账户/赠礼/家庭权限负测 | 是否存在跨用户信息泄露或错误权限继承？ |
| G2 | EvidenceService、资料适配/Claim、只用可信证据的快速问答及操作指导 | 是否仍把缺证当否定、编造维修与保修政策？ |
| G3 | TaskSpec/Run/ContextResolver/OutcomeStore 与执行状态、重试恢复 | 跨入口/重启/撤权后是否保留正确任务但不泄露旧信息？ |
| G4 | 专业能力统一接入：创意/组合、记忆分身、故事、家庭、赠礼、REA 软件实验；再完成真实物品 E2E | 同一任务能否跨能力完成，而非只在特制模拟公寓有效？ |
| G5 | 可逆导航实现和整体体验；执行 85 案对应的离线/浏览器/模型/人工验收；交付报告 | 用户能否完成任务？所有失败、成本和限制是否如实报告？ |

**可调整顺序说明**：V1.1 将证据优先，本 V1.2 因真实家庭授权和新 Context 可能触及隐私，建议先建立最小 Policy 核心，再迁入 Evidence 与 Task；两者可在独立工作流并行，但必须先经权限门禁才能合并。工程可细化内部子阶段，不得跳过最终门禁。

## 6. 验收策略与阻断

85 案的预设分类已经核对：**34 live_model，23 browser，16 integration，9 prototype，3 software_lab**。这不是 85 个可以靠单元测试自动判定正确的场景。随执行包提供的 `wujian_acceptance_preflight.py` 仅做数据完整性与结果格式核对；**不运行任何模型或浏览器，不评定商品事实是否正确**。

- **P0 阻断**：跨账户敏感数据泄露、撤权未生效、重复产生真实副作用、把模拟执行冒充硬件、关键危险操作违规、关键事实无依据断言、生产迁移导致不可恢复数据丢失。
- **P1 阻断**：跨入口任务身份丢失、一般用法大面积失败、把“用户说完成”变成“设备已完成”、完整旅程只有 UI 按钮而无可验证行为。
- **可安全降级**：创意方案尚待实物验证、外网厂家页面暂时不可用、特定硬件接口不开放，必须呈现未知/模拟/需确认，不应静默假装通过。

**性能阈值**：默认使用已约定的普通问答目标“有效首响应 P50 ≤ 3 s、完整正确 P50 ≤ 10 s”，但只在独立真实模型与浏览器测得的**正确回答子集**中评估；同时报告全部请求 P50/P95、失败率和人工审阅。无法获得付费模型额度时只判 `blocked_model_budget`，绝不把假替身输出当作真实质量通过。

## 7. 立即可执行的三条旗舰旅程

- **旅程 A｜陌生耳机到帮助与家庭交接**：以真实 Sony WH-CH520 型号和官方说明书建立**合成持有**实例 → 问官方配对/按键/ANC/售后 → 将操作指导和求助摘要分享给获授权的另一账号 → 对方接手 → 用户反馈。不得推断未有证据的售后政策，不发送私人记忆。
- **旅程 B｜跨物品创造与硬限制**：DJI OM6（官方手机重量/尺寸）+ Canon EOS R50（相机）+ IKEA SAMLA（不适合直接食品接触）+ 台灯 → 用户提出摄影/收纳/创意目标 → Agent 发现正确资源和不能用的组合 → 给出替代方案和可执行步骤，模型创意不得虚构兼容与承重条件。
- **旅程 C｜个人故事与物品传递**：个人相机/相框绑定真实商品型号（合成持有） → 记录故事、设置分身、确认/撤回记忆 → 选择性赠礼 → 接收者独立实例/独立回忆，不回传新私人内容；任务进度在合法范围内接续。

REA 单独作为第四条**软件模拟**实验链：分析自有 JS 灯 → 提出候选能力 → 授权 → 幂等执行 → 回读 → 撤销 → 禁止再用。不得用此结果声称真实小米台灯可被 REA 控制。
