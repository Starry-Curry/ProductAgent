## 一、评审结论和决策状态

**推荐批准的技术方向**（待产品负责人确认）：**统一任务所有权 + 可恢复 TaskRun + 领域状态/权限内核 + 专业执行器**。统一指用户体验和核心契约；不意味着每条请求必须经历模型长循环。

| 决策项 | 结论建议 | 状态及前提 |
|---|---|---|
| R1 统一 Task ID / Run ID | 采纳；短问答可用临时 Run，不强制持久任务 | **待确认方案**；须验证跨入口恢复 |
| R2 Evidence Claim 语义 | 采纳；正面支持/明确反驳/证据不足/冲突 | **高优先级**；关键断言无来源不得确定表达 |
| R3 权限与关系分离 | 采纳；关系是事实，授权是独立、可撤销的访问决定 | **安全门禁**；家庭/赠礼不能继承无关私密信息 |
| R4 能力与执行状态 | 采纳；支持只读与写入、候选/验证、幂等/回读 | **安全门禁**；真实 REA 软件实验不能冒充物理控制 |
| R5 执行架构 | 单逻辑 Agent，专业执行器；现有 LangGraph 只在复杂路径保留 | **技术方向候选**；先做最小基准对照 |
| R6 导航 | 先做 3 / 4 / 现有多入口可点击对照，暂不锁定数量 | **待用户测试**；见 HTML 原型 |
| R7 框架与存储 | 先保留 Next.js/SQLite/LangGraph，新增兼容适配层 | **建议**；性能和模型质量不靠换框架自动解决 |

**明确不建议：** 今天另起一个全新数据库、强制采用多 Agent、直接把事实问答的实验性自由生成打开为默认、因为导航原型像四栏就立即大改首页、把真实商品官网信息与个人物品当前状态混为一谈。

## 三、不可混淆的三层数据模型

1. **客观/外部通用层**：`ProductModel` / `KnowledgeDocument` / `EvidenceClaim` / `CapabilityClaim`。它们由型号、地区、固件、时间、官方文档的适用范围约束；不意味着任何具体实物当前可用。
2. **个人/家庭实物层**：`ItemInstance` / `Person` / `Household` / `Relation` / `Grant` / `Experience`。每件实物有自己的状态、拥有者与使用者；未授权故事/图片/个人记忆不与公共商品知识同级可见。
3. **当前任务与运行层**：`Task` / `TaskRun` / `ToolReceipt` / `Outcome`。用户目标、所选物品、参与者、授权快照和真实运行状态在这里；不是把全量 Context 拷进聊天窗口。

**共享身份规则：** 商品型号 ID 与实物 ID 必须分离；两件同款有两个 `itemInstanceId`；从 A 送给 B 的实物可建 B 的新实例并保留授权可见的流转关系，不能直接开放 A 的全部历史；未完成任务的参与者只能查看与当前任务相关的获准摘要。

## 四、技术契约：任务与运行

### 4.1 TaskSpec 与 TaskRun 分离

```ts
// 逻辑接口（供实现时再与现有代码/types 对齐）
type TaskSpecV1 = {
  taskId: string; version: 'task-spec/1'; revision: number;
  createdBy: string; householdId?: string;
  goal: string;
  intent: 'answer'|'guide'|'plan'|'explore'|'customize'|'record'|'collaborate'|'gift'|'control';
  itemInstanceIds: string[];
  participantIds: string[];                 // 不代表自动获授权
  currentStage: 'draft'|'ready'|'active'|'waiting_user'|'waiting_other'|
                'verifying'|'completed'|'partial'|'blocked'|'failed'|'cancelled';
  contextRefs: { kind: 'item'|'product'|'claim'|'memory'|'relation'|'capability';
                 id: string; revision: string; whyNeeded: string }[];
  constraints: { key: string; value: unknown; origin: 'explicit'|'derived' }[];
  createdAt: string; updatedAt: string;
};

type TaskRunV1 = {
  runId: string; taskId?: string; sessionId?: string; version: 'task-run/1';
  actorId: string; entryPoint: string; executor: string;
  status: 'queued'|'running'|'waiting_user'|'waiting_other'|'verifying'|
          'succeeded'|'partial'|'blocked'|'failed'|'cancelled'|'unknown';
  stepReceipts: { stepId: string; toolCallId?: string; receiptId?: string;
                  status: 'planned'|'pending'|'verified'|'failed'|'unknown' }[];
  observedPolicyRevision: number;  // 每次动作前必须再授权，不能仅看旧revision
  progress?: { shortLabel: string; nextDecision?: string };
  startedAt: string; finishedAt?: string;
};
```

**必要的精细取舍：** 简单阅读或一轮说明书问答可以建立**临时 `runId`**，但不必永久保存一个任务实体；当用户要求「把这件事留着、继续、交接、记录结果」时再创建持久化 `TaskSpec`。这样保证一致协议，又不把日常 App 变成繁琐任务管理器。

**跨入口：** UI 可以改变 `entryPoint` 和当前页面，但不得无故重置 `taskId`、`itemInstanceIds` 和已完成步骤。切换身份则必须重新评估可读取的子集；不能因为 `taskId` 相同就复制其他人的私密记忆。

### 4.2 状态机、并发与恢复

| 操作 | 预条件 | 成功记录 | 失败/重试规则 |
|---|---|---|---|
| 创建任务 | 当前用户身份与物品范围可用 | `taskId`，草稿；无现实完成声明 | 重复 `requestId` 返回原结果 |
| 开始运行 | 已核对必要约束及权限 | 唯一 `runId` / executor版本 | 同一 `runId` 不重复有副作用步骤 |
| 查看/接手家庭任务 | 当前身份是获授权成员；状态允许 | 分开记录 `seenAt` / `acceptedAt` | 撤权立即拒绝下一次访问 |
| 工具写操作 | 对象版本、Grant、用户明确确认、幂等键满足 | 先写意图，再执行，再只读回验 | 超时返回 `unknown` 或 `failed-or-uncertain`；查询原回执，不盲重试 |
| 完成现实目标 | 结果证据足够；需用户报告/设备回读等 | 结构化 `Outcome`，注明真实性级别 | 仅模型输出不能自动标为完成 |
| 更正/忘记/撤销 | 当前有权执行 | revision/epoch 更新，旧引用失效 | 不得被旧会话、缓存、异步子任务再次注入 |
| 赠礼确认 | 双方身份、明确选择内容、归属和未完事项审核 | 新实例+来源关系+许可故事快照 | 不允许私人故事或人格随实物默认转移 |

**生命周期门禁：** 任务内容采用 `expectedRevision` 做并发更新；工具接收 `requestId` 并签入目标版本；权限变更时未完成的异步工具须暂停/失败；检查点恢复前重新加载相关对象和 Grant。副作用成功却丢回执时必须进入 `unknown` 待查，而不是再发一次。

### 4.3 Outcome 的证据级别

```ts
type OutcomeV1 = {
  outcomeId: string; taskId?: string; runId: string;
  goalStatus: 'achieved'|'partial'|'not_achieved'|'unknown';
  basis: 'verified_document_fact'|'user_report'|'software_simulator_readback'|
         'hardware_readback'|'external_receipt'|'saved_personal_experience'|
         'not_verified';
  evidenceRefs: string[]; reporterId?: string;
  itemInstanceIds: string[]; occurredAt: string;
  notes?: string; canReuseForFutureTasks: boolean;
  sharingPolicyId?: string;
};
```

- 答对说明书：完成的是**信息任务**，不是确认用户真的操作成功；实际操作要用户报告或实物回读。
- 保存一段自己的故事：`saved_personal_experience` 可以成为真实的记录结果，但故事内容中的客观事件是「用户叙述」，不能当成第三方核验事实。
- 设备软件灯回读：`software_simulator_readback`，严禁升格为 `hardware_readback`。
- 家庭人员声称修好了：`user_report`，不能自动改变设备真实状态。

## 五、技术契约：证据、主张与回答

### 5.1 分离来源、断言与推理

```ts
type EvidenceClaimV1 = {
  claimId: string; version: 'evidence-claim/1';
  subjectModelKey: string; predicate: string; normalizedValue: unknown;
  verdict: 'supported'|'refuted'|'not_found'|'conflicting';
  assertedScope: { region?: string; firmware?: string; edition?: string };
  sourceRefs: { documentId: string; passageId: string; url: string;
                textHash: string; excerpt: string; retrievedAt: string;
                relevance: 'direct'|'comparison' }[];
  derivation: 'explicit'|'deterministic_rule'|'proposed_inference';
  confidenceBasis: string; lastReviewedAt: string;
};
```

**必须区分两种层面：** `verdict` 表示该断言是否被现有适用证据支持；`derivation` 表示结论是原文直接表达，还是按确定规则（如尺寸范围）得到，还是仅有模型候选。`proposed_inference` 不能因为模型相信而直接成为 `supported`。

例子（实际自动化用原文可查引文，下面只说明判断逻辑）：

| 问题 | 证据或事实 | 正确 verdict | 可呈现的结论 |
|---|---|---|---|
| Sony WH-CH520 再配对 | 官方指南明确写已有配对信息时按 Bluetooth 按钮约5秒 | supported + explicit | 给出按键、时长、适用条件 |
| Sony WH-CH520 不支持 ANC 吗 | **当前已读取的某个帮助页未提到 ANC** | **not_found** | 只说明该页无法证明支持或不支持；继续查适用规格 |
| IKEA SAMLA 11L 装散装面粉 | IKEA 官方明确未获食品接触批准 | refuted + explicit（针对「适合直接食品接触」） | 不推荐该用途；不被创意绕过 |
| DJI OM6 装重310g手机 | 官方范围170–290g，用户报告手机310g | refuted + deterministic_rule（针对「在推荐范围内」） | 超出推荐范围，不能确认为兼容 |
| 飞利浦 HD9252/90 用 /81 手册 | 只有另一后缀页面 | not_found / 型号待核 | 不把 /81 当作 /90 自动兼容 |
| 两个资料版本相互矛盾 | 两个准确型号/地区的适用来源冲突 | conflicting | 显示冲突并要求进一步核对适用版本 |

**切忌**把 `not_found` 错写成 `refuted`。但也不能为了规避此错误，永远不作否定判断：直接否定证据与可验证的规则越界可以给出清晰结论。

### 5.2 事实回答最短可靠路径

```text
识别当前实物/型号/地区
 → 查可用的、适用的官方知识段
 → 按子问题形成候选主张（Claim）
 → 对否定/数值/安全/维修等高风险断言做原文/规则校验
 → 只用通过的 Claim 组织简洁回答
 → 对缺证部分单独说明未知，并给低成本核实途径
 → 为用户显示可核对的出处
```

**流式策略：** 段落可以早显示，但高风险事实必须等通过校验才以确定性语气展示；首个字节早到不等于首个可靠信息早到。将 `candidate_text` 与 `verified_answer` 分开计时，不以失败时的空流减少平均耗时。事实回答实验开关默认继续关闭，只有完整质量回归门禁通过才能成为默认。

**不应全靠二次模型审判：** 首先用确定性证据-主张规则、型号检查、数字/否定边界和来源范围做拦截；必要的语义审查也应有独立评测集与人工抽检。

## 六、技术契约：关系与权限

### 6.1 Relation 不等于 Grant

```ts
type RelationV1 = {
  relationId: string; subjectId: string; objectId: string;
  type: 'owns'|'uses'|'maintains'|'shared_household'|'lent_to'|'gifted_to'|
        'compatible_with'|'mentioned_in_story';
  source: 'user_statement'|'confirmed_action'|'document'|'system_observation';
  effectiveFrom: string; effectiveTo?: string;
  scope?: string; revision: number;
};

type GrantV1 = {
  grantId: string; issuerId: string; subjectId: string;
  resourceType: 'item'|'task'|'story'|'memory'|'capability'|'device';
  resourceId: string; actions: ('read'|'write'|'share'|'execute'|'revoke')[];
  scope?: string; expiresAt?: string;
  grantedAt: string; revokedAt?: string; revision: number;
};

type AccessDecision = {
  allowed: boolean; reasonCode: string;
  policyRevision: number; filteredContextRefs: string[];
};
```

**执行原则：** 同一家庭、共同使用、曾收过礼物、被故事提到，都不能自动授予私人记忆查看权。`canRead` 旧接口由新 `authorize(actor, resource, action)` 逐步替换，旧 JSON 模型通过 adapter 继续可读；所有跨用户共享与工具写入都必须经过服务端裁决。分享指定型号的厂家知识，不意味着分享个人资料上传全文、照片、私聊或记忆。

### 6.2 隐私场景必须全过

1. A 邀请 B 入家：B **不会**自动获得 A 的物品清单。
2. A 仅共享相机：B 可看到获准档案/公共厂家事实，**看不到** A 私密故事与购买凭证。
3. B 接手家庭事项：只能看到 A 确认的任务摘要和被授权物品信息，不能顺带召回私聊。
4. A 撤销对 B 的共享：下一次 API/工具检索立即拒绝；旧缓存/模型输入/活动任务不得继续使用旧内容。
5. A 送礼给 C：C 得到新实例、获准故事快照与来源；A 看不到 C 后续私人故事。
6. 任一人「忘记」个人记忆：下一轮检索、相关上下文与准备给模型的内容不再包含它；历史必要审计按独立政策处理。

**高风险特殊情况：** 已生成给第三人的永久快照不一定可在对方已持有的副本中远程删除；产品必须明示“撤销将阻止未来访问，但不能撤回已获得的副本”，必要时支持收礼端收到更正通知，而不能承诺技术上不可能的完整遗忘。

## 七、技术契约：能力注册与工具

```ts
type CapabilityRegistrationV1 = {
  capabilityId: string; targetType: 'product_model'|'item_instance'|'software_simulator';
  targetId: string; operation: string;
  sourceState: 'documented'|'discovered_candidate'|'read_observed'|
               'software_verified'|'hardware_verified';
  evidenceRefs: string[]; adapterId?: string; adapterVersion?: string;
  inputSchemaId: string; outputSchemaId: string;
  risk: 'read_only'|'local_write'|'device_write'|'external_send';
  requiredGrantActions: string[];
  canReadback: boolean; failurePolicy: 'abort'|'unknown_and_reconcile';
};
```

- 阅读能力和修改能力必须分开授权；有协议文档不代表硬件在线或用户已授权。
- REA 输出只先登记 `discovered_candidate`；只读探测后 `read_observed`；用户明确授权写入、成功并回读的**自有软件灯**才是 `software_verified`。
- 控制真实设备还需来源合法、协议/接口适配、设备可达及实际硬件回读，才能声称 `hardware_verified`。
- 普通衣服、相框、纸盒等物品也可以具有“人工可实施能力”与创意条件，不强行要求数字接口。
- 外部发送、赠礼、付款、账号权限变更属于高风险动作，需人确认；**本设计不授权额外费用或真实外部发送**。

## 八、跨模块接口与责任边界

| API/服务建议 | 输入 | 输出 | 必须保证 |
|---|---|---|---|
| `resolveTaskContext` | actor、goal、入口、物品/任务引用 | task/run、可读取的 Context refs | 当前身份和权限、最小必要数据 |
| `readEvidenceClaims` | 准确型号、子问题、用户可读来源 | claim verdict、适用范围、原文依据 | 缺证≠否定；跨型号不误混 |
| `planService` | 已授权 item + 目标约束 | 可行方案、缺口、必要条件 | 方案不等于已执行；不编造物理条件 |
| `requestAction` | task/run、capability、参数、confirm、requestId | 预期写入回执或等待授权 | 幂等、对象 revision、Grant 二次校验 |
| `getTask` | taskId、actor | 对当前 actor 过滤后的任务视图 | 不跨账号泄露敏感字段 |
| `recordOutcome` | task/run、依据、反馈者、证据 | 真实度分类的 Outcome | 用户报告≠设备回读；失败可修正 |
| `shareItem` / `handoff` | item、member、scope、必要摘要 | Grant + 交接回执 | 仅有权成员；敏感信息最小化 |
| `composeGift` / `claimGift` | item、选中故事、收礼身份与确认 | 新实例、经许可快照、流转关系 | 无私密记忆/照片默认复制 |
| `recallExperience` | actor、task、item、策略 | 有来源/允许召回的经历片段 | 纠正/遗忘/撤权时不返回 |

**建议的后端边界：** `TaskService` / `ContextResolver` / `EvidenceService` / `PolicyEngine` / `CapabilityRegistry` / `OutcomeStore` 为功能接口；可以先映射到现有 SQLite/模块，不要求立即拆成微服务或独立进程。

## 九、实施迁移：整体一轮可以做，但必须阶段可恢复

**Gate 0 — 设计定案（Codex 开始前）**
- 产品理念文件固定；本评审的关键领域契约和任务状态定义经过一致性检查。
- 选定最小可用的读/写适配层方案，明确旧数据如何与新模型相互映射。
- 冻结测试用例的核心事实真值和安全条件，记录风险例外。

**Gate 1 — 统一安全与资料证据**
- 增加 `EvidenceService`、可审查的 Claim 决策及来源适用性，不给未经核验的生成事实通行。
- 用已经发生过的事实错误做反例，包括 ANC、保修、维修政策、异型号参数。
- 不更改演示/个人数据库，优先无损适配与离线回归。

**Gate 2 — TaskRun、Context 和权限内核**
- 从原会话/计划/家庭任务接入统一 Task ID / Run ID；读时解析最小上下文。
- 以 PolicyEngine 实现授权判定，保留旧 `canRead` 兼容适配但禁止新增越权绕行。
- 使用版本/幂等和持久回执支持撤权、超时、重启恢复。

**Gate 3 — 专业能力接入**
- 快速事实问答、步骤指导、跨物品目标、创意/改造、数字分身、故事、家庭和赠礼均接入统一上下文协议。
- 将软件灯验证纳入 Capability Registry；但真实硬件必须单独测试，不能通过软件仿真自动判定。
- 对所有专业工作流保留既有质量强项，并消除重复路由与重复检索。

**Gate 4 — 入口和体验升级**
- 对 3、4 和现有多入口原型做任务查找测试，选择最终导航；先满足完整旅程，再调整视觉细节。
- 物品详情与任务中心显示同一当前任务、结果和可继续动作；故事、家庭与赠礼均可从场景入口继续。

**Gate 5 — 全量验收和交付**
- 既有回归全通过；85个真实商品/合成家庭测试案例形成逐案证据；事实问答随机样本人工审阅。
- 真实模型测试和费用仅在获用户批准后开启；模拟/在线来源标识完整，保留原始失败。
- 数据迁移不丢失历史物品、礼物、故事、家庭状态和会话；演示与真实身份隔离。
- 所有阶段可在**同一轮 Codex 大任务**推进，但每门保留可恢复提交和明确通过/阻断条件；无法通过时停在可运行结果，报告具体原因，不以进度文档替代实现。

### 9.1 最小迁移步骤（实操指导）

1. 建立只读 `LegacyDomainAdapter`，读原 `workspace.body` 及现有 relation 字段，产生 `ProductModel`/`ItemInstance` 候选视图；不修改原数据。
2. 为新任务、Grant、Claim、Capability 和 Outcome 增加独立 SQLite 版本化结构，并建立幂等请求键及 owner-scope 索引；每个模型都有 `schemaVersion`。
3. 在少量关键读路径使用双读对比；新数据未齐时退回旧读路径，记录差异。
4. 将单个业务动作的实际写入统一收敛到受检事务服务；对于旧状态变化采用同事务兼容写入，不安排永久双写无协调。
5. 增加迁移回放、旧版本恢复路径与完整性校验；只有影子对照过关后才默认切换。
6. 数据删除/覆盖/迁移回滚如会影响真实用户信息须先确认；此 RFC 不构成数据变更授权。

## 十、测试评价：契约测试先于模型抽样

| 类型 | 检查对象 | 阻断条件 |
|---|---|---|
| Schema | TaskSpec、TaskRun、Claim、Grant、Capability、Outcome | 未知字段/越界对象/缺少revision 被默认接受 |
| 权限 | 共享撤权、家庭成员、赠礼、私人故事 | 任何未经许可的信息跨身份泄露 |
| 执行 | 重试、超时、中断、回读、不确定结果 | 重复执行副作用、把模拟成功写作真实设备成功 |
| 证据 | 无证否定、型号混用、售后政策、数字限制 | 任一无证实的关键确定性断言 |
| 连续性 | 物品→家庭、故事→赠礼、问答→创意、任务刷新 | 丢任务ID、错物品、丢已试步骤、错误继承私密上下文 |
| 用户价值 | 用户任务目标、实际受益、体验负担 | 只凭按钮存在或 HTTP200 宣称业务完成 |
| 回归和性能 | 当前371项离线基线与新增契约、真实模型/浏览器 | 重大旧功能退化；性能报告用失败样本冒充提速 |

**优先验收样本：** `QA-05, QA-06, QA-17, CONSTRAINT-01~05, PERSONA-04~06, FAMILY-01~09, GIFT-01~08, AGENT-01~09, ENTRY-01~09`；完整85案不应因先测重点而被取消。成功的动作需要读回可核实的结果；不适用实物验证时应标明 `simulation_only`。

## 十一、导航原型的决定标准（不得凭展示图直接选定）

独立附件《物间_导航与任务连续性_三方案可点击原型.html》提供 3、4、7 主入口对照。它是**导航与流转测试工具**，不是应用的新 UI 设计、不是实际 Agent，也没有连接真实账号数据库。

测试步骤：同一位受试者在随机或平衡顺序下分别体验 A/B/C；每种导航在“第一次会点哪里”、成功找到目标操作、点击数、绕路数、是否能保持任务物品上下文上评分；任务与页面名称按既有 `ENTRY-01~09` 制作。真实参与者评分再决定导航，不采信模型对自己原型的主观打分。

**建议的接受线：** 关键任务必须100%有可到达路径；不能出现帮助/赠礼/长辈需求的死路；普通任务不强制先录入所有物品。首次发现率、点击数与误入按使用测试数据比较；5—8人用于识别明显问题，不能推出人群级统计优势。

## 十二、还需要业务负责人决定什么

只有两个会改变开发方案的关键选择：

1. **允许把这套接口作为整体升级的默认工程契约吗？** 若认可，Codex 可以一次性连续执行各 Gate，保留回退与真实验证；若不认可，先修订而非让模型临场创造新架构。
2. **导航是否在得到初步任务测试结果后再做最终定案？** 当前原型仅比较信息架构；不是新视觉稿。建议先收集至少一轮真实任务使用数据后再锁定主入口。

**不建议现在决定的事项：** 是否上公网、支持哪些真实智能设备协议、是否建立公开物品社区、是否采用新框架、多 Agent 是否成为基础设施。这些需要后续具体验证；不妨碍统一基座按当前逻辑升级。
