## 0. 给团队的决策结论（先读）

这版有实质工程进展，**不应推倒重做**。新增了 `src/lib/ai/harness.ts` 的最小任务执行与核查、`src/lib/products.ts` 的型号专属 Product Pack、`service_runs/service_feedback` 的 SQLite 记录、若干组件拆分，以及可双击启动的 Windows 分发包。相比此前仅有硬编码问答与单页逻辑，方向正确。

但它目前仍属**可交互工程原型 + 部分可信 AI 底座**，还不是已验证的「识物—懂人—懂物—组合—执行—关怀—记忆」产品。最关键的空缺：

1. **输入端尚无真实图片识别、扫码解析与型号匹配闭环**；只能上传档案图片与手动选少数资料包。
2. **Product Pack 只有罗技 M185 的两个型号变体的人工整理规格事实**，且明确不包含完整使用/排障步骤；不能支持海量物品泛化。
3. **AI Harness 只具备单次只读模型调用与格式/引用 ID 校验**，没有完整的工具选择、分步执行、运行状态、事实蕴含检查、失败恢复、评测回归。
4. **发现与跨物品规划仍主要依赖两条内置玩法和野餐/旅行正则匹配**，不是对真实能力、条件与创意的通用检索和组合。
5. **人与家庭 Context 主要是固定演示角色与简单共享标志**，没有可解释、可撤回、分人的偏好、关系、维护角色与授权范围体系。
6. **物品数据仍是 JSON 快照**；新增的 SQLite 独立表只覆盖模型运行与反馈。真实多人权限、并发、礼物流转和审计尚未进入生产级。
7. **服务执行记录缺少可复盘的完整输入/输出及检索证据快照**；难以做 FancyTech 式 Evaluation、good/bad cases 和质量迭代。
8. **新分发包未见工程测试目录、测试脚本与产品需求文档**（这是指当前交付的 Windows 包，不代表同学的开发仓库没有）；启动说明明确**未经 Windows 真机测试**。

**总体优先级**：先保护已有功能不回退 → 修正运行/测试和可信性 → 打通 1 件真实商品的识别与指导 + 1 个可验证的多物品创意 → 沉淀可回放运行轨迹与评价体系 → 再深化家庭、礼物、长期数据架构。不是先采购图数据库、造多 Agent 或微调模型。

## 2. P0：马上修补的工程质量和可信性问题

### P0-01｜建立唯一源码、自动测试、可重复构建

- **[实查]** 新包内 `package.json` 没有 `test`/端到端测试脚本；包内没找到老版的 `tests/domain.test.ts`、`tests/browser.mjs` 或 V1.1 需求文档。不能因此断言作者源码仓库也缺。
- **[建议]** Git 主仓库存放源码、`docs/`、锁文件与测试；CI 每次提交运行 `typecheck + lint + unit + integration + build`；关键流程加 Playwright 手机/桌面端截图和自动操作。
- **[建议]** 建立 `docs/implementation-status.md`：功能编号、真实/精选/模拟/未接入状态、负责人、测试截图或 trace、最近构建版本。再建 `CHANGELOG` 与合并请求模板。
- **验收**：其他两名成员从干净仓库 clone 后能按 README 安装运行；同一 commit 的构建可复现；没有把 `.env.local`、用户数据库、旧 ZIP、node_modules 及内部会议资料提交到公开仓库。

### P0-02｜修复「引用编号存在 ≠ 回答可信」

- **[实查]** `src/lib/ai/harness.ts:validateAnswer()` 只验证 JSON 字段与 `evidenceIds` 属于当前 Product Pack；有 Pack 时要求至少一个 ID，不验证**回答的事实是否由引用支持**。
- **[验证]** 在隔离测试中，Pack 事实为「只支持 2.4GHz USB 接收器」，模拟模型却声称「支持蓝牙直连」并引用该 claim ID，现有函数仍通过校验。这证明的是校验逻辑不足，不代表千问已实际犯错。
- **[建议]** 引入「回答切分为可核实 claim → 将 claim 与检索片段逐项匹配 → 验证相容/冲突/资料不足 → 未通过则删减或要求确认」。高风险步骤采用人工预审的结构化 Skill 与确定性安全规则；不要把另一个 LLM 的 yes/no 当作唯一安全屏障。
- **验收**：构建官方资料匹配、反向推论、错型号、未知功能、编造按键等反例测试集；错误的型号专属操作指引必须拒绝或退回「尚不能确定」。记录校验失败原因与证据链。

### P0-03｜把服务的全流程记录为可重放事件

- **[实查]** `service_runs` 保存 run 的元信息（人员、itemId、产品身份、工具名/状态、模型、延迟、引用 ID、tokens），但 `Run` 类型没有完整**用户问题、回答正文、检索片段快照、约束判断、每一步错误**；不能从数据库完整重放一次运行。`service_feedback` 仅 completed/unresolved 用户自报。
- **[建议]** 建立 `task_run / run_step / evidence_snapshot / outcome / feedback` 或等价存储，采用可控脱敏与保留期。包含 `runId, userGoal, actorScope, itemSnapshot, model, promptVersion, toolName, inputHash, resultSummary, retrievedEvidence, decision, latency, tokenUsage, errorCode, userFeedback, verificationBasis`。
- **隐私界限**：输入和原始照片不应默认永久保留；敏感字段单独授权/脱敏，日志不可成为全家都能看的聊天库。
- **验收**：任何一次 AI 建议可回答「当时谁在什么权限下问了什么？检索了哪份资料哪个版本？模型与工具做了哪些步骤？用户反馈什么？什么未被验证？」。

### P0-04｜先把权限和数据安全边界写进测试

- **[实查]** `x-demo-actor` 可在本机任意选择 `lin/dad/friend`，`canRead()` 依固定人员和 `shared` 布尔值判定；`localOnly()` 限制 localhost 与 Origin。开发包已说明**不是真实认证**。
- **[建议]** 保留本地演示模式，但严禁原样部署公网。真实协作时，服务端会话校验身份；显式 `household_membership` 与资源级权限，分开 `view/use/manage/maintain/gift/see_memories`，对附件和礼物链接同样授权。记录撤权后的实时访问行为。
- **验收**：覆盖未授权读物品、读取私密故事、修改别人维护记录、借角色头伪装、过期礼物链接、撤权后的缓存、并发重复认领等负向测试；禁止客户端角色字段作为真实身份依据。

### P0-05｜稳定数据、升级与回滚

- **[实查]** `src/lib/db.ts` 以一个事务中的 JSON 文档保存全部物品、任务、礼物等；`migrations.ts` 已有备份与服务记录表，但不是全量关系数据迁移。
- **[建议]** 一方面立刻建立数据库版本与导出/备份/恢复工具；另一方面逐步将高频对象（User, Household, Item, Membership, Permission, Task, Gift, Transfer, Memory, Evidence）迁为独立表，在中间层兼容当前 UI，避免「先重写数据库、其余全停」。
- **验收**：旧 2.0 demo 数据迁移后 ID、所属者、任务、礼物和故事不丢；并发写入无覆盖；恢复备份能再次启动；失败迁移不会留下半成功状态。

## 3. 真实「扫一扫就懂」的两条识别路线（F1/F3）

**A. 生态订单入口（未来依赖实际授权）**：授权订单 → 解析商品、SKU/规格与数量 → 映射 Product Catalog → 建立 *候选拥有记录* → 到货/赠送/退货等状态确认 → 形成具体 Owned Item。不要默认淘宝天猫订单接口已经可用。

**B. 独立实物入口（应优先研发）**：

1. 摄像头、相册图片、商品二维码、条码、铭牌 OCR、用户文字，多入口可并存；未登录直接问物品无需先保存。
2. 码制分类：UPC/EAN/GTIN 等条码一般优先用于商品识别线索，**不保证唯一锁定生产批次、硬件修订版或用户手上这件物品**；QR 可能只是营销/售后链接，必须验证地址和上下文；铭牌和完整型号更适合区分版本。
3. 识别输出候选 Top-K：品牌、系列、型号、修订版、识别依据、置信/不确定项；不要因外观相似就自动认定型号。
4. 结合官方知识检索，提供用户一步确认，必要时提示补拍机身底部、标签、接口或包装。确认后形成 `ItemIdentityBinding`（来源、时间、确认者、证据）。
5. 匹配不到时，允许「临时通用求助」「手动添加」「上传说明书」，禁止编造该型号按钮/接口。
6. 如果用户选择保存，转换为 Owned Item，并正确处理同款多件、数量、送人、消耗、借用、转手及已有重复记录。

**建议技术流水线**：本地 `getUserMedia`/文件选择 + 条码解码（BarcodeDetector 可检测时使用，并提供 JS/WASM 兼容 fallback）→ OCR/VLM（按需要）→ 多来源商品检索 → 实体消歧与校验 → 资料包绑定。**扫码识别、码到商品详情、真正获得官方手册，是三件独立的问题。**

**测试集**：10—20 件真物品，至少覆盖相似外观、缺少铭牌、低照度、反光、无品牌手作、二维码失效、多版本不同配件、私人礼物。记录识别正确率、人工确认次数、失败率和耗时。至少拿 3 个商品做「确切型号 → 正确说明书 → 可执行步骤」的真实演示。

**拒绝造假的要求**：上传图片成功不等于 AI 识别；输入自定义型号不等于已匹配官方资料；接入 VLM 不等于能够自动验证现实动作。

## 4. Product Pack：让说明书变成 AI 可用的能力、约束和步骤

当前 M185 的 `Product Pack` 仅是少数人工摘录的 `claims/limits`。下一层不是堆更多 PDF，而是形成可维护的 **Machine-readable Product Pack**：

```
ProductModel / Revision
  ├─ Identity：品牌/型号/变体/序列化规则/适用资料版本
  ├─ Evidence：官方链接/文件/页码或章节/摘录/核查时间/可信级别
  ├─ Capabilities：功能、输入、输出、任务角色、条件
  ├─ Constraints：安全、环境、尺寸、材料、电气、兼容性、前提
  ├─ Components：按钮/接口/配件/耗材/位置、图示
  ├─ Skills：安装、使用、维护、排错的结构化分步流程
  ├─ Evaluations：怎样验证这一步已完成，客观/用户确认/未知
  └─ Status：来源已核实/需要确认/已过期/不适用
```

**资料处理流程**：官方页面/PDF/用户手册 → 文本/表格/图示分块 → `型号-版本` 对齐 → 结构化抽取 → 事实溯源 → 人工审查关键步骤 → 导入检索库 → 每次回答带准确出处。商品页和民间帖子可作为其他来源，但不能假装「官方」。对已知失效或互相矛盾版本应标识。版本变化触发旧 claim/Skill 失效检查。

**先做精选三类商品而非 1000 SKU**：例如一件有清晰使用说明的家电、一件有接口/配件兼容性的消费电子、一件手作/普通用品（可能只有用户资料），证明能共享同一套框架而不是为 M185 硬编码。

**资料评测**：跨版本错配、官方找不到的操作、图片文字冲突、需要专业维修、说明书仅说「兼容」但现实未满足前提，都要能回答「不知道／需要核对」。

## 5. Agent Harness：当前雏形如何走向可可靠执行的产品

FancyTech 会议纪要中，管理层提出了「任务说明书 → Reference → Evaluation → good/bad cases → Benchmark → 后续改进与模型选择」的框架。**这是访谈中的公司陈述与可借鉴的设计方法，不是我们已验证的技术事实，也不意味着需要复制其商业架构、自动训练或多 Agent。**

### 5.1 不需要一物一模型，也不必一开始多 Agent

推荐在当前 Next.js 服务端先形成**一个有状态任务编排器 + 受控工具注册表 + 共享物品/用户知识**。不同任务套不同的「任务说明书/Skill」；复杂到有必要时再引入 LangGraph 等框架。关键在于执行规则可测试、每一步可追踪，而不是用了什么框架。

### 5.2 必须区分模型建议、工具读取、业务写入

推荐任务状态机：

```
请求/生活目标/事件
 → 理解意图与识别涉及的人和物
 → 授权/用户 Context/物品状态取数
 → 选择任务 Skill（问答/排障/妙用/目标/家庭/礼物）
 → 调用商品资料、图像、组合或家庭规则等只读工具
 → 候选计划生成
 → 规则验证（安全、型号、兼容、来源、状态、用户权限）
 → 需要时向用户确认缺失条件
 → 输出分步方案/建议/可执行操作
 → 用户同意后通过业务 API 执行允许的变更
 → 验证/用户反馈/失败回退
 → 按授权保存结果与必要记忆
```

**模型不能直接写家庭/物品数据库。** 所有变更由业务服务二次校验角色、授权、幂等性和当前状态；模型只是输出候选参数或操作草案。危险操作、自动购买、向家人发送敏感内容、礼物所有权变更需人工明确确认。

### 5.3 工具契约（第一批建议）

| 只读/识别工具 | 作用 | 写入/事务工具 | 触发条件 |
|---|---|---|---|
| `resolve_item` | 找到用户所指物品、确认角色权限 | `save_item_binding` | 用户核对型号并同意 |
| `search_product_knowledge` | 按型号/版本检索事实与来源 | `save_service_outcome` | 用户确认操作结果 |
| `extract_capabilities` | 取得已有功能和使用限制 | `create_family_task` | 指定分享范围、负责人并确认 |
| `get_actor_context` | 取得最小必要个人偏好/任务情境 | `update_maintenance` | 操作人有权且确认日期/行为 |
| `list_accessible_items` | 列出可用物品、状态与未知项 | `create_gift_draft` | 用户选择已录入物品与内容 |
| `check_constraints` | 尺寸、接口、安全、耗材、场地限制 | `confirm_gift_transfer` | 双方状态和实际交付确认 |
| `get_family_context` | 只返回有权限看的家庭关系与事项 | `save_memory` | 用户选择保存范围/真假性质 |
| `get_device_signal` | 数据来源/有效期/离线/授权 | `update_consent` | 数据主体明确操作 |

工具返回统一 `{status, source, asOf, evidence, uncertainty, scope, result}`；必须限制权限、超时、重试与工具循环次数；遇到空资料、安全风险和授权不足走明确的 fail-closed 路径。输入文档、网页与用户上传信息均按不可信数据处理，做 prompt-injection 测试。

### 5.4 Reference / Evaluation / 错题库：适合我们规模的落地版

- **Reference**：按任务存高质量人工审查案例（好回答与不好回答、对应可信商品证据、使用条件）。不是无来源的「智能生活妙招大全」。
- **Evaluation**：对身份正确、事实有据、约束满足、安全、可执行、对人有帮助、交互成本分别评价；数值指标与人工盲评结合。
- **Bad case**：识别错型号、遗漏关键条件、虚构兼容、把用户确认当客观验证、无授权读取家人的故事、拟人台词冒充设备传感器等。
- **Good case**：明知型号不足而请求补拍；无新购却完成任务；家庭任务转交但隐私保留；赠礼故事只传递被选内容。
- **回归**：每改 prompt/model/Product Pack/检索/工具，自动回放同一组案例；如果安全或事实正确性下降就阻止合并。
- **成本**：采集延迟、tokens、成本估算、失败率；简单请求优先明确规则/索引，复杂创意再用模型；模型切换必须用同一 benchmark 比较，不凭「更贵/更新」判断更好。
- **不要照搬**：未经授权共享用户家庭数据做训练、自动把单例经验提升为公共事实、上来就 RL/后训练、创建数十 AI 员工，都不属于比赛阶段合理做法。

### 5.5 第一阶段实际验收

同一个问题输入不同 `item/model/user/context` 时，能看到检索和输出确实变化；错误资料可被拒绝；工具报错后可解释恢复；任务至少经历 1 次追问和 1 次用户反馈；所有这些都留下受控可查的 trace。

## 6. 如何真正「理解人」以及「人与人」—— Context 不是堆画像

建立**最小够用、用户可控制**的分层 Context：

1. **显式信息**：用户告诉系统的偏好、技能熟练度、目标、交互方式、已确认的物品实际状态。
2. **关系信息**：购买者、所有者、使用者、照料者、被赠送者、借用者、家庭成员，包含时间和授权范围。
3. **任务情境**：现在想解决什么、时间地点/预算/人数/已有资源/场地条件；一次性情境默认不写入永久画像。
4. **审慎推断**：用户可能偏好简短指导、喜欢某类手工，须标记「推测、为什么、何时、有效期、允许纠正」，不能因为购买/赠送过商品就认为本人喜爱或正在使用。
5. **人与人关系目标**：例如「爸爸希望自己能操作、女儿希望减少反复解释」，这与单纯「净水器需要维护」不同。应优化长辈自主性、子女负担和信息边界。

建议数据字段：`fact_id/subject/scope/field/value/source/observed_at/confirmed_at/confidence_or_status/expires_at/visibility/consent_id/correction_history`。其中个人敏感生活习惯使用最少收集、可删除和到期失效原则，不能默认训练模型。

**上下文装配（Context Builder）**：任务相关性排序、权限过滤、事实与推测分离、过期规则、长度预算、引用来源与敏感信息脱敏；`爸爸问净水器` 只带有权限的净水器资料、他的操作偏好及必要维护情境，而不带家庭其他人的全部购物记录与情感故事。

**可测试场景**：同一台设备由技术熟练的子女、需要大字/语音的老人、临时来访者分别提问，输出的术语、步骤、可用权限不同；**事实和安全标准不能因人格/风格变化而下降**。

## 7. 物品与物品如何协同：从关键词清单走向能力+约束+创意

**[实查]** `planning.ts` 用 `/野餐|郊游/` 与 `/旅行|出门|出游/` 选固定模板，再用 `/水杯|保温杯/.../` 这样的名称正则筛物品。它无法判断物品是否真的兼容，也不理解数量、功能与剩余耗材。`ideas` 固定绑定 `lamp/frame/beads`；新增商品不会自动进入这两条创意。

### 7.1 能力模型与关系

- 商品/物品具备 `Capability`：提供什么功能、需要什么输入/电源/尺寸/材料/辅助物品、实际可用状态与来源。
- 任务具有 `Requirement`：必须满足的条件、可选质量目标、人数/数量、场景限制、安全约束。
- `Compatibility`：接口与方向、供需数量、尺寸/规格、适用版本、可替代边界；不能光凭两个商品都带 HDMI 就宣称能连用。
- `UsagePattern`：可直接接线的**能力协同**、一起完成任务的**任务协同**、生活小妙招的**类比重组**。
- 输出「确定可用／可能可用需确认／不兼容／未知／确实缺少」，并明确原因，不强制先购物。

数据库初期用关系表（item/capability/requirement/compatibility/recipe/provenance），根据查询复杂度再考虑图数据库。**不因名字叫 Capability Graph 就必须安装 Neo4j。**

### 7.2 妙用发现的三段式引擎

**第一段召回**：商品真实功能 + 已许可/可使用的公开教程和真人案例 + 用户已记录的成功玩法 + LLM 功能类比生成候选。**不能无授权搬运整篇小红书/B站内容当成自有数据。**

**第二段适配**：结合用户实际拥有的物品、材料数量、使用环境、个人能力与兴趣，在候选玩法中进行筛选；为未知条件生成不超过必要数量的确认问题。

**第三段验证与呈现**：给出「所需物品、用户已有、缺少/待确认、每一步方法、注意事项、可靠依据、预估时间、创新点、可替代方式」，区分真人案例/官方功能/AI 未实测创意。用户主动选择「试试」，完成后可反馈可行性并保存照片。

**游戏化边界**：只用于「发现」主动探索，例如解锁已尝试组合/记录真实作品；维修、故障、老人求助严禁签到闯关式设计。

**推荐测试题**：至少 10 组真实拥有物品（可含手电筒、杯子、夹子、收纳盒、拼豆、相框、野餐装备）；请独立评审「新颖、可行、实用、风险、是否愿意真正尝试」，与通用 AI 基线比较。完全随机合成两个物品、编造材料兼容或鼓励不安全改装应判负分。

## 8. 家庭：不只是共享物品，而是围绕物品共同照顾人（核心 F6）

设计三套紧密联系但边界不同的能力：

**A 共享物品与责任协作**：家庭空间、共享物品卡、购买者/所有者/主要使用者/负责人、任务分派与交接、评论、维护历史、相关手册、历史未解决的问题；「已收到」「处理中」「已完成」「用户确认」「客观检测」状态分开。任务可在共享物品下创建，也允许不依赖物品的家庭协作事项，但不扩张为通用飞书。

**B 物品维护与闲置照料**：官方维护周期、用户上次真实记录、确认过的消耗量和适用环境 → 提醒/推迟/完成/变更负责人/下次时间。对于闲置未使用提醒，只有可信观察才能断言「最近没使用」；单纯用户没打开 App 不代表物品没有使用。

**C 家人关怀（经授权）**：适用于子女与老人，围绕真实设备活动的温和关怀：数据主体同意 → 数据来源质量检查 → 与用户自己的时间习惯比较 → 区分 `没有数据/设备离线/外出/授权暂停/真正缺少使用信号` → 低打扰通知给授权亲属 → 明确无法推断健康/安全事件。确认老人本人意愿、自主性和撤销权；误报率高时规则自动降级/关闭。

目前示例全家固定 `lin/dad`、单 `care` 对象，不支持多个家庭/设备/规则/授权粒度。后续要将 `CareRule` 绑定 `device_id + owner + data_source + consent + baseline + allowed_recipient + quiet_hours + escalation + expiry`，同时记录静默和停止的原因。

**验收场景**：爸爸把净水器共享给子女，子女接管维护任务；爸爸可自行获得说明；维护到期后创建事项；在授权且存在真实/明确模拟信号时出现关怀提示；设置外出/暂停/设备离线后不误报；撤权后家人不再看见相关个人活动。每一件物品的帮助最终回到人的便利和关系。

## 9. 赠送、数字心意、长期记忆与可选角色（F8/F9）

**已确认业务规则**：实体物品**不限渠道，但先进入系统获得具体 Item ID 才能发起赠送**；未登录可访问礼物体验；阅读祝福不转移归属；认领须确认实际取得物品；仅传递用户明确选择的内容；收礼人后续私人记忆默认不回流。

**下一步深化**：

- 礼物模板不局限文字：视频、语音、照片、互动小故事、可选角色性格、昵称、欢迎语与链接/二维码；真实拍摄与 AI 合成要区分，声音/肖像授权。
- 将「送礼创建、待接收、已浏览、认领中、已认领、撤销、过期、争议」作为明确状态机；支持并发幂等、防重复认领、链接到期/重新生成和线下交付确认。
- **保持身份连续但权限分段**：一件 Item 的归属可变，原购买者和旧家庭私密记录不能因更换主人泄露；商品知识与用户选择的故事随物品走；真实记录保存 `original_author/provenance/visibility/consent`。
- **[实查/设计缺口]** 现有 `claim` 分支将选中的故事文本重新创建为 `author: 接收者` 的记忆，丢失原始作者信息。建议改成携带来源的 `GiftContentSnapshot`，并由收礼人另行创建新故事。礼物应表达谁给了谁什么心意，不能抹掉赠送者归属。
- 角色不应冒充真实情绪和物品状态；当用户问维修/安全时，优先准确服务，退出人格表达。

**验收**：同一件用户手工制作作品，录入→设计音视频祝福及可选角色→访客链接→受赠人认领→故事正确署名→各自后续私密记忆隔离；礼物过期、已撤销、重复认领和越权查看需有真实负向测试。与普通电子贺卡比较「物品身份及长期经历」是否提供额外价值。

## 10. 生命周期、主动服务和生态接口

将订单、物流、到货、安装、首次使用、维护、耗材、报修、借用、闲置、赠送、转卖、归档建成**可选事件驱动链**，不是用户必须手工填写每个状态。关键是「事情发生时提醒该谁、是否需要行动」，而非每天机械推送。

- 事件模型：`OrderCandidateCreated / ItemConfirmed / Delivered / MaintenanceDue / MaintenanceDone / UserNeedsHelp / GiftOffered / GiftClaimed / PermissionRevoked` 等，可来自用户操作、授权生态接口、提醒规则或设备信号。
- 事件来源与可靠性分级：平台订单 ≠ 真正持有；物流送达 ≠ 用户已使用；到期 ≠ 耗材确实耗尽；信号缺失 ≠ 老人发生问题。
- 通知中心：站内为基础，推送/短信/微信需真实渠道权限才开放；去重、安静时段、批量合并、撤回授权、误报反馈。
- 卖家售后：现有链接和问题摘要继续保留；下一步将 SKU/购买凭证、现象、照片、尝试步骤整理为**用户确认后**可转发的工单。不能声称官方售后系统已连接。
- 阿里生态：独立适配器，不让订单 API 成为产品第一使用门槛；接口可用性与字段、授权及审核合规需要单独实证。

## 11. 数据模型与后端逐步升级（建议 schema，而非强制马上重写）

```
users
households / household_memberships
product_models / product_versions / product_packs / evidence_sources
owned_items / item_identity_bindings / item_state_events
item_person_roles / resource_permissions
item_capabilities / compatibility_constraints / usage_patterns
user_context_facts / consents / context_corrections
service_cases / task_runs / run_steps / evidence_snapshots / feedback
activity_goals / task_requirements / plans / plan_items
ideas / idea_item_roles / idea_attempts / outcomes
family_tasks / assignments / maintenance_rules / care_rules / device_signals
memories / media_assets / gift_offers / gift_content_snapshots / item_transfers
notification_rules / notifications / audit_log
```

**建模规则**：

1. `ProductModel`（同型号）与 `OwnedItem`（这一件）分开；手工制品可以没有 SKU。
2. 一个人的订单与一件物品不是必然 1:1，处理多数量、赠送、退货和同款多件。
3. `ItemPersonRole` 与 `HouseholdShare` 分开；买家、所有者、使用人、照料负责人可能不同。
4. `Evidence` 与 `State` 分开；客观接口、用户确认、模型推断、官方说明各有来源与时效。
5. `Task` 与 `Outcome` 分开；「操作已执行」≠「用户称成功」≠「客观验证成功」。
6. `UserContext` 与 `Memory` 分开；推断偏好不是历史事实，AI 拟人故事不能伪装为真实经历。
7. 每次数据修改产生审计记录；高风险操作需要乐观锁/事务与幂等键。
8. 迁移旧 JSON 时保证旧 ID 与分享关系/礼物不变；逐步将前端切到服务层，不直接把 SQLite 表结构暴露给模型。

**技术取舍**：本机单用户可暂留 SQLite；支持多人协作与云端分享时，可评估 PostgreSQL（配合可靠的会话认证、对象存储及行级/服务层权限）。Neo4j 不是必需条件；只有能力关系查询确实复杂到关系数据库方案明显欠佳时再做性能/维护成本比较。图与关系表均可实现能力网络。

## 12. 测试、Benchmark 与有说服力的比赛展示

### 12.1 建议建立四套可复现评测

**I 识物与知识**：20—30 个实物/图片/条码与型号版本样本，考核 Top-1/Top-K、错误匹配、需人工确认次数；另选 30 道说明书有据/无据/错版本问题，测资料召回、事实支持与拒答。

**II 物品服务**：至少 10 个具体操作/维护/排障场景，含错误按钮、缺少配件、危险维修、相似型号，比较任务完成时间、真正完成率、与普通搜索及通用 AI 的差距。

**III 妙用与任务组合**：10 组实际物品包，由真人盲评创新性、可执行性、适用性、安全、是否真想尝试；特别记录「用户缺一个条件后 AI 是否正确退让」。区分 AI 生成的候选与已被真人尝试验证。

**IV 家庭与记忆**：10+ 个权限/协作/赠送用例，包括 A/B 关怀的离线、外出、撤权、噪声、重复提醒、老人独立操作、认领后私人历史隔离，检查严重隐私错误次数和误报。

测试时分别标注 `静态样例 / 真实模型 / 真人实操 / 外部 API 观测`，严禁用通用脚本声称「设备实时验证」。

### 12.2 指标不是越多越好，而是要证明因果增量

- 成效：真实目标完成率、首问解决率、平均人工确认次数、节省时间、错配/错误指导、建议实际采用率、家庭事项处理时间、用户感知情感价值。
- 可信：支持性引用比例、错型号率、未知承认、错误工具调用、越权次数、撤权是否生效。
- 工程：运行成功率、延迟 p50/p95、token/请求成本、任务回退成功率、build/test 一致性。
- 体验：第一次上手成功率、用户主动开启「发现」后的有效尝试、维护负担、低打扰与老年操作可达性。

**不要**把 DAU、提示词长度、Agent 数量、物品录入数、生成创意数或引用编号通过率当成产品成功的充分证据。

### 12.3 三条特别适合展示的端到端技术闭环

**主线一：实物 → 知识 → 帮助 → 记忆**：拍照/条码与型号候选 → 用户确认 → 对应 Product Pack → 可溯源回答 → 步骤与失败回退 → 本次服务留存 → 再提问不需重新交代。展示错型号时拒答。

**主线二：已有物品 → 新玩法 → 约束 → 真人尝试**：真实用户物品组合 → 基于素材案例+能力筛候选 → 发现一个想不到但可行的妙用 → 核对限制 → 用户选择尝试 → 结果记录。与无上下文通用 AI 结果对比。

**主线三：物品 → 人与人**：父亲家的净水器有维护事项 → 子女接手 → 明确用户授权的 B 类信号提示（无法实测则全程标识示例） → 已处理与下次维护记录；补充已录入手作礼物 → 数字心意 → 收礼体验 → 记忆隔离。体现「物品价值最终回到人际照料和表达」。

## 13. 三人并行开发与可操作任务队列

**重要前提**：角色以下仅是建议，先由三位开发者和仓库 Owner 确认；**同一仓库、各自分支、统一接口契约**，不要两人同时直接重写 `src/app/page.tsx` 或 `src/lib/domain.ts`。

### 开发流 A｜物品识别、商品知识与 AI Harness（技术深化主要负责人）

1. 拉取最新 Git 分支并整理已有 `runAssist`，明确失败/超时/需确认状态；恢复测试。
2. 建立 3 件以上真实商品的 Product Pack，包含确切型号与来源、功能和正确步骤。
3. 搭建图片/扫码/铭牌候选识别闭环与人工确认；无凭证时可先使用离线条码解析 + 公开数据 + 明确标记的有限识别演示。
4. 接通真实千问并验证请求、模型支持、成本、错误返回；将模型配置隔离到服务端，不暴露密钥。
5. 改造 Harness 运行状态与逐步工具执行、资料引用检查、任务追问和失败处理；写 trace。
6. 建立 30+ 例反事实/危险操作/错误证据回归集，连接 CI。

### 开发流 B｜数据库、家庭、长期 Context、礼物及权限

1. 定义版本化数据 schema 与迁移兼容策略，先迁核心关系对象，不破坏旧数据。
2. 从固定角色/共享布尔值，抽象家庭成员与资源级授权；完善有负责人/状态/维护时间的家庭事项。
3. 将维护提醒与 B 类关怀规则分离，建立 signal provenance、授权/暂停/外出/离线/误报规则。
4. 建立结构化 user context（显式/推断/未知）与最小授权检索；实现修改、撤回、到期失效。
5. 赠礼流程修复作者溯源、内容快照、转移事务与重复认领；设计音视频存储接口和收礼人隐私。
6. 做多角色、撤权、家庭协作、赠送负向测试；独立开发环境不得读取其他成员的个人数据。

### 开发流 C｜产品体验、发现组合、QA 与展示（产品统筹）

1. 校对首页和信息架构：正常模式继续保留「我的物品」的显著入口，免注册临时问物品、主动发现、场景规划、家庭、赠礼自然衔接；长辈版以简单服务和关怀事项为主。
2. 拆分 60KB 主页面为稳定路由和组件，明确 loading/error/empty/unknown/retry，补移动端可访问性。
3. 将两条固定妙用演进为可对新增物品适配的玩法候选与「用户想试试」流程；区别官方/真人/AI 假设。
4. 活动规划从名称正则转成条件检查的最小模型；先支持野餐或手工制作两个真实用户场景，而非虚假的任意通用规划。
5. 设计故事式礼物开场与家庭协作视图，视频/角色保持可选。
6. 组织 5—10 位用户体验与逐项验收；制作可重放 demo 数据、演示脚本和失败场景。

### 合并门槛

每条 MR/PR 必须提供：变更目的、影响的 F 编号、数据库迁移影响、接口类型、真实/模拟状态、测试命令及结果、截图或 trace、已知限制、回滚方式。**要合并的是经过验收的成果，不是 Codex 生成的代码行数。**

## 14. 时间顺序与优先级（不要把愿景当截止日前承诺）

当前为 2026-10-17；现有内部计划以 10/20 为验收目标。任务量可以大，但必须把**验收版**和**后续深化版**区分：

| 层级 | 建议先后 | 验收物 |
|---|---|---|
| **P0 不可破坏** | 单一 Git 基线、权限不回退、旧数据迁移、测试能跑、核心路径按钮真实可用 | 自动化测试、可重复构建与可复盘场景 |
| **P0 真技术证明** | 接通模型至少一个场景、3 件精选 Product Pack、模型基于证据答、错误型号拒答、记录 trace | 实际 API 成功日志及失败回退用例 |
| **P1 核心体验证明** | 一个真实识物流程、一组真人验证的创意组合、家庭 A/B 规则与礼物认领 | 端到端演示、来源标签、案例评分 |
| **P1 架构深化** | Context 最小版本、权限精细化、关系型数据拆分与导出恢复、用户可控制的记忆 | Schema、迁移、负向测试和操作录像 |
| **P2 技术纵深** | 自动 Product Pack 抽取、不同模型/工具的评价、真实多用户部署、富媒体赠礼、渠道集成 | Benchmark 趋势、成本对比、授权/安全评审 |
| **远期** | 大规模阿里订单/厂商数据、跨用户验证经验网络、端云与本地模型、真正跨设备活动监测 | 接口授权与严格证据，不提前宣传 |

**可延期，但不能造假**：哪怕比赛只能真实运行 3 个商品，也应清楚显示「正确/未知/不支持」；哪怕 B 类老人关怀没有真设备，也应以可交互授权规则演示其正确逻辑，而不暗示正在监控真实老人。

## 16. 供产品负责人验收的十个实际问题

1. 「我今天拿起一件自己没买过的商品，**不用注册能否扫码/拍照找到准确资料并直接问**？找不到会怎样？」
2. 「我录入一件新物品，**发现页是否随之产生与它有关且可验证的玩法**，而不是永远只有相框+拼豆？」
3. 「这个建议是依据哪份说明书哪一节？**如果我换一个型号，它会及时纠正还是继续编造？**」
4. 「AI 的回答如何用我的实际物品、实际能力和当前目标？**与没有我的物品信息的通用 AI 有什么客观差异？**」
5. 「爸爸和我问同一台净水器，系统怎样体现不同的目标、技能与权限？**又不泄露私有故事？**」
6. 「A 类维护提醒、B 类使用习惯关怀，**哪些是真实数据，哪些是示例？离线、外出或撤权怎么办？**」
7. 「我给朋友赠送一件手作物品，祝福、角色和记忆怎样一起传？**新旧持有者的私密信息会不会串？**」
8. 「你们说有 Harness：请展示一次任务的**输入、工具步骤、证据校验、失败回退与记录**，而不只是打印出一串提示词。」
9. 「如果模型发生幻觉、商品资料版本错了、API 断了，用户会看到什么？**系统有没有可靠降级？**」
10. 「这次改进前后，用户实际任务成功率、错误率、完成时间、建议可用性、tokens 成本有什么**可重复测量的数据**？」

**总原则**：我们从物品价值出发，通过理解「人—物—人」关系，真正创造实用、发现、管理、家庭关怀与情感传递的价值；技术投入是为了让这些价值更可靠、更低成本地发生，而不是只让架构图更复杂。
