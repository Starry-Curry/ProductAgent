# 物间：物品理解、人的理解与家庭照顾的研究取舍

日期：2026-11-04。范围：根据用户最新反馈，核对现有代码、真实开发记录与一手开源资料，调整实施优先级。本轮没有安装候选工具、切换模型、改动业务数据库或调用付费模型做新实验。下列改进均为待验证设计，不是已实现能力。

## 1. 已核实的缺口

1. 最近完整真实旅程 `var/evaluations/20261104-214230/results.json` 中有 26 件物品、1 个持续任务，知识记录为 0。创意步骤调用了 Skill、search_world、read_item、find_items，但没有公开案例搜索。当前“有知识工具”尚未变成稳定知识沉淀。
2. `KnowledgeClaim` 已存 content、conditions、basis、source、quote、scope、status；conditions 和任务 plan 仍是自由 JSON。原文摘录校验能确认文字出自某资料，尚不能确认该资料适用于当前型号/版本，也不能确认模型正确理解了条件。
3. `ProductRecord` 以完整 spec JSON 哈希定身份，其中包括来源链接。相同型号因资料链接差异可能形成不同记录；规范化要将稳定身份与来源清单区分，仍保留地区和真正影响能力的版本差异。无需先替换数据库。
4. `known_claims` 及检索只读取当前用户拥有的知识；赠礼只复制选定经历和人格，未传递可复用的公开商品知识或维护历史。私人隔离正确，但目前不能称知识已随物完整延续。
5. 家庭当前是好友、按物只读授权和简单 Reminder。缺少家庭空间、公共物品的管理关系、照顾责任、周期、认领/完成/异常反馈及通知交付记录。
6. REA 连接绑定到物品，但探索适配器目前只按入口调用工具；没有向探索过程交付统一的型号、已知能力、适用资料、已有观察和未决问题简报，也没有完整的用户逐步操作旅程。
7. 数字分身已有昵称、性格、颜色、成长笔记及证据字段，不是完全没开始；经历驱动的外观成长和可靠叙述仍未实现。

依据：`wujian/database.py`、`foundation.py`、`domain.py`、`retrieval.py`、`devices.py`、`agent_runtime.py`、真实旅程原始结果。没有把所有候选设计当作已存在的数据结构。

## 2. 物品理解应沉淀什么

目标：让模型能回答“这件物能做什么、为什么、在什么条件下、现在能否做、还缺什么证据”，并使同一认识用于用法、创意、维护、分身及赠礼。

最小认识单元应能表达：

- 能力或性质与它支持的动作/用途。
- 生效条件、已知边界、仍未知的关键参数。
- 适用于型号共性还是具体实例；关联版本、当前状态与观察时间。
- 官方资料、公开案例、用户实际报告、模型假设分别是什么。
- 原文/页图/用户反馈依据，以及后续纠正或失效关系。

优先在现有 KnowledgeClaim 与业务操作上验证小型有类型契约，确有查询或演化需求才拆表。非标准物可拥有性质、个人意义与可用条件，不强行绑定 SKU。不能从照片直接确认矿物成分、承重、耐热或未经验证的协议。

学习过程候选：相关资料/观察 → 提取候选认识及条件 → 核对适用范围与证据 → 合并/保留冲突或未知 → 后续任务按需读取 → 实际反馈修正。技能承载通用理解方法；具体商品知识留在可更新数据中。该过程不要求每轮聊天全量执行，更不要求用户填满全部属性。

参考 [Text2Afford 官方论文](https://aclanthology.org/2024.conll-1.27/)及[作者代码](https://github.com/sayantan11995/Text2Afford)：它研究上下文中的物品可供性，并提供数据与评测脚本。适合借鉴相同物品在不同条件下能力变化的测试；它是研究项目，不是可直接接入的通用商品理解服务，也不直接证明对百炼模型的增益。

## 3. 创意案例从哪里来、怎样复用

来源可覆盖：用户提供的具体帖子/视频、公开可读的生活改造社区与教程、官方进阶用法、专业实践、用户真实成功/失败经历。不限于国内平台；国内平台的可访问性要实际验证。

搜索应沿多条线索展开：目标效果、物品属性/能力、原理或材料替代、已知失败。不能只搜索完整商品名，也不能把公开帖子中的效果当作已验证的事实。

应保留的案例内容：原链接与作者/发布时间（取得时）、解决什么问题、原始物品和关键步骤、奏效原理、适用条件、作者实际展示/仅作声称的结果。面向用户迁移时说明哪些条件相同、哪些尚未知；相近转载不重复充当多份独立证据。

| 候选 | 原始能力 | 当前取舍与进入条件 |
|---|---|---|
| [Trafilatura](https://github.com/adbar/trafilatura) | 网页正文与元数据提取、结构化输出 | 静态教程正文提取不完整时，用相同公开页面与当前 BS4 路径对比；有明确增益再引入 |
| [Crawl4AI](https://github.com/unclecode/crawl4ai) | 动态页面读取、浏览器与结构化提取 | 找到确实需要 JS 渲染且可访问的案例页面后再试；不能因此承诺已接通小红书/B站 |
| [MediaCrawler](https://github.com/NanmiCoder/MediaCrawler) | 针对小红书、B站等平台的内容采集实现 | 已核对仓库及[许可证](https://github.com/NanmiCoder/MediaCrawler/blob/main/LICENSE)：当前为非商业学习许可，非可默认嵌入产品的通用宽松开源组件；本轮仅研究其功能范围，未安装或采集 |
| [Open Deep Research](https://github.com/langchain-ai/open_deep_research) | 研究、搜索、压缩与报告的完整工作流 | 借鉴搜索与来源整理方法；目前不整套嵌入，避免与已有 Agent 循环重复 |

当前百炼搜索和原文读取先作为基线。搜索、读取、案例提炼是不同环节；工具负责取到内容，案例能否迁移仍由模型推理和试验检验。视频无可读字幕/正文时，需另行验证多模态路径，不能把标题当作已看过视频。

## 4. 理解人：评估成熟实践，避免两套事实系统

理解应围绕实际帮助所需的信息：目标、偏好、熟悉程度、时间精力、当下条件、人际关系、个人意义和过去选择。一个人不同情境下可以有不同偏好；一时难过不能推断为永久性格。用户自己的经历与送来的故事、模型创作必须区分。

| 实践 | 值得借鉴的机制 | 当前取舍 |
|---|---|---|
| [ReMe Auto Memory](https://github.com/agentscope-ai/ReMe/blob/main/docs/en/auto_memory.md)及[记忆分层](https://github.com/agentscope-ai/ReMe/blob/main/docs/en/memory_as_file.md) | 保留来源；区分事件记录与长期可复用理解；提炼过程经验 | 已使用其检索。本地也阅读了 auto_memory / dream 的实际代码与提示；对自动提炼先隔离验证，不直接开启文件写回与现有 SQL 双写 |
| [Mem0 源码](https://github.com/mem0ai/mem0/blob/main/mem0/memory/main.py)与[更新提示](https://github.com/mem0ai/mem0/blob/main/mem0/configs/prompts.py) | 提取新事实后与已有记忆比较，决定新增/更新/删除/不变 | 评估更新行为及公开扩展接口，不能仅因名气安装；其通用更新规则不自动适合所有个人偏好和故事 |
| [Letta memory blocks](https://docs.letta.com/v1-sdk/memory/memory-blocks) | 少量始终可见的核心理解与其他可检索信息；用户理解和人格块分开 | 可借鉴有限上下文预算和角色分离，不迁移到整套 Agent 平台 |

ReMe 主分支文档说明不等于本地固定版本已通过验证。安装后的检索成功也不证明自动理解/纠正成功。需要用最新用户表达、旧事实、时间、作者与情境冲突的真实应用案例比较。

单一事实来源是当前已有事务、撤权、赠礼机制的有效约束，不是禁止使用外部记忆引擎；若某成熟实现经验证更适合，可以替换相关职责，并迁移/删除旧写入路径，而不是长期维护两套竞争认识。

## 5. 家庭管理与关怀：补上核心体验

家庭关怀是传递价值的一条主线，应有最小完整切片，与赠礼并行保留。公共净水机、空调等仍有自己的型号、当前状态、维护记录；家庭成员有共同可见范围和各自照顾职责。长辈的使用习惯及协助偏好来自实际选择，不由年龄自动推定。

首个候选旅程：

1. 录入公共净水机及家庭关系，读取适用维护资料，记录实际最近更换与使用条件；信息不全时保持未知。
2. 依据实际计时、耗材寿命报告或已确认规则产生待处理事项，展示依据。尚无设备遥测时不伪称检测到滤芯异常。
3. 按家庭选择先提醒合适的人；长辈可选择“我处理/稍后/请家人帮忙”，无需读技术说明。
4. 家人接手后明确谁负责；“看到了”“接手了”“更换完成”分别记录。本人或家人报告完成后更新同一物品及维护历史，再决定下一周期。
5. 静默时段、频率、延后与求助升级由家庭配置；没有收到反馈不直接推断身体或设备出问题。外部通知未真实送达时不标已送达。

可借鉴 [Grocy](https://github.com/grocy/grocy) 的家庭资源与 chores 管理，以及 [Home Assistant Alert](https://www.home-assistant.io/integrations/alert/) 对触发、确认、恢复和重复间隔的区分。当前不引入整套系统。普通提醒、周期任务、通知传递、真实设备状态是不同职责，按切片缺口选择组件。

## 6. REA 与原有物品理解的接续

REA 属于创造。已知型号、固件、官方接口、已有观察应从共同底座读取；不反复让用户提供同一信息。型号仍不确定、资料已过期或实际控制入口变化时再做必要核对。型号已知不意味着协议、认证或控制地址已经确认。

接入候选：生成按需的目标简报，携带当前物品身份/状态、已核对接口资料、授权入口、已有实验及未决问题；不将全部私人回忆发送给探索工具。REA 返回证据继续绑定到同一物品与任务，防止资料里的可用能力与这台设备实际观察混淆。

物间面向用户应说明：已知什么、还缺哪一个条件、下一步打开哪里/做什么、怎样判断成功、怎样恢复，并能在用户完成一步后继续。是否由物间调用工具执行，取决于实际控制通道；本轮不预设所有设备都需同一套逆向流程。

## 7. 调整后的实施顺序与验证门槛

| 顺序 | 下一切片 | 需要看见的用户结果 |
|---|---|---|
| P1 | 物品认识沉淀与理解人的更新共同推进；同时补分段耗时记录 | 在开发用大陆商品/非标物上自动保留有依据的能力和边界，换会话改写问题仍能使用；偏好纠正和临时条件正确生效 |
| P2 | 真实案例帮助创意迁移 | 从未预置答案的公开实例中提炼原理，适配已有资源；资源/条件改变后方案改变；实际反馈进入同一认识与任务 |
| P3 | 家庭公共物品维护与求助接手 | 从维护依据到合适的人收到事项、接手、完成、状态更新的完整小旅程；没有传递到设备的通知不冒充到达 |
| 插入验证 | 有具体目标时做 REA 最小屏保/显示改变 | 复用已有型号资料，按步骤接续，并在真实目标上观察结果及恢复 |
| 后续深化 | 分身的经历归属、成长节奏与外观 | 正确讲述谁的经历，基于相处记录成长；视觉实现不先于事实可靠性 |

P1 的认识同时服务兑现、创造、延续、传递，不能只在创意入口生效。公共商品知识与私人经历的用途区分、赠礼/家庭知识接续应随对应切片补齐；不要提前做全部隐私管理界面。

每次引入工具前记录具体失败、现有基线、预期改善、接入成本和退出条件。用相同模型、等价资料与工具条件做对照，保留首答；不以“有更多字段/步骤/调用”作为智能增益。开发验证与独立验收分开。方法借鉴不等于项目作者为物间方案背书。
