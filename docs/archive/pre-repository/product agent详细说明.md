# 物品智能服务｜产品说明书详细版

**工作名称：** 物品智能服务产品（Product Agent / Owned Item Agent 为历史候选概念，并非已定产品名）  
**所属方向：** 天猫 AI 黑客松 · 智能日常（与 AI WORKS 产品线独立）  
**文档定位：** 产品理念、需求逻辑与完整功能设想的团队讨论稿；**不是 PRD、MVP 决议、技术方案或排期**  
**修订时间：** 2026 年 10 月 13 日  
**版本状态：** V0.3（与精简版同步的产品共识底稿；待团队进一步确认）

> **核心命题：** 让人已拥有的实体物品，更充分、更容易、更持久地发挥对生活的**有效价值**。  
> **用户体验愿景：** 我买过、拥有、使用或与家人共享的东西，AI 能逐渐认得、理解；我需要某件物品时，能轻松用好它；我提出一个目标时，AI 能帮我发现和组织已有物品的能力，而不要求我先把家里整理成精确库存表。  
**核心服务：**「围绕物品求助」与「围绕目标调用已有物品」并列重要；管理、购后服务、维护、关怀与物品流转围绕这两条路径展开。  
**技术边界：** 实时视觉指导、结构化商品能力包、端侧模型、Experience Network 等是候选能力与技术路径；不预设其为现阶段的全部产品形态或已验证的实现。

---

## 一、产品概览：我们在做什么

### 1.1 产品的出发点

用户购买物品是为了满足现实需求，但**购买不等于价值实现**。商品说明书、功能参数、已有配件、使用记录与售后信息分散在订单、包装、品牌网站、视频、客服和家庭成员的记忆中。用户可能不会用、忘记有、想不到组合、找不到资料、疏于维护，或者将物品送给别人后无法延续必要服务。

我们的设想是：AI 以商品与用户的实际关系为基础，在用户需要时召回正确的物品信息，把复杂知识转化为可执行指导，并围绕用户主动提出的目标发现物品的新用途、替代方案和组合价值；在日常使用和家庭协作中，以最低管理成本延续物品价值。

### 1.2 最重要的六个判断

1. **有效价值高于使用频率。** 不是鼓励用户多用东西或多打开 App；急救物品可能长期不用，但关键时刻能找到、会用，就是价值。
2. **人先有目标，AI 再组织物品。** 用户想拼豆才需要材料建议；用户选好出游目的地后，已有装备才成为规划的关键资源。系统不应为提高活跃度替用户制造目标。
3. **覆盖几乎所有实体商品，分层提供服务。** 耐用品通常值得拥有更深的持续使用服务；食品、日用品、手工材料等参与场景与补货，具体管理深度因物品和用户而异。
4. **最低管理精力，尽可能深的服务。** 能从授权购物记录等来源识别的，不要求重复录入；未知或过期状态在必要时轻量确认，允许用户选择更精细的管理。
5. **既懂物品，也懂用户，但不擅自替用户定义偏好。** 购买记录是线索，不等于真实拥有、使用者身份、余量或兴趣；推断需要可解释、可纠正、可撤回。
6. **可信知识与可观察结果比拟人的 Agent 数量重要。** 商品知识应对应准确版本、能力与限制；能观察则验证，不能观察就请用户确认，不编造现实状态或解决结果。

### 1.3 产品的两大主动服务入口

- **从物品出发：** “我的咖啡机怎么清洗？”“这台相机如何做直播？”“爸妈不会用这个电饭煲。”——理解、指导、排障、维护与协作。
- **从目标出发：** “周末去烧烤，家里已有的东西够吗？”“想拼豆，缺什么？”“在家办个下午茶。”——调用已有物品、发现组合与替代、生成可执行计划、识别真实缺口。

此外可以有**轻量的非打扰式服务**：物流、保修或维护事项、快消品补货提醒，以及节假日可选的场景灵感。用户无须因“AI 猜到你可能喜欢某活动”而频繁收到推送。

## 二、产品理念与推理链

### 2.1 根问题：物品的潜在价值与实际获得的价值存在落差

| 价值落差 | 用户的具体问题 | 可能的 AI 作用 |
|---|---|---|
| 知识和操作障碍 | 功能不会用，配置复杂，遇到故障不知从何查起 | 识别具体物品，调用可信资料，分步指导、诊断和售后衔接 |
| 意识与组合障碍 | 已有东西还有别的用途；不同物品的组合和替代被忽略 | 基于目标、功能与约束匹配已有资源，提出不同方案 |
| 记忆与维护障碍 | 忘了买过、放哪、是否用完、是否该清洗 | 自动整理候选物品、按需确认状态、低负担提醒 |
| 关系与流转障碍 | 送人、共用、借出后，说明书、责任和帮助中断 | 按授权共享知识、物品信息、协作任务与必要服务 |

### 2.2 四种需要实现的价值

**A. 兑现原有价值：** 用好一件物品本就具备的功能。包括上手、配置、个性化使用、维护、排障以及有据可查的服务帮助。

**B. 发现潜在价值：** 基于用户此刻的目标，发现单物品未使用的功能、多物品组合、跨品类替代和“原来家里就有”的解决方式。

**C. 延续和保护价值：** 让物品长期可找、可用、可维护、可转移，减少无效重复购买、遗忘和不必要损耗；包括物流到货、保修、耗材与生命周期处理。

**D. 传递与共享价值：** 让物品及其使用知识能够在人与人之间顺利流转，支持家庭成员尤其是需要帮助的长辈，以及礼物、借用、共同任务。

**因此，“管理、规划、关怀”是重要的功能表达，但不是完整的产品定义。** “单物品智能服务”是不可缺少的价值兑现机制；购物后服务和物品流转是重要连接环节；“了解用户”与“可信交互”则贯穿所有功能域。四种价值彼此交织，不代表固定开发先后顺序。

### 2.3 从产品价值到服务机制

完整逻辑不是「先做智能说明书，再做多物品规划，再做经验网络」。更准确的是：**用户有物品和真实目标 → 系统在授权范围内识别物品身份、获取可信知识 → 将商品功能、限制、兼容关系与当前任务匹配 → 提供指导或组织方案 → 以适当证据确认是否产生有效价值。**

这一机制可服务两条并行路径：一是用户需要使用、配置、维护某件物品；二是用户想完成事情，AI 寻找、组合或替代其已有物品。购物后的持续联系是可供利用的机会，但实际价值可以发生在任何被用户需要的时刻；长期经验迁移并非必要前提。

### 2.4 我们不追求什么

- 不做“每件商品一个聊天机器人”的形式主义；物品卡片、记忆和服务入口不代表后台必须有独立运行的 Agent。
- 不以 AI 导购、促销或提高购买频率作为首要目标；判断“不需要买”也应是正确结果。
- 不要求用户先把所有购买物品录入、分类并持续盘点，才能体验核心服务。
- 不把生活目标选择、旅游目的地推荐、通用日程或社交聊天全部接管；只有与物品价值有关时，才延伸相应服务。
- 不因为已有购买记录就默认“仍然持有、尚未用完、位置已知或用户喜欢”。
- 不把 Experience Network、模型后训练、完整智能家居控制当成当前产品成立的前提。

## 三、产品边界与人群

### 3.1 覆盖范围：几乎所有实体商品

**商品覆盖**：家电、3C、家具、工具、摄影装备、厨房用品、户外用品、服饰、玩具、手工材料、食品、日用品、宠物用品等原则上均可进入。**服务深度**取决于实际任务和该物品可获得的信息，而不是“一刀切”。

| 物品特征 | 典型例子 | 重点价值 | 管理态度 |
|---|---|---|---|
| 长期耐用品 / 功能复杂 | 咖啡机、相机、电脑、净化器 | 配置、隐藏功能、指导、保养、维修、兼容 | 可形成较完整档案与服务记录 |
| 易耗品 / 高频复购 | 咖啡豆、纸巾、清洁剂、食材 | 场景使用、补货、保质期、数量是否足够 | 估计优先、确认可选，不强制逐次扣减 |
| 场景材料 | 拼豆、颜料、露营燃料 | 用途、组合、缺口、剩余材料 | 仅在使用情境中问关键状态 |
| 礼物 / 家庭共用物品 | 买给妈妈的电饭煲、共用投影仪 | 服务转交、代为指导、责任与权限 | 购买者≠拥有者≠使用者≠维护者 |
| 已退货、出售、送人或消耗完毕 | 旧手机、送人的水壶、已吃完的零食 | 历史凭证、退出当前物品集合 | 易归档、保留必要历史、随时纠正 |

**重要数据区分：** 购物记录 ≠ 当前拥有；拥有 ≠ 位于家中；位于家中 ≠ 能正常使用；型号功能 ≠ 当前可用能力。这些差别决定推荐是否可信。

**管理对象也需要区别：** 商品型号（共享商品知识）、购买记录（交易事实）、用户拥有的具体一件或一批物品（物品实例）、消耗品余量估计（不等于实际库存）可能分别存在；它们可以关联，但不应混成一条记录。

### 3.2 典型用户与关系

- **普通消费者：** 买过很多东西，不愿维护精确清单，偶尔遇到不熟悉的功能或生活任务。
- **复杂耐用品用户：** 对 3C、摄影、咖啡或工具有更深的使用、兼容、保养需求。
- **兴趣与活动用户：** 拼豆、烘焙、露营、聚会等由明确目标触发的跨物品场景。
- **家庭照料者 / 长辈：** 为家人购买设备，希望说明书与帮助能跟着物品走，必要时请求家人协助。

这些是候选人群，不代表已完成用户访谈或优先级排序。

## 四、整体产品形态与交互原则

### 4.1 用户看到的产品

一个支持**个人物品空间**与经授权的**家庭物品空间**的 App / 服务入口。用户既能查到某件物品，也能直接告诉 AI 当前想做什么。服务可通过文字、图片、语音、物品卡片、订单入口、扫码或 NFC 等方式触发；入口的最终组合待测试。无需先决定是否必须做独立 App。

**界面内容建议（功能逻辑，不是定稿导航）：**

1. **此刻我想做什么：** 随时输入目标或问题，默认关注完成用户任务。
2. **我的物品：** 按需搜索、分类、查看商品与服务档案；支持个人 / 家庭视图。
3. **需要我关注的事：** 物流、维护、补货、协作请求等有依据且可处理的事项；没有重要事项时保持安静。
4. **家人一起用：** 共用空间、物品权限与协助任务。
5. **服务记录：** 问题处理、说明书、订单凭证、售后资料及必要历史。

### 4.2 必须坚持的交互原则

- **先完成任务，再补齐档案。** 资料不足时只询问关键缺口；支持手动识别或临时使用，不因未建档阻断帮助。
- **能少问就少问。** 将商品信息、订单和已确认历史用于减少重复问题；不因便利而擅自提高推断的确定性。
- **把复杂知识变成具体操作。** 短步骤、图片框选、局部演示、读给我听；必要时让用户确认完成情况。
- **清楚标明事实来源与不确定性。** 官方资料、用户确认、系统估计、模型建议分别呈现。
- **主动服务不等于主动打扰。** 用户提出目标是主路径；打开 App 时可见可选灵感，必要提醒可自主订阅、聚合、关闭。
- **深度管理是可选能力。** 需要精细库存、位置和保养记录的人能够深入；多数用户只承担轻量确认成本。
- **退出与流转同样简单。** 已用完、退货、送人、转卖、遗失、暂时不确定，都不应成为繁重编辑流程。

## 五、完整功能体系（按价值和依赖组织，不按开发排期）

### F1 物品识别与低负担物品空间｜基础能力

- 经用户授权，**候选**支持淘宝 / 天猫历史购物记录的一次性或增量导入；需验证真实接口、权限与数据范围，不视为现有能力。
- 支持非淘宝渠道：手动建档、商品名称 / 型号输入、订单截图或商品照片识别、扫描条码 / 二维码、NFC 绑定或识别（按条件开放）。
- 自动建立**候选物品档案**：名称、品牌、准确型号/版本、可获得的说明书或商品知识、购买日期和凭证、类别、数量、来源可信度；信息不足时仍允许临时使用。
- 将**商品型号资料 / 交易记录 / 用户实际持有物品**分开关联，尽量识别多件同款、批次/型号差异，并允许合并、拆分与纠错。
- 对物品分别管理：**类型**（耐用品/消耗品等）、**关系**（自用/送人/共用/借出等）、**状态**（在用/待确认/用完/已退出等）、**位置和使用者**。这些不是互斥的单一分类。
- 自动去重、批量处理、多件同款物品、搜索、分类、筛选、收藏/置顶、按人或房间查找；可以逐渐补充而不是先录全。
- 对数据提供修正、合并、删除、归档和导出入口；商品状态可以设置有效期或等待再次确认。
- 消耗品数量和库存属于**按需增强项**，允许“可能还剩”“已用完”“不确定”，不默认要求用户精确记账。

### F2 单物品智能服务｜直接创造价值的核心

- 商品是什么：功能、参数、型号差异、使用限制、常见问题、适用配件；说明书和资料的**来源与适用版本**可查看。
- 首次使用：到货后的开箱检查、装配、初始配置、联网、安装与常见设置。
- 深入使用：用户按需询问高级功能、场景化设置、个性化用法与已有配件配合方式；不强迫完整学习。
- 多模态指导：自然语言问答、语音输入、朗读、图片或屏幕截图辅助理解、一步一步的操作指引；按场景探索箭头标注、短动图、实时摄像头指引。摄像头是可选的现场观察入口，不应强制用户全程举着手机。
- **现实物品与说明书对齐：** 通过图像识别、OCR 或物品照片等候选能力，对照具体型号的铭牌、接口标签、按键、提示灯、错误码、零件图与说明书，指出「当前这一步在哪里操作」；模型识别不可靠时退回截图、文字或人工确认。
- **流程进度：** 指导卡片支持上一步 / 下一步 / 暂停继续；对状态变化或关键操作询问是否完成，条件允许时再接入设备或系统数字状态进行核验。
- 故障诊断：根据型号和用户描述提出必要澄清，按可信资料、可观察事实和风险高低建议检查步骤；支持“还是没解决”“已解决”。
- **核验与回退：** 明确区分「操作已执行」「用户认为问题解决」「客观状态已恢复」；有网络连通性、打印队列、系统设置等可靠 Digital Trace 时可客观检查，否则通过用户确认，不能由模型单方面宣称已修复。
- **安全与主动诊断：** 尽量先做低风险、高信息增量的检查，避免把所有可能的维修步骤一次抛给用户；涉及漏电、冒烟、燃气等风险时停止不安全指导，转向专业售后。
- 维护与售后：清洗、滤芯或耗材适配、保养规则、保修凭证、维修与退换货信息；记录问题、已尝试步骤和处理状态；生成可复制、下载的售后材料并保留用户确认。
- **适老化和辅助交互：** 大字模式、分步呈现、语音朗读、简化术语、请求家人协助。

### F3 目标驱动的场景 Agent｜直接创造价值的核心

- 用户**先提出真实目标**：做拼豆、周末烧烤、家庭聚餐、布置房间、搭建直播、准备出行装备等；AI 不以物品存量主动替用户决定目标。
- 理解目标的关键约束：人数、时间、场地、预算、用户已有安排与偏好；缺少的信息按需询问。
- 从已拥有物品中发现**可用资源**：不仅按商品类别匹配，也按功能、尺寸、接口、兼容、替代用途及使用限制匹配；说明书与商品详情需提取能够用于任务判断的能力信息，而不只是全文检索。
- **多物品组合**：哪些能一起工作，哪些有依赖或冲突，哪些已有物品可能提供意外但合理的替代方案；对「相机＋麦克风＋电脑」等链路检查接口、规格与限制，而非只用类别名称作匹配。
- **能力缺口先验证后推荐：** 区分缺一件商品、缺一个配件、缺一种使用方法与缺一次简单配置；最优建议可能是「不需要买」。
- **方案与选择**：给出多个合适方案（例如最低新增购买、最便捷、质量优先），说明依赖条件与不确定性；用户自行决策。
- **准备和执行支持**：生成物品清单、步骤、准备顺序、注意事项，按需保存为任务或共享给家庭成员。
- **缺口分析**：分清“已确定拥有”“可能拥有、需确认”“确实缺少”；先利用现有替代方案，必要时再给补充建议。
- 对无法确认的余量、位置或可用性，不编造结果；建议应标明依赖哪些确认信息。
- 可在节假日、季节或特殊日子生成**打开 App 后可见**的相关灵感，默认不频繁推送，不把通用旅游规划作为本产品核心。

### F4 交易到使用的连续服务｜重要连接功能

- 物流查询（在合法授权及接口存在的前提下）、签收和到货核对；只展示与本产品有关的服务增量，避免复制纯物流工具。
- 从订单或到货自动建立候选物品档案；到货后提供对应说明、初始配置、使用注意事项。
- 保留订单凭证、购买日期、可核实的保修条款与售后入口；涉及退货、换货、赠送时更新物品关系；可探索为商家提供维修相关问题和历史步骤的结构化交接。
- 故障无法自行处理时，汇总准确商品信息、问题现象、照片（经授权）、已尝试的步骤、对话摘要，由用户决定是否提交商家或维修方。
- 售后进度与解决状态在可接入真实服务时再开展自动化；未接入时至少可保留与导出记录。

### F5 维护、消耗与轻量提醒｜延续价值

- 耐用品：按官方建议与用户确认的使用情况，提示检查、清洁、保养或更换耗材；支持“已处理 / 稍后 / 不再提醒”。
- 消耗品：根据订单与自愿提供的使用信息，提出补货时间的**估计**；可合并同类提醒，不需要每日手动扣减数量。
- 关注保质期、保修期、定期维护或需要检查的事项；无法实际感知设备状态时，不宣称已经检测。
- 允许按**物品或提醒类型**设置接收方式：不开通知、仅在打开 App 时呈现、必要时通知；对老人与家庭场景可设置适当协作提醒。
- 日常提醒应与物品真实价值相连；一般宠物喂食或通用日程只有在明确构成物品/家庭照料流程时才考虑延伸。

### F6 家庭空间、照料与协作｜价值在关系中传递

- 个人物品空间默认归个人；经选择后将指定物品或信息共享到家庭空间。
- 家人邀请与角色：物品拥有者、使用者、维护协助者、家庭管理员等。**管理员不天然获得所有成员的私人购买记录**。
- 按物品和权限控制查看、编辑、协助、导出等操作；支持撤销共享、转交管理与家庭成员退出。
- 为长辈提供大字模式、朗读和分步操作；“请家人帮忙”可以带上物品型号、具体问题、已尝试步骤，记录协助请求及完成情况。
- 家庭目标可共享清单、分工或协作处理，但不预设家庭中所有人的偏好与隐私都能互见。

### F7 赠送、借用与物品流转｜重要关系功能

- 标注购买用于自用、赠送、共同使用或代购；允许轻量确认接收者及物品去向。
- 礼物可随用户许可附带电子说明书、使用帮助入口、购买与保修信息的适当子集，而非转移全部私人订单信息。
- 借用或临时共享物品时，可保留归还、所在位置及双方约定；无需构建完整社交网络才能先实现服务。
- 转卖、丢弃、消耗完毕或退货后，可退出当前持有清单但保留用户选择保留的必要历史。
- **好友网络、跨家庭共享平台与网络效应属于远期研究假设**，不是当前必须上线的即时通讯或社交产品。

### F8 个性化理解与 Context｜贯穿式能力

- 理解用户**明确表达**的兴趣、技能水平、偏好、时间与预算约束，以及当前目标。
- 将物品信息与人的关系分开：购买者、拥有者、使用者、维护者可以不同；购买摄影设备不代表用户一定爱好摄影。
- 根据任务请求必要的地理、天气、人数、环境等信息；未经授权不默认持续读取位置或个人信息。
- 用户能够查看、更正或删除被系统长期保留的判断；将**已确认 / 推断 / 未知**明确区分，考虑时间失效，并让系统尽量能解释「本次建议为什么使用这条偏好/哪件物品」。
- 同一用户不同场景可有不同偏好；不把全部历史信息无差别塞入每一次对话。

### F9 通用交互、知识可信度和安全｜所有服务的质量底座

- 按目标和复杂度选择文字、语音、图片、步骤卡片、来源链接、家人协助或专业售后交接。
- 重要产品事实以准确型号/版本的官方说明书、型号资料、授权商家信息等为依据；可设来源层次：**官方资料 / 经厂商核验的支持知识 / 已证实的社区经验 / 待核实经验与模型推断**，呈现出处和适用范围；更高来源等级不等于自动适用于所有版本。
- 核实具体版本与适用条件，资料冲突、型号不明或危险操作应停止猜测；尽量提示下一项低成本的确认动作。
- 涉及共享、发送售后材料、购买、远程设置、读取照片或家庭数据等操作时，需要相应授权和明确确认；提供退出、撤回或删除入口。
- 响应式手机与桌面体验、数据导出 / 备份、对话和服务记录管理、必要的操作历史。敏感家庭图像和原始环境数据应优先考虑最小采集、短期处理与按需授权；端侧处理是可验证的技术选项，并非已确认必须全量本地部署。

### F10 候选的平台能力与更远期方向｜目前不列为必需功能

- 已授权设备的真实状态读取与必要控制（取决于厂商 API、操作系统和设备协议）。
- 多用户间经过授权、去标识化、跨案例验证的使用经验迁移、Experience Network、后续 Skill 更新；单次成功先形成待验证案例，不能直接传播或宣称完成模型后训练。
- 面向商家/品牌的「可供 AI 理解的商品资料包」管理与核验工具（Product Pack Builder 候选）：维护型号、手册、图示、能力、兼容、配件及售后流程；这属于生态设想，不是 C 端使用的先决条件。
- 独立或协作的多 Agent、复杂后台任务编排、跨品牌服务自动履约。
- 更广泛的好友关系、物品互借平台、社交网络和商业生态。
- 更深的商品/服务补充推荐（Capability-aware Recommendation 候选）与可选自动履约；必须服从用户目标、正确性、授权与避免利益冲突的原则，「不用买」始终可成为正确结论。

## 六、五段典型用户旅程（用于检验功能是否成体系）

### 场景 A｜一台刚到货的咖啡机

**用户目标：** 第一次顺利使用，并在需要时学会清洗。  
**体验：** 授权订单导入或手动识别 → 确认具体型号 → 获取有来源的首次使用步骤 → 用户有需要时提问清洁、耗材适配 → 依据资料和选择设置可选维护提醒 → 遇到异常时保存排障和售后记录。  
**有效价值：** 缩短学习与解决问题时间，减少错误操作，并把长期使用知识集中在同一物品入口。  
**未知边界：** 不一定能获知真实使用次数或机器状态。

### 场景 B｜周末已决定去烧烤

**用户目标：** 在选定地点和人员后，尽可能利用家里已有的东西完成准备。  
**体验：** 用户发起目标 → AI 询问人数、场地限制和必要条件 → 识别烧烤架、收纳箱、餐具、保温用品及可替代工具 → 给出已有、待确认与缺少清单 → 用户确认燃料等消耗品状态 → 形成准备方案及必要补充建议。  
**有效价值：** 更少遗漏和重复购买，更少准备时间；不替用户决定是否去烧烤或去哪儿。

### 场景 C｜给妈妈买的电饭煲

**用户目标：** 妈妈能够独立使用，遇到问题可获得帮助。  
**体验：** 购买者将指定电饭煲共享给妈妈 → 妈妈使用大字/朗读/分步教学 → 不清楚时点“请家人帮忙” → 家人看到有授权的型号和问题摘要 → 必要时联系售后。  
**有效价值：** 减少重复解释、降低学习门槛并改善照料体验。  
**隐私边界：** 妈妈不因此获得购买者全部订单，管理员也不自动查看其他人的私人物品。

### 场景 D｜拼豆材料与家中现有工具

**用户目标：** 现在就开始拼豆。  
**体验：** 用户输入项目 → AI 找到历史购买的拼豆及可能适用的收纳盒、镊子等 → 提醒确认材料是否仍有余量 → 给出低成本的准备与替代选择。  
**有效价值：** 利用原本未被联想到的已有物品，降低准备门槛。  
**未知边界：** 订单不能证明材料未被用完。

### 场景 E｜高频复购的纸巾或咖啡豆

**用户目标：** 不想经常记库存，也不想突然用完。  
**体验：** 系统识别重复购买 → 在用户愿意的情况下估计补货节奏 → 在一个合适的触点合并提示“可能需要确认是否补货” → 用户一键选“还有 / 用完 / 不提醒”。  
**有效价值：** 少操心、少遗漏、少无效提醒；不把估算余量假装成实际库存。

## 七、产品真正要解决的管理成本问题

### 7.1 将“自动记录”与“真实状态”分开

**自动可获得（取决于授权和接入）：** 购物商品名、订单时间、候选型号与数量、商家信息。  
**需要来源核实：** 说明书版本、参数、保修条款、官方配件。  
**经常需要用户确认：** 自用或送人、谁在使用、是否仍持有、物品实际位置、耗材余量。  
**只有有可靠观察来源才能确定：** 部分设备的运行状态、实际故障结果和剩余寿命。

### 7.2 管理方式设计为“按需逐渐深化”

- **默认零负担：** 商品可成为候选物品，不要求用户逐项分类。
- **轻量确认：** “这是自用还是送人？”“还在用吗？”采用一次操作可完成的回答；不对每件订单机械询问。
- **任务时校准：** 做烧烤计划时才问燃料还有没有；帮助妈妈使用时才核实使用者。
- **自愿深度管理：** 用户可以主动补充余量、房间、保养计划、家庭责任人，获取更准确的服务。
- **减少维护债务：** 自动识别可疑过期信息，允许批量归档、暂停跟踪、删除及纠错；不能用提醒逼用户盘点。

## 八、有效价值：产品效果评价的基本原则

### 8.1 我们如何定义“有效价值”

**有效价值**是：用户在符合自身真实目标、安全与权限约束的前提下，因为产品的帮助，更好地获得、使用、保存或传递已有物品的价值。它可以表现为任务完成、时间与金钱节约、使用质量提升、减少错误和焦虑、改善家庭协作，或一次有意义的“原来还可以这样用”。

**不等于：** 使用次数更多、消息推送更多、购买更多、库存登记更精确、对话更长、App 日活更高。某些物品的价值恰恰在于需要时能找到并安全使用，而不是每天使用。

### 8.2 可以考虑的衡量维度（待用户测试确定口径）

| 价值方向 | 用户可感知结果 | 候选指标 | 应避免的误判 |
|---|---|---|---|
| 单物品服务 | 自己完成配置或解决问题 | 任务成功率、耗时、重试次数、是否转人工、用户理解程度 | 用户点“解决”不等于原因已确定或永久修复 |
| 场景与组合 | 用已有物品完成想做的事 | 方案采纳率、实际完成率、确认可复用物品数、确认避免的重复购买 | AI 列出更多物品不等于价值更高 |
| 低负担管理 | 更少整理也能找到和使用物品 | 每次有用任务的额外确认步数、维护用时、物品信息过期率 | 录入数量多不等于库存真实准确 |
| 维护与延续 | 及时且有依据地处理事项 | 有效提醒处理率、误提醒 / 打扰率、保养事项完成率 | 不可把提醒发出视为实际维护完成 |
| 家庭协作 | 家人更容易获得帮助 | 协助请求完成率、重复沟通减少、满意度与权限投诉 | 共享越多不等于关怀越好 |
| 信任与安全 | 建议可信且可纠正 | 错误型号匹配率、无依据答案率、危险建议率、错误状态标记率 | “很会说”不等于事实正确 |

### 8.3 如何验证「真的更有用」

从任务端而非模型端评价：**用户要做什么 → 若不用本产品如何完成 → 使用后是否更快、更好、更省成本或减少了不必要行动 → 使用过程新增了多少管理成本、误判和打扰。**

建议区分三种结果证据：**客观观测**（例如网络连通性恢复）、**用户确认**（例如用户表示理解并成功操作）、**推断或暂时结果**（尚不能证明长期解决）。同时记录安全/隐私代价；「建议被采纳」「物品被列进清单」不等于已经实现有效价值。

### 8.4 验证方式

优先对比**用户不用产品时真实怎样完成任务**，而不只看演示是否流畅。分别设计单物品指导、跨物品场景、轻量库存和家庭协作的实际测试；记录解决结果、用户投入、信息错误和负面体验。对无法自动确认的结果使用用户反馈或人工核验，明确证据强弱与样本范围。

## 九、竞品关系、差异化与商业设想

### 9.1 差异不在“也有 AI 聊天”

- 对比通用 AI：希望减少具体型号、拥有关系和历史信息的重复解释，并将建议与真实物品集合相结合。
- 对比说明书与品牌客服：希望跨品牌、跨物品、跨家庭成员连续提供可核查的指导，必要时仍交接到官方渠道。
- 对比家庭库存 App：不只回答“有什么”，还帮助用户完成目标、理解功能与使用。
- 对比智能家居：不仅覆盖联网设备，还覆盖普通实体商品、消耗品、礼物和未联网物品，但不宣称无接口设备能够被实时感知。
- 对比物流或电商 App：不只追踪交易，而要把签收后的知识、使用、维护和人与人之间的服务延续起来。

这些是**拟验证的差异化方向**，而不是已证明优于现有产品的结论。

### 9.2 平台商业价值（作为独立假设，不反向规定产品功能）

未来可研究：天猫/淘宝购物记录降低识别成本，商品知识、商家和售后关系支持更长的购后服务链条；用户真实场景中的能力缺口可能连接到更精准的补充购买。但这一设想依赖开放接口、数据授权、商家配合与真实用户价值。获客、平台生态、收购及网络效应均不是当前产品定义的依据。

## 十、功能成熟度与实现边界

### 10.1 本轮已形成的产品方向共识

- 以**有效物品价值**为核心，覆盖几乎所有实体商品；对不同品类提供不同深度的管理和服务。
- 两条核心用户路径：物品问题求助；用户主动提出生活目标，由 AI 调动已有物品。
- 用户尽可能少维护物品信息；允许按需深度管理和轻量确认。
- 多物品场景、家庭照料、购物后延续服务都应纳入完整功能设想。
- 不把一件商品一个 Agent、体验网络、后训练、好友社交网络视为当前成立的先决条件。

### 10.2 候选实现路径（不构成固定技术架构）

- **物品识别：** 授权订单导入 + 手动补录 + 拍照或条码辅助；优先建立候选身份并标记信息可信度。
- **商品知识 / Product Pack 候选：** 按型号与版本建立可维护、可检索的商品知识能力包，覆盖 Identity（型号/版本）、Manual / FAQ / Diagram（可信知识）、Capability（功能参数）、Constraint / Compatibility（限制与兼容）、Guide（操作流程）、Evidence / Verification（来源与如何验证）。不要求一件商品训练一个模型，普通日用品可只保留必要字段。
- **AI 引擎：** 目前倾向使用千问作为候选大模型底座；是否使用统一 Agent、多 Agent、模型路由、知识检索或其他工具由实际场景决定。另有材料描述团队 9B 多模态模型及压缩能力，属于**待团队核实的技术储备**，不是本产品已决定采用的方案。
- **状态与 Context：** 用户明确提供、系统推断、可靠设备观察应分层；权限、过期与纠正机制不可忽略。
- **家庭协作：** 从具体物品授权、协助记录入手，账户体系、邀请、同步及细粒度权限后续验证。
- **现实观察与核验：** 从静态知识/用户图片到操作系统数字痕迹、外部传感和设备原生 API，按可获得性选择；在设备、版本、权限及输入不足时明示 Unknown。对实际已完成的任务与因果判断分别记录证据。
- **端云与隐私：** 本地识别、端侧压缩模型、云端大模型、混合架构都可以比较；依据设备算力、延迟、准确率、成本、隐私与授权作取舍，不预设所有图像都上传，也不预设所有模型调用必定本地。
- **可验证的评测：** 可建立小型代表性测试集覆盖型号/OCR、说明书图示理解、部件定位、步骤追踪、有据回答、拒绝猜测、任务结果和失败退出；比较基线方案，不将 benchmark 分数等同用户有效价值。
- **真实闭环：** 从用户目标到可验证的结果；未接入物流、品牌售后、IoT 等外部系统时，产品演示须明确说明模拟范围。

## 十一、端到端功能核对：不能只交付一个「会说的 AI」

下表是对产品功能的**查漏清单**，不是开发优先级、已实现状态或指定技术选型。

| 用户可感知环节 | 应考虑的具体功能 | 成功前提 / 风险 |
|---|---|---|
| 轻松找到物品 | 自动/批量导入候选商品、搜索筛选、手动补录、拍照/扫码/NFC 召回、同款多件与纠错 | 订单与实际拥有的区别，型号和版本准确性 |
| 理解具体物品 | 说明书、订单与保修凭证、可信问答、零件图/接口图、功能和适配关系 | 来源可信、版本匹配、不能凭空补参数 |
| 把知识变成操作 | 文字/语音/朗读、大字模式、步骤卡、局部高亮、图片或摄像头现场指引 | 镜头角度与小字识别、操作安全、必要时退回人工确认 |
| 处理出错和失败 | 「没解决」、继续诊断、暂停恢复、已尝试步骤汇总、售后资料生成/复制/导出/转交 | 用户自报结果和客观验证分开、材料外发前确认 |
| 围绕目标组织物品 | 约束识别、跨物品能力匹配、组合与替代、准备清单、缺口/购买判断、共同清单 | 当前拥有与数量不确定、兼容或安全限制 |
| 延续生命周期 | 到货准备与验收、保养、耗材估计、保修、退换/出售/赠送、轻量提醒与归档 | 用户维护成本、误提醒和误导性状态 |
| 家庭与赠送 | 成员邀请、按物品授权、长辈指导、请家人帮忙、协助记录、共享与流转 | 私人订单和家庭管理员权限不能混同 |
| 用户信任与掌控 | 说明依据、已确认/推断/未知、个人推断可纠正、隐私授权与撤销、数据备份/导出 | 不因追求更高活跃而强制收集或打扰 |

上述功能构成完整设想，**并不要求同一版 Demo 全部实现**；具体开发范围、分工、排期和验收将在后续讨论确定。

## 十二、仍需后续讨论、验证及分工的议题

本文件用于让团队清楚**想做什么与为什么做**。以下问题重要，但不应在这份说明中伪装成已经定案。

1. **物品识别与授权：** 淘宝/天猫能提供哪些真实订单字段？旧订单、跨平台、线下商品如何低成本纳入？如何映射准确型号及版本？
2. **状态维护与成本：** 不同品类何时确认状态？怎样避免误识别、重复记录、长期过期；精细管理的自愿门槛多高？
3. **商品知识和可用能力：** 说明书、商家信息、参数、社区经验如何获得、核验、更新并转化为组合规则？
4. **用户 Context 与隐私：** 购物行为能推断什么、不能推断什么？个人 / 家庭权限、授权撤销、数据删除与位置隐私如何处理？
5. **Agent 与交互：** 如何根据目标选相关物品、询问关键约束、判断不确定性？千问与其他模型及工具怎样搭配？
6. **场景质量：** 哪些类型的组合真正让人惊喜并能实现？如何验证不是“看起来不错但执行不了”的空想？
7. **提醒与日常入口：** 物流、家庭照料、维护、补货何者足够高价值？如何控制打扰与运营成本？
8. **服务闭环：** 什么能够真实自动执行，什么只能指导；售后、跨品牌协作、家庭账户等外部接口如何获得？
9. **评测与商业边界：** 有效价值的基线、量化口径与用户样本如何设计？如何避免为成交而产生偏向性的建议？
10. **可分工的模块：** 后续可以按物品数据、知识可靠性、场景 Agent、家庭与协作、交易/维护、体验设计、隐私与评测划分实施责任；具体分工、优先级与排期尚未决定。
