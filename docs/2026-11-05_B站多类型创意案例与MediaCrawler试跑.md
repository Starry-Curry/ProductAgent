# B站多类型创意案例与 MediaCrawler 试跑

日期：2026 年 11 月 5 日。任务范围为公开内容研究与小范围采集可行性验证。本轮未修改应用代码、业务数据库、应用依赖或模型配置，也未调用付费模型。

## 1 创意的范围

用户提供的废物利用案例用于说明生活中的创造力，不构成限定类别。物间需要覆盖：单物的新用途、多物组合、兴趣与游戏、空间安排、审美与情感体验、可支持设备的功能组合与调整，以及旧物再用。它们可以重叠，不应变成七个割裂的产品模块。

这轮搜索没有只使用“废物利用”“旧物改造”关键词；还检索了台灯手机摄影、长尾夹用途、投影窗景、洞洞板组合、玻璃杯演奏、户外技巧和智能家居联动。

以下案例来自搜索可见的 B站标题、创作者简介/内容简介和章节目录。本轮没有完整观看视频，也没有独立实物复现。部分视频详情网页直接读取返回 412。因此下表是候选案例目录，不能标为已验证操作教程；最后一列是物间应进一步核对的判断。

## 3 MediaCrawler 实际试跑

### 工具和测试范围

来源：[NanmiCoder/MediaCrawler](https://github.com/NanmiCoder/MediaCrawler)。本轮读取了 README、LICENSE、依赖清单、基础配置以及 B站 crawler/client 的源码。用户明确说明当前为非商业研究并授权尝试，因此进行了本地隔离测试，没有把许可问题当作拒绝试跑的理由。

项目现行许可证为 NON-COMMERCIAL LEARNING LICENSE 1.1。此处仅做少量学习验证，不据此增加后台批量采集任务。许可文本、访问是否成功、材料是否足以支持结论，是不同问题。

源码归档放在忽略目录 `tmp/research/MediaCrawler-main/`，独立 Python 3.12 环境放在 `tmp/research/mediacrawler-venv/`。Git clone 遇到本机 schannel 凭据错误后，改用公开源码归档；下载和解压成功，解压前检查了路径不能越出目标目录。

依赖仅安装到研究环境，没有安装到物间 `.venv`。实际安装的主要版本：httpx 0.28.1、Playwright 1.64.1、Pydantic 2.14.3；客户端导入链还需要 Pillow、OpenCV、Redis 等。导入依赖不等于使用了这些功能；没有启用代理、滑块处理或媒体下载。

### 为什么没有直接运行默认主流程

源码 `media_platform/bilibili/core.py` 表明：

- 完整 `start()` 流程会先检查登录，未登录时进入登录过程。
- 默认配置开启评论采集和已有浏览器 CDP 连接等能力，不符合本次只读少量公开内容的需要。
- 普通关键词搜索会将低于20的最大结果数提高为20，不能把配置写成3就声称只取3条。

因此使用独立脚本调用原始 `BilibiliClient`，请求一个已知视频的公开详情，以及一个关键词搜索。没有运行完整 CLI、登录、存储流程或浏览器流程。脚本通过 Python namespace 加载客户端，避开包初始化导入整个 crawler；没有伪造响应或替换客户端的请求逻辑。脚本子进程清除继承的代理设置，不读取 `.env`、现有浏览器资料或登录态。

### 真实结果

| 检查 | 结果 |
| --- | --- |
| 公开源码下载、隔离依赖安装 | 成功 |
| 原始 BilibiliClient 导入 | 成功 |
| `get_video_info(bvid="BV1Py4y1b7Vc")` | `ConnectError`，未取得详情 |
| `search_video_by_keyword("台灯 手机 摄影", page=1, page_size=3)` | `ConnectError`，未取得搜索结果；不能说实际返回了3条 |
| 补充普通 HTTP 诊断：公开详情接口 `/x/web-interface/view` | HTTP 412，返回HTML页面，未取得视频数据 |
| 补充普通 HTTP 诊断：B站 robots.txt | TLS EOF 连接异常，未取得内容 |
| 网页研究工具直接打开三个候选详情页 | 返回412；搜索可见的已索引标题、简介仍可作为发现线索 |

客户端两个请求都在取得正常数据前失败。补充诊断也显示当前访问有障碍，但没有足够证据把它唯一归因于登录、IP、地区或客户端代码。未尝试绕过验证、轮换代理或反复重试。

结论：**本环境尚未跑通 MediaCrawler 的 B站采集；不能宣称已接入，也不能凭此认定工具不支持B站。** 下一次验证应先确认普通浏览器能正常访问目标；如需登录，使用用户主动完成登录的独立研究会话，再验证一个具体视频的元数据，最后验证一页关键词搜索。登录成功也不等于能取得完整字幕、视频理解或可靠教程。

## 4 这些材料怎样服务物间

最有价值的沉淀是“一个东西为什么能在这个情境起这个作用”，以及成功或失败的条件。案例标题或向量相似度只能帮助发现，不能代替这层理解。

候选最小流程：

1. 从用户目标和已有物品发现案例，也允许用户无目标时找好玩的方向；搜索用原用途、部件、材料、动作与场景组合，避免只搜“某物妙用”或只搜“废物利用”。
2. 区分只看到了标题、看到了作者解释、看到了实际演示、用户亲自试过等依据。能取得章节或时间点时保留定位；内容不足时继续读取，不能由模型补齐教程。
3. 提炼参与物品、各自承担的作用、必要配件、步骤、适用条件与未知项。对象可以是标准商品，也可以是非标物，不强迫每条创意都有型号。
4. 对照用户手上实物的照片、规格、状态和意愿做适配。已坏的灯、珍惜而不愿打孔的礼物、缺少网关的设备，与原案例不能等同处理。
5. 给少量有差异的方案，说明哪些已有、哪些缺少、为什么适合。新迁移部分标为候选，不包装成来源已经验证过的效果。
6. 实践结果回到共同的物品认识、任务与经历；用户愿意留下的照片和文字再成为回忆。适合共享时可传给家人或朋友，继续复用同一份事实。

例如“家里有台灯和手机，想给朋友做的杯子拍张好看的照片”可以贯通：确认杯子的真实特点和灯的现状 → 找到贴近资源的拍法 → 完成一次拍摄任务 → 把用户主动记录的照片关联杯子与这次经历 → 将用户选中的故事与礼物一起送出。不是为四个价值各复制一套数据库。

## 5 架构判断与后续验证

本轮没有证据要求更换 SQLite、引入图数据库或增加多Agent层。当前更缺的是来源可读、内容足够、物品特征与使用条件表达正确，以及真实效果反馈。

MediaCrawler 如果后续验证可用，适合作为可替换的来源适配器或独立研究采集任务，向现有来源与案例机制提供材料。它不应直接写成物品事实，不应拥有用户私有记忆，也不应成为所有创意请求的必经链路。只有标题的结果可用于推荐原视频，不能作为完整操作依据。

下一轮小批验证应混合单物新用、多物摄影、空间安排、娱乐和设备联动，不全是再利用。采用“这堆东西还有啥好玩的”“租的房子不能打孔，桌面又放不下了”“不想再买灯，现有这些能拍好看点吗”等自然说法，明确模拟的拥有关系与已知事实。

先比较无案例、仅标题、足够细节的案例三种输入对同类任务的影响，再决定最小存储和检索调整。评估重点包括有趣程度、实际可行性、资源与个人意愿适配、是否编造属性，以及能否解释未知。不能只看能否搜到链接或返回合法JSON，也不能用本轮见过的案例冒充独立盲测。
