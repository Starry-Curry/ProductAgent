# 已保存真实旅程：运行耗时剖析

2026-11-06。仅分析已有results.json与SQLite `mode=ro`，没有启动应用、迁移、调用API或修改生产实现。机器可读逐轮数据在本地`tmp/acceptance/real-runtime-profile.json`，提取脚本在`tmp/research/profile_saved_runs.py`，原始运行记录不公开提交。14轮结果里的events全部与对应SQL Run.events一致，所需model_timing时长／输入输出tokens字段没有缺失。

**现有证据主要指向主Agent模型阶段、搜索，以及错误后的额外模型轮次；没有证据支持“数据库是当前主要瓶颈”。** 本地读取与有界视频取帧确有耗时，但在这些保存样本中远小于后续模型阶段。这不代表所有抓取或真实大库都快。

## 口径

- `total_elapsed`使用harness逐轮elapsed，包含排队/轮询等应用等待。多轮相加是各轮时长合计；不同旅程部分并发运行，**不是整个实验连续墙钟时长**。
- `model_call_count`是已完成的`model_timing`事件数，记录主Agent模型调用阶段，包括其网络/SDK等待；不等于纯思考、GPU计算或供应商内部推理时间。失败且无结束事件的调用不能补成0秒。
- 输入token是各模型调用输入累计，包含重复上下文；没有去重、缓存命中或图像/思考token拆分，不能当唯一上下文长度。
- `tool_end`按同ID的tool_start取工具名。工具耗时可以重叠，合计只表达记录的工作量，**不是critical path**。事件没有绝对起止时间，精确关键路径记unknown/null；JSON保留波次内成员最大值，但也不把它当波次实测墙钟。
- 外部HTTP为harness计到的百炼/兼容地址传输attempts，包含搜索、嵌入和SDK重试。公开网页GET、DoH和FFmpeg不是该付费服务请求计数。模型次数与外部HTTP次数分别列出。

## 等待主要在哪里

1. **长回合的主因是多次模型阶段，且重复输入明显。** 安静玩法两轮9次模型输入累计293,566 tokens，单次输入从7,651增长到49,442。网页资料与历史计划会反复进入后续步骤；这表明上下文和轮次值得下一批细查，但没有前后控制实验，不能声称压缩一定能省多少时间。
2. **搜索等待确实重要，但不能混同抓网页。** 安静玩法有7次search_public_web，REA3.6有2次；前者最终仍没取得完整玩法案例。等待不仅是“取得更多资料”，还包括选源和搜索方向是否产出有用证据。已保存事件不能拆出搜索服务推理、公开HTTP及解析各占多少。
3. **本地抓取／视频处理在这些样本不是主要等待。** binder原生第一轮57.41秒，其中模型阶段51.251秒，取网页1.156秒、取帧4.672秒；第二轮模型54.000/54.27秒。compact一轮58.92秒，模型53.438秒、取帧4.016秒。不能据此外推长视频、被墙网站或所有型号都一样快。
4. **数据库瓶颈没有得到证实。** 保存Experience工具0.047秒、read_item至多0.188秒、list_sources0.032秒，结构验证调用至多0.109秒；本次没有SQL statement/事务等待span、锁冲突、磁盘/CPU采样。只能说这些工具端到端短，不能用`elapsed－model`剩余部分命名为“数据库时间”，也不能推出大规模数据库性能已通过。

whale第二轮44.72秒，模型阶段44.375秒；写回忆及权限检查都在几十毫秒级。其等待更像需要作出几次模型决策/修复，而不是墙记录写入慢。第三轮36.23秒同样有34.703秒模型阶段。问题机制和业务判定见既有fresh-life-first-review；耗时分析不把找回聊天原句改判为已读同Experience。

## 哪些不是有效A/B结论

- binder原生与compact的第一轮用户文本相同，但仅各一次、启动条件/实现版本/请求负载未随机控制。原生首轮57.41秒、compact58.92秒，均4次模型；本记录**没有显示compact带来响应时延收益**，也不能据1.51秒差断言稳定退步。不要将原生两轮111.68秒与compact一轮58.92秒比较成减半。
- REA两模型首轮用户文本相同，但3.8首轮有8次模型、不同检索/抓取路径及错误修复，3.6是4次；3.8另有第二轮，3.6没有对应轮。只能说明这些实际旅程发生了什么，不能据207.98对109.25秒宣称3.8模型固有速度慢一倍。
- no-thinking分身3轮均一次模型、合计24.36秒；whale包含真实写入、引用拒绝和跨重启检索。不同题目/路径不能归因于思考开关，更不能用性能数据替代陪伴或创意质量验收。

## 预算与unknown

只读账本当前counter=596/600，其中**200是早期两个基线探针的保守预留，不是200次实测请求**。实际attempts表有395条兼容服务传输记录，另有一行保守预留标记；api-budget.json单独保存1次初始凭据探针。核对为395条实测传输＋1次单独初始探针＋200预留＝596。剩余计数4不在本任务使用。

395条账本传输包括：chat/completions成功296、CancelledError4、ReadTimeout4、RemoteProtocolError1；embeddings成功19；responses成功71。它们是整个本轮账本，不是本报告14轮的57次HTTP，更不是44次主模型阶段。全账本各请求elapsed也会并行，不能合计作实验墙钟。

未知／未测：精确并行critical path；每条SQL/事务等待；provider的TTFT、prefill、thinking、decode与缓存命中；search工具内部的服务/下载/解析拆分；样本外的高并发、大库与长媒体表现。JSON对精确关键路径使用null，并保留这些unknown。当前证据更支持先定位模型轮次、有效选源、重复上下文与修复链，而不支持现在据此更换数据库或宣布任何新优化已经有效。

## 下一次实测的条件留存

剖析发现旧报告未单独保存有效的thinking开关，因此本轮在既有显式付费harness补充`conditions`，留存实际模型、thinking开关与budget、stream、embedding模型、Python/关键SDK版本及显式允许的源码/Skill/锁文件SHA256。本地未提交修改也会反映到内容哈希，避免仅写Git SHA而遗漏条件。只记录这些配置，不序列化Settings，不读取.env、私人库、媒体或运行日志。

两项离线回归分别核对有效开关/未提交Skill变化可区分、密钥与私人文件不会进入清单；实际HTTP计数原有两项回归同时通过。没有启动新付费回合，也没有改写旧冻结报告、由哈希反推旧条件或宣称性能提升。后续受控对照应从有完整条件的新报告开始。
