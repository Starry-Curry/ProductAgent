# 来源读取与生活创意证据改进

日期：2026-11-06。本文记录本轮实现、真实资料回放、候选工具实验和未解决问题；不表示智能底座、生活创意或实机 REA 已通过验收。

## 1. 目标与工作边界

物间需要自己发现、下载、读取公开资料，并把取得的认识用于使用指导、创造、记忆及传递。Codex 的研究用于改进工具和核验结果，不把预先整理的案例答案灌入 Agent，也不把某个测试型号写成固定答案库。

本轮遵循两项具体方法：

- **第一性原理**：先区分失败发生在网络连接、正文提取、证据适用性还是模型推理，再改对应机制。页面返回成功不等于获得正文，获得正文也不等于理解正确。
- **对抗性审查**：主动检查内网重定向、登录空壳、推荐内容混入当前物品、代码被排版破坏、引用正确但结论过度等反例。独立审查发现的问题先复现，再修复和回归。

生产侧继续复用 HTTPX/httpcore、BeautifulSoup、Pypdf 与 Python 标准 JSON 解析能力，没有另建爬虫平台、案例数据库或来源审判 Agent。

## 2. 已实现的来源读取机制

### 2.1 在本机网络环境下安全读取公网资料

实际环境的系统 DNS 会把公网域名解析到 `198.18.0.0/15` 基准测试网段。原有公网地址检查因此拒绝全部资料请求；直接删除检查会破坏内网访问边界。

现在仅在系统解析结果全部落入该网段时，向固定阿里公共 DoH 地址查询真实公网地址；它不是允许连接的目标网段。正常 DNS 结果也要通过公网单播检查。资料请求连接到已检查的 IP，同时保留原 Host、TLS SNI 和证书校验，每次重定向重新检查，不继承环境代理或跨请求 Cookie。

实现见 `wujian/public_network.py`、`wujian/knowledge.py`。未修改系统 DNS、代理或证书设置，未开通收费服务。机制复用 [httpcore 官方 SNI 扩展](https://www.encode.io/httpcore/extensions/#sni_hostname)，没有自建 TLS 或 HTTP 协议栈。

### 2.2 公开正文、元描述与视频观察分别表达

`fetch_document` 保持原调用方式，能够保存原始公开响应，并读取 HTML、PDF、JSON 和 Markdown/纯文本。返回内容带原文行号、来源标识和读取范围，后续由同一来源与知识体系复用。

B站页面支持公开 JSON-LD、`videoData` 原始简介和分P信息。取得这些内容只证明读到了网页，不证明观看视频、识别画面、取得完整操作过程或实际试用成功。公开字幕 JSON 已有格式读取支持，但本轮探测的视频字幕、章节列表为空，不能将格式支持写成已取得字幕。

小红书请求若实际落到登录页面，或在笔记路径中只返回登录提示，不作为成功的笔记读取。空 B站页面也不会因系统添加了一句范围说明而变成“有原文”。

### 2.3 排除 B站 SEO 推荐污染

真实页面的 `description`、`og:description` 不只是当前视频简介，还可能拼接播放统计和“相关视频”标题。例如台灯2视频的 SEO 描述里会出现另一个台灯1S视频，不能把它当成当前型号的能力证据。

现在优先保留当前视频的 JSON-LD / `videoData` 原始简介，不混入 SEO 推荐清单；只有旧页面缺少这些字段时才保留有范围标注的 meta 简介，并去掉可识别的推荐、计数后缀。页面周边的合集、推荐和账号操作不冒充当前视频正文。原始响应仍保存，未把视频标题扩写成未经读取的教程。

### 2.4 读取官方帮助页的实际内嵌正文

小米官方帮助页的真实 FAQ 位于脚本中的 `$GLOBAL_PAGE.PageData.main_body`。此前直接移除脚本会同时丢弃 FAQ，最后只剩商城导航；通用正文提取器也没有解决这个问题。

现在只在对应官方 `/service/` 页面，严格解码实际返回的 PageData JSON，沿明确的 `main_body`、`section`、`body` 容器读取问题名称与回答内容，不执行 JavaScript，不递归提取会话、推荐或导航状态。原文配图只保留链接，没有假称已读图。标准 JSON-LD FAQPage 中 Question 的 acceptedAnswer 文本也可读取。

### 2.5 保留协议和命令原有排版

Markdown、代码及纯文本不经过 HTML 标签剥离，避免损坏 `<target>` 等内容。HTML 高亮代码块按 `<pre>` 的文本语义保留行，避免内联高亮标签把一条命令切成多条。缓存来源重新打开时继续提供原始响应中的导航链接。

已有来源正文不因解析器升级被静默重写，否则历史引文和行号可能失效。需要新解析时使用刷新读取形成新来源记录，旧证据保留。

## 4. 成熟工具对照与暂不新增依赖的理由

本轮在独立临时环境安装 Trafilatura **2.3.1**，依据[官方 API](https://trafilatura.readthedocs.io/en/latest/corefunctions.html)、[提取流程](https://trafilatura.readthedocs.io/en/stable/extraction-overview.html)及[源码](https://github.com/adbar/trafilatura/blob/master/trafilatura/core.py)，关闭评论提取、保留表格，对相同原始资产比较 balanced、precision、recall。

| 材料 | 旧 BS4 输出 | precision 正文 | 加回当时的元数据后 | 有界内容检查 |
|---|---:|---:|---:|---|
| B站玻璃杯布光页 | 5205字 | 93字 | 1771字 | 4项内容预告保留；balanced/recall仍带合集，合并达5261字 |
| [折射摄影文章](https://digital-photography-school.com/4-refraction-ideas-your-creativity/) | 10265字 | 6808字 | 8238字 | 手选10项关键条件保留 |
| 中文电视研究博客 | 10135字 | 8901字 | 9147字 | 14项关键条件、8个原始代码块保留；代码块以忽略排版空白方式对照 |
| 小米官方帮助页 | 4022字 | 0字 | 80字 | 三种模式均未找出脚本内的实际 FAQ |

这组数字来自更早的解析基线，不能与上一节的后续阶段字数直接混比。有限锚点保留不等于全文语义无损。

Trafilatura 对一般文章有收益，保留为候选；目前不把带来17个包的安装变成所有页面的必经层。此次关键损失发生在特定公开数据载体，现有 JSON/HTML 能力已经能修复。PDF、JSON、Markdown、协议和代码文本也不应为了压字数统一送进 HTML 正文筛选。

同样没有集成 MediaCrawler 或默认安装视频下载器。可参考 [yt-dlp 的 B站实现](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/extractor/bilibili.py)了解字幕、章节及登录边界；[MediaCrawler](https://github.com/NanmiCoder/MediaCrawler)的存在不能证明当前网络下能读到小红书正文。此前公共探针的受限记录仍保留，本轮不绕过登录、借用 Cookie 或批量抓取。

## 5. 仍未解决的模型推理限制

真实 `creative-integrated-v4` 与 `rea_research-protocol-v1` 输出显示：即使原文可读取，模型仍会补入未查证参数、把预期效果写成保证，或忽略工具链的现实前提。以下仍属于未通过的质量问题：

- 给台灯1S写出未经读取的色温数值，并把单次布置产生清晰动态焦散写成必然结果。视频简介只能支持“有这种主题/线索”，不能证明给定台灯、杯形和环境一定成功。
- 把“Windows电脑安装Wireshark、同一局域网、知道电视IP”写成足够的抓取条件。需要先确认采集位置能否看到目标流量；过滤条件不会凭空取得没有到达该网卡的数据。DNS有解析也不证明电视正在使用该域名。
- 将一段真实卸载命令引文用于支持整段网络研究总结。行号和引文匹配，只证明那些原句存在，不证明同一条认识中的其它概括受其支持。
- 用旧社区报告推断当前固件、当前客服政策，或把通用工具文档称为该型号协议。地区、固件、网络拓扑、主机命令环境与用户实际观察仍需核对。

用于复核的一手资料：

- [小米国内台灯1S产品参数](https://www.mi.com/mjsmartlamp-1s/specs)：含明确产品型号与色温范围。工程探针确认现有读取器可读到这些字段；它没有在失败轮次中被 Agent 实际读取，不能事后算作那次回答的依据。
- [Wireshark 官方捕获环境说明](https://wiki.wireshark.org/CaptureSetup/Ethernet)：说明交换网络下观察其它设备通信的环境前提；工程探针可读取正文。未据此连接电视或抓取任何用户流量。
- [Wireshark 官方用户指南](https://www.wireshark.org/docs/wsug_html_chunked/)：可继续查具体采集方式与工具条件。没有安装工具或执行设备操作。

这些链接用于研究、核对和审计，没有写入 Skill 成为测试答案。后续真实模型任务仍应由物间自行搜索、下载、选择原句和分析。

下一步质量验证应检查：物品的关键能力与参数是否实际读取；每个方案的因果链和未知条件是否表达准确；新工具是否确认运行环境与数据入口；知识是否拆成引文真正支持的小结论；实际反馈能否修正当前任务。不能通过再接一个通用抓取框架或额外模型审稿，就宣称这些推理问题已解决。

## 6. 后续工具试验与取舍

公开来源实际配图已能通过 `view_source_image` 交给同一主模型观察：只允许取自已授权原文的图片线索，重新校验公开目标、跳转、大小与像素，保存原始图片资产。真实国内宜家 VARIERA 501.777.27 原文及配图已由物间自主取得；它纠正了一部分外形误认，但仍生成不存在的后壁等错误空间关系。因此不能把“看图成功”写成“理解物品已可靠”。

搜索返回现在保留实际搜索调用的链接与查询，不再把搜索模型的综合文字作为原文证据。现有工具增加可选 `read_limit=0..2`：模型明确选择时，可在一次工具中发现并取得少量原文，逐条标明 retrieved/unavailable/not_read；全文和原始资产仍由同一 SourceRecord/Asset 管理，首个窗口3500字符，可再展开。服务返回顺序不是相关性排名，item_id关联也不等于型号匹配。

试过默认读取1条后，创意开发任务虽然取得更多网页，仍有不成立的迁移，并未证明整体提升，故默认恢复0，只保留按需合并。借鉴的是 [Anthropic 2025工具设计实践](https://www.anthropic.com/research/writing-tools-for-agents)中的常见连续操作组合、紧凑上下文与真实任务评测方法，以及[上下文工程实践](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)的按需展开；不是照搬其效果数字。已有SDK可承载，不增加Agent、抓取平台或第二套来源库。

一次额外物理方案复核实验使用同一实际配图，对三个失败方案及一个简单有效控制方案进行复核：它指出了虚构后壁，却漏判纸放在平台下方的视线问题，还错误质疑白纸覆盖细孔的控制方案。额外调用32秒，没有可靠解决核心问题，故没有作为生产必经critic层。原始结果保留本地 `tmp/research/physical-review-loop/`。

实际公开页面还有一次编码误判：有效UTF-8中文被自动猜成CP775，导致标题与引文乱码。继续复用BeautifulSoup的UnicodeDammit，优先严格UTF-8，同时保留BOM与声明的旧编码回退；UTF-8、GB2312与UTF-16 JSON回归通过。旧来源正文不静默重写。

## 7. 视频团队的成熟工具可行性

真实创意任务读到两条B站简介，但简介缺少装配动作；这已成为借鉴具体玩法的证据缺口。独立临时环境仅安装 [yt-dlp](https://github.com/yt-dlp/yt-dlp) 2026.10.26，复用机器已有FFmpeg 9.0，未改生产依赖、未登录或读取浏览器Cookie。

- `BV1pa4y1B7f8`（4种长尾夹手机支架）匿名元数据读取1.485秒，时长70.313秒，返回15种格式。
- `BV1vW411M7VZ`（长尾夹星形摆件）读取0.890秒，时长300.4秒，返回11种格式。
- 两条均未返回字幕、自动字幕或章节，不能以此断言没有画面内字幕。
- 仅第一条验证5–10秒的360p AVC片段，输出186859字节、5秒、640×360；抽5帧，抽查3帧能看到长尾夹支撑手机成品，尚不能还原全部动作，也不能证明8553适配。输出大小不是测得的网络流量。

初始FFmpeg证书失败被保留；使用现有公共CA的ASCII临时路径并明确保持 `tls_verify=1` 后成功，没有关闭验证或修改系统证书。时效播放URL、原始metadata与媒体只保留tmp，不公开提交。

交给A团队的候选接口是：已授权来源ID＋有界时间窗 → 实际媒体区间/帧资产ID、时间、格式、来源 → 主模型观察；原文简介、帧观察、模型解释分别标记。生产还必须把提取器与FFmpeg的每个媒体目标及重定向纳入公共网络边界，并限制网络/进程资源，不能把研究脚本直接开放为Agent任意URL下载器。本轮只是成熟链路探针，不冒充物间Agent已自行观看视频、生成动画或完成实机验证。

### 7.1 探针之后的实际接入

上述是最初研究阶段；随后已在提交 `3b10cf0` 接入 `wujian/source_video.py`，不是将研究脚本直接公开为工具。`video` 可选依赖仅增加锁定的 yt-dlp 2026.10.26；FFmpeg复用本机现有程序，由操作者配置绝对路径。未增加抓取账号、浏览器Cookie或收费服务。

提取器的HTTP统一经过既有公开地址检查、DNS固定、Host/SNI及证书验证；禁用提取器备用网络入口，只允许匿名GET。元数据有请求/字节/耗时上限；媒体是至多12MB的低清单文件，FFmpeg只读本地MP4、禁远程协议和外部引用，每帧有进程超时。接受字节上限不是精确线上的流量上限：读取器在首个超限块终止。取消不再先删除仍在写入的临时目录，工作线程持有目录并停止后续帧。

Agent工具 `sample_video_frames(source_id,start_seconds,end_seconds,frame_count)` 只接受已获准B站BV网页来源，窗口至多30秒、1至4帧。保存原视频Asset与帧Asset，另建 `origin=video_frame_sample` 来源，父网页不变。实际下载的是有界原视频文件后本地抽帧，不能说只下载了几秒。`read_source` 可按当前权限重开同一批已存图片，无需再次下载；原网页缓存按origin区分，不会被同URL抽帧manifest冒充。

画面以SDK原生DataBlock进入同一主模型，正文只给实际采样秒数、来源与观察范围，解码元数据留在SQL manifest。引用显示“已看指定区间抽帧，未观看完整视频或音频”。画面解释可保留为关联该source_id的 `inference/provisional` 认识，不因此成为额定能力或已验证操作；这是已有KnowledgeClaim的引用能力补齐，没有另建视觉知识库。

真实物间主Agent已从用户给出的公开视频链接自主取得原网页、抽帧并回答：得力8553作为真实国内型号、拥有关系为合成；BV1pa4y1B7f8实际取得2,828,800字节视频和2.5/7.5/12.5/17.5秒四张640×360画面。采样工具约4.67秒，初测两轮57.41/54.27秒；紧凑观察表示复测单轮58.92秒。两者使用同四张画面，未证明提速。

## 8. PDF页图直接进入同一主模型

原`view_source_page`先渲染PDF，再额外调用视觉模型转述，主Agent只看到文字解释。这增加调用，也丢失了再次核对原图的机会。网页配图和视频帧已经证明当前主模型的原生图片接入能运行，因此复用同一DataBlock机制，没有增加模型/服务。

先通过真实PDFium、临时SQL、HTTP共享和SDK工具复现两项失败：渲染期间撤回直接或家庭共享，工具仍把PNG发送到额外视觉HTTP边界。仅替换外部模型传输，不替换渲染或权限业务；外层Runner可能还会阻止最终回复，不能据此声称真实界面已经漏给用户。现在渲染前后分别用`readable_source`检查，原件asset_id变化也拒绝返回，成功时直接返回PNG、source/page/asset及观察范围，登记本轮实际依据。

删除普通页图的额外视觉RPC。进一步核对队友`demo/a-guidance-3d`发现其场景提取仍使用`Settings.vision_model`，因此保留该配置/环境字段兼容，不以单分支暂时无调用者为由阻断团队集成。`render_source_page`签名与base64返回保持，工具内部改为原生图像块，不再提供`visual_reading`二手转述；公共HTTP契约没有变化。主模型按当前模型设置处理图像，不代表任意换入的纯文本模型都支持图片。

[pypdfium2官方文档](https://pypdfium2.readthedocs.io/en/stable/python_api.html#incompatibility-with-threading)明确指出，不同文档的PDFium原生调用也不能跨线程并行。因此唯一页图渲染入口以进程内锁覆盖原生文档/页/位图的完整生命周期；没有增加队列或服务。常规页保留1.4倍渲染，超大页最长边限制2000像素，PNG超过8MB真实拒绝；这不是全应用并发限制。复杂PDF的CPU耗时尚未隔离到独立沙箱，不能冒称不受任何恶意文档影响。
