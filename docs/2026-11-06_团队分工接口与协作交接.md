# 物间团队分工接口与协作交接

版本日期：2026 年 11 月 6 日。适用于三人并行开发与集成。

三人分别负责物品理解与教学、创造与回忆及物品名片、社交与家庭协作。所有功能使用共同的人、型号、实物、知识、个人理解、经历、任务和权限，经由同一主 Agent 协作。底座允许随真实需求调整，由指定负责人集中维护公共语义与接口。

本文包含已确认的产品方向、可核查的现有接口，以及建议采用的任务和协作安排。尚未点名的岗位以 A、B、C 表示；B 为队长本人。公共底座负责人由三人中一人兼任，开工时填写姓名，不增加第四位开发者。

## 2 四个栏目与完整用户体验

四个栏目是用户入口，不是四套后台或四个独立 Agent。

| 栏目 | 承载体验 | 跨模块联系 |
| --- | --- | --- |
| 物伴 | 阿圆统一问答、用法指导、创意交流、目标规划、事项接续；按需展示步骤和方案卡 | 进入时携带相关物品与事项；按权限读取知识、状态、偏好和经历 |
| 物品 | 家庭用品、我的物品、搜索筛选；点开后进入以物品名片为主的详情 | 名片展示同一物品的状态、经历、照顾记录；用法、新玩法和可选分身对话接回物伴 |
| 回忆 | 用户主动记录照片、文字、时间和经历；一段经历可以关联多个物品 | 回忆墙与物品经历读取同一条记录；是否供 AI 参考、是否分享分别控制 |
| 朋友 | 好友、主动分享的心愿、赠礼、接收与精选故事 | 复用真实物品、经历和授权；家庭管理放在物品与照顾入口，业务由 C 负责 |

大字版重点呈现问一问、拍照问、家人提醒与单步指导，复用普通版的记录和处理结果。语音不可用时仍能通过文字与照片完成主要任务。

物品名片占主要内容区，包含照片或可选分身、名称、位置、当前状态、个人介绍与经历等。物品列表退回上一层；不是继续保留大列表、仅在右栏展示详情。没有分身的物品正常展示照片和资料，不强制拟人。

名片上的“发现新玩法”只作入口。具体的搜索、交流、候选方案和调整回到第一栏与阿圆进行；用户需要继续实践时再保存或接续共同事项。首页同样提供克制、手机可见的创意入口，不自动推送大量创意内容。

典型贯通体验：录入物品 → 查询用法或发现新玩法 → 接续实际事项并反馈 → 主动留下经历 → 在名片与回忆墙查看 → 选择物品和故事向朋友传递。用户可从任一步进入，不必走固定流程。

## 3 三人的职责与交付

### 3.1 A 物品理解与教学负责人

负责 F1、F2 的主要实现，以及 F8 中使用、排障和维护知识；为 F3、F4、F5、F9 提供共用认识。

| 工作 | 交付内容 | 与他人的边界 |
| --- | --- | --- |
| 身份与认识 | 准确型号、地区版本；非标物的外观、材料、用途与未知 | B 负责名片呈现；不要求手作、礼物或石头填写商业型号 |

| 使用与排障 | 简洁首答、必要时逐步指导、依据核对、失败分支、售后说明所需事实 | 复用共同 TaskRecord，和 C 共用任务进度；不能预置虚假的操作结论 |
| 视频理解与切片 | 针对具体问题定位相关片段、保留原视频与时间范围、解释适用对象 | 复用共同来源与媒体能力；不能把相似设备的视频直接认作本机教程 |
| 教学动画 | 从核实过的步骤产生清楚的教学表达，可优先图示和标注，再验证动画 | 动画是知识的呈现，不是操作事实的证据；按钮、顺序和设备外观需核对 |

主要接入文件：`wujian/knowledge.py`、`agent_skills/product-guidance/SKILL.md`；涉及 `learning.py`、`source_access.py`、`evidence.py` 和公共模型时与底座负责人协调。教学界面可在既有事项组件中增量接入，不单独复制聊天系统。

A 向 B 提供的核心能力是“这件物品能做什么、依赖什么、不能做什么、哪些不知道、依据在哪里”，而不是一段不可追溯的商品介绍。创意案例的选题、搜集策略和改编质量由 B 负责；A 提供通用的资料读取与证据能力。

## 4 共同数据与模块互通

| 概念 | 当前承载位置 | 共同约定 |
| --- | --- | --- |
| 标准型号 | ProductRecord 及 ProductSpec | 品牌、准确型号、地区、版本；共性知识不覆盖具体实例状态 |
| 具体实物 | ItemRecord、状态与关联 Profile | 用 item_id 接续；同型号的两个实例不是同一个物品 |
| 个人介绍与分身 | Profile；接口投影为 description、avatar 等 | 展示设置与实际状态、私人经历分别表达 |
| 可复用物品认识 | KnowledgeClaim、SourceRecord | 保留类型、依据、范围、条件和来源；模型猜测维持 inference |
| 日常个人理解 | Memory | 安静积累，支持情境、期限、纠正与遗忘；不等于主动发布的回忆 |
| 回忆墙经历 | ExperienceRecord | 一次保存可关联多物，照片文字与作者保留；AI 用途与分享分开 |
| 持续事项 | TaskRecord、TaskParticipant | 同一目标接续同一事项；方案、条目进度和现实结果分别表达 |
| 家庭与共享 | Household 等关系、明确授权 | 家庭身份、物品权限、故事用途、设备控制互不代替 |
| 赠礼与心愿 | Gift、Wish | 心愿不是已拥有资源；赠礼不是自动转移所有私人信息 |
| 检索 | ReMe 投影 | 业务事实以 SQL 为准；撤权或修改后不能继续使用过期投影 |

模块间传递真实 ID 和版本，展示名称不作身份主键。照片使用有权限的 asset_id；不在业务 JSON、聊天上下文或数据库中无条件复制整段视频及图片字节。

本轮后续内部简化：`view_source_page`向同一主模型返回实际PDF页图及页码/来源的原生DataBlock，取消额外视觉模型的`visual_reading`转述；`render_source_page`签名和base64返回保持，PDFium生命周期串行、异常大页有界。已核对A的3D分支仍使用`Settings.vision_model`，因此保留配置兼容；普通页图不再额外调用该模型。A若消费`visual_reading`，集成时改用实际页图/同一主模型观察；不能整文件覆盖公共主循环。这里是内部工具变更，HTTP/OpenAPI未改变。

用户点击入口时，只携带已知且必要的对象和意图；模型仍可自主寻找其他相关资源。不要把某个入口的固定提示当成完整用户要求，更不能覆盖用户已经输入的限制。

## 5 现有接口与调用约定

以下列出基线已有且本轮继续复用的 HTTP 接口。输入输出以当前分支 Pydantic 与生成 OpenAPI 为准；本轮兼容字段变化见第 1.2 节。本文仅列模块接入重点，新开发的内部函数直接复用业务操作，不要求所有进程内调用都绕一遍 HTTP。

### 5.1 公共入口与物品理解

`POST /api/assets` 的存在不代表视频上传、转码、长任务和动画产物已经受支持；多媒体新增范围先验证再扩展。

创意入口的请求形状如下。例子中的 ID 为占位，不可原样用于真实数据库：

```json
{
  "text": "这盏台灯除了照明，还能玩点什么？别让我拆它。",
  "conversation_id": null,
  "item_ids": ["item_example_lamp"],
  "photo_ids": [],
  "entry_context": {"intent": "creative", "task_id": null}
}
```

`entry_context.intent` 现有值为 general、guidance、creative、planning、story、persona。接续话题时使用真实 conversation_id；接续事项时使用真实 task_id。物品名片的原入口、返回位置等导航信息先留在前端，确有持久化需要再扩展契约，不能直接向当前禁止额外字段的请求塞新字段。

### 5.2 创意 记忆与回忆

| 方法与路径 | 用途 |
| --- | --- |
| `GET /api/experiences`、`POST /api/experiences` | 回忆列表与主动记录 |
| `PUT /api/experiences/{experience_id}`、`DELETE /api/experiences/{experience_id}` | 版本化编辑和删除 |
| `GET /api/experiences/{experience_id}/shares`、`POST /api/experiences/{experience_id}/shares` | 查看或增加指定好友分享 |
| `DELETE /api/experiences/{experience_id}/shares/{recipient_id}` | 撤回未来读取授权 |
| `GET /api/memories`、`DELETE /api/memories/{memory_id}` | 查看和遗忘个人理解 |
| `POST /api/memories/{memory_id}/correction` | 显式纠正个人理解 |

新回忆当前默认 allow_ai=false；这是既有事实，应在体验中提供清楚、低打扰的控制，不在每次日常聊天后追问要不要保存。共享回忆和允许 AI 参考是两件事。

Agent 主动记录复用 `domain.create_experience`。0008 在 `messages` 新增内部 JSON 字段 `recorded_experiences`：原用户消息保存规范化请求摘要到已写入经历 ID 的映射，和回忆记录同次提交，不复制正文或媒体。同一原消息的同一请求重试返回已有结果；不同消息或不同内容仍可有意记录。原记录删除后保留收据，旧请求不能把它复活；后续编辑或关闭 AI 参考也不能被重试覆盖。检索中的 `record_receipts` 只是获准历史聊天的写入回执，不授予回忆正文权限；AI 关闭时不能作为 `story_refs` 引用。二者均不是新增公共 API 字段。数据库备份、升级和删除后的重试反例由底座负责人维护。

创意没有另一套模型接口，继续走 `/api/chat`。主 Agent 的 `learning.knowledge_updates` 可表达 capability、boundary、procedure、observation、case；`conditions` 包含 requirements、limits、unknowns，`basis` 区分 document、user_report、inference，`scope` 区分 product、item。这些是现有结构化认识字段，不是新增 HTTP 写入接口；沿现有验证与事务提交。

内部`search_public_web`可选`community="bilibili"`复用video extras里的yt-dlp公开搜索，默认web维持百炼；不是新增HTTP契约或来源事实库。搜索线索之后仍需fetch_document/read_source及按需图像观察；不从标题直接保存已验证案例。匿名会话由工具本次生成，受限/缺组件不自动转收费搜索。搜索不需要FFmpeg，视频抽帧才需要；公共reader的same_origin/cancel_event是内部可选参数，原有调用不必改变。

### 5.3 共同事项与反馈

| 方法与路径 | 用途 |
| --- | --- |
| `GET /api/tasks`、`POST /api/tasks` | 读取及保存共同事项，保留既有语义 |
| `POST /api/task-boards` | 显式创建结构化事项板 |
| `GET /api/tasks/{task_id}/board` | 当前清单、步骤、参与关系与进度 |
| `PATCH /api/tasks/{task_id}/entries/{entry_id}` | 实际条目反馈 |
| `PATCH /api/tasks/{task_id}/entries/{entry_id}/assignee` | 条目分工 |
| `POST /api/tasks/{task_id}/shares`、`POST /api/tasks/{task_id}/accept` | 邀请、接受参与 |
| `DELETE /api/tasks/{task_id}/shares/{participant_id}` | 撤回参与 |
| `POST /api/tasks/{task_id}/conversation` | 返回当前用户可用的同事项会话 |
| `POST /api/tasks/{task_id}/feedback` | 针对当前方案的真实结果反馈 |

现有 plan 可用 `schema: interaction/1`，kind 为 checklist、guidance、idea；条目使用稳定 id、title、可选 item_id、group、note、state 等字段。group 为 owned、buy、borrow、confirm、step；state 为 pending、ready、not_found、unchanged。待购买或未落实借用的东西不能冒充已拥有物品 ID。

条目反馈示例：

```json
{
  "expected_version": 3,
  "state": "not_found",
  "note": "我找了一圈，那个夹子应该借给同学了。"
}
```

ready 条目不代表现实任务完成；旧方案的成功不能完成新方案。协作者能看哪些内容、能在聊天中推动哪些更新，需要继续做角色验收，不能由“能进入同一事项”推断成“模型已有发起者的全部写权限”。

本轮最终计划沿 `turns.commit_result` / `commit_continuation` 进入共同 TaskRecord，不新建创意专属任务库。接续时带原 task_id 和 expected_version，反馈对应本次用户原话；没有新目标就不另造一项事项。模型生成期间不锁库，最终短事务重新检查上下文 revision，将计划、学习、最终回答和 Run 状态一并提交；失败回滚不能只留下“已保存的成功方案”。结构化结果预检复用真实业务操作，在独立 Session/SAVEPOINT 中试写后回滚，不作为第二个 writer。预检和引用呈现只能做 SQL 及已有资料的只读导航，不能暗中联网、操作设备、通知或写检索投影。

### 5.5 REA 与多媒体待扩展边界

已有 REA 接口包括 `GET /api/devices/status`、`POST /api/items/{item_id}/device`、`POST /api/devices/{target_id}/explore`、`POST /api/devices/{target_id}/proposals`、`GET /api/devices/operations/{operation_id}` 和 `POST /api/devices/operations/{operation_id}/execute`。照片识别、准确型号、已读说明书能复用，但不能据此推断控制软件、协议、固件及实际效果已确认。

本轮无需真实连接即可从物品进入设备个性化资料研究与逐步指导；明确的物品 ID 和可编辑草稿接到同一主 Agent，不自动发送或启动设备桥。真实控制仍沿上述授权、目标、提案和执行接口，当前没有真实电视去广告或屏保改变的成功证据。

公开视频已有内部工具 `sample_video_frames`，对应 `source_video.sample_source_video`：输入已获准的公开来源 ID、起止秒数和 1–4 帧；限 B 站单 BV 首 P、最长 30 秒窗口、可取得的有界低分辨率单文件 MP4，媒体上限 12MB。先取得原网页，再经可选 yt-dlp 解析与现有公共网络读取边界下载；FFmpeg 只读取本地文件，不读取远程地址。安装源视频可选依赖并提供真实 FFmpeg 后才可用，缺失或受限返回明确错误，不能模拟成已看视频。

抽帧结果保留原来源、请求窗口、原媒体及派生帧资产；保存前重新检查来源权限。`read_source` 再次打开派生来源时返回实际原生图片，而不只返回清单。它只观察少量画面，不听音频、未观看全片，也不是只下载该时间窗；不能据此编完整动作或宣称适配当前型号。公开视频简介、公开字幕文本、实际抽帧和模型解释保持各自性质，推测即使关联真实来源仍是推测。

来源导航基于已获准 SourceRecord 的 ID、原 URL、标题、行号、页面链接与资产；最终回答及事项来源展示复用这些记录，只读生成导航，不把显示引用变成新的抓取、授权或写入。缓存原网页重新打开也保留可用链接；B 站导航与推荐噪声不混作作者提供的案例来源。

视频剪辑 UI、字幕生成与教学动画尚无核定完成的专用契约。A 与底座负责人沿现有抽帧基础先验证真实教学收益，再决定最小扩展。候选新增结果应表达关联物品和型号适用性、原始来源、片段起止时间、对应步骤、产物 asset_id、生成或引用性质、状态及失败原因；这部分是未来契约要求，不是已交付字段。

长任务确有需要时先比较成熟任务执行能力与现有运行管理，不能另造一套失去重启状态的队列。不能让每次问答都强制生成动画；视频、图文、动画按问题和真实收益选择。

### 5.6 所有模块共同遵守的语义

1. 身份取自服务端认证，客户端传入 recipient_id 等业务对象不代表可冒充该身份。前端隐藏按钮不能代替后端授权。
2. 接口要求 expected_version 时必须携带读取到的版本。冲突后刷新并展示差异，不能自动换成新版本强行覆盖。
3. 按实际错误处理 401、403、404、409、422 和服务故障；未获准对象可能以 404 隐藏存在性，不依赖错误差异枚举他人物品。
4. 未读原文不能伪造来源，搜索摘要不等于原始资料。用户报告、模型推测、软件观察和实物效果分别保留。
5. 不假设所有 POST 天然幂等。任务接续会话等已有去重语义可以复用；其他动作按实际实现防重，超时后先核实是否已提交。
6. 失败、断线、撤权、取消后不得展示成功或继续使用旧权限结果；草稿、对象上下文和可恢复入口要保留。

## 6 底座变更与共同文件维护

遇到新需求先判断是展示、模块能力还是公共语义变化。底座应支持有价值的功能；不能为了不动底座逼功能绕路，也不能每遇到一个问题增加一个 Agent 或数据库。

| 变化 | 实施方式 | 核对范围 |
| --- | --- | --- |
| 模块内布局、文案、展示 | 模块负责人自行实现 | 手机与电脑、空/错/加载状态 |
| 模块内新玩法或资料策略 | 功能负责人实现，沿共同工具接入 | 真实输入、来源、约束、效果与耗时 |
| 新增公共可选字段、工具 | 与底座负责人先对齐最小输入输出；优先兼容旧调用 | 三方消费位置、默认值、旧记录 |
| 权限、认识更新、任务含义、数据库结构变化 | 底座负责人协调小 PR；影响方参与审查 | 迁移备份、越权反例、跨功能旅程与回退 |
| 破坏性接口变化或框架替换 | 先比较替代路径与收益，负责人决定切换方案 | 调用方同步、数据保留、失败恢复与成本 |

变更提议用以下短模板即可，不要求每个小改动写长方案：

```text
用户场景：谁在做什么，当前在哪一步失败？
现有机制为何不足：给出复现与证据。
最小改动：涉及哪些公共字段、接口、规则或工具？
影响方：A / B / C 哪些调用会变化？
兼容与数据：旧调用、旧记录、权限、迁移如何处理？
验证与恢复：怎样证明改善，失败如何恢复？
```

收到提议后先对齐契约，调用方可使用明确标注的 Mock 并行；最终必须替换为真实实现并联调。共用文件不永久锁死：在 PR/任务记录中说明谁正在改什么，避免同时整体重写。

| 共同文件 | 维护约定 |
| --- | --- |
| `api_models.py`、`contracts/openapi.json`、`frontend/src/generated/api.ts` | 源契约先修改；从 Pydantic 导出并生成，不手改生成文件 |
| `database.py`、`migrations/`、`migrate.py` | 底座负责人协调；新增迁移，不改已共享的历史迁移；多人迁移先对齐 revision 链 |
| `domain.py`、`foundation.py`、`interactions.py` | 界面与 Agent 共用操作；权限和结果语义统一审查 |
| `agent_runtime.py`、`turns.py`、`learning.py`、`retrieval.py` | 主循环和认识机制统一；各模块补工具或 Skill，不复制主 Agent |
| `App.tsx`、`navigation.ts`、`Conversation.tsx` | 公共入口、运行、草稿和上下文，由底座负责人协调 A/B/C 的接入 |
| `TaskBoard.tsx`、`Editors.tsx`、`shared.tsx`、`styles.css` | 多模块使用；局部改动并声明影响，CSS 尽量限定模块作用域 |

公共表单过大时可按业务拆分，但只为当前多人冲突或维护问题拆分，不先重构整个前端。

## 8 Git 本地数据与接口协作

### 8.1 分支与集成

`main` 保存负责人批准的基线，`develop` 为三人集成。每人从更新后的 develop 建自己的短期分支，例如 `feat/object-understanding`、`feat/creative-memories-cards`、`feat/social-household`；底座改动可用 `codex/foundation-<topic>`。大方向分支也要小批提交，尽早发可审查 PR。

1. 开始前确认 `git status`，保护自己已有修改；不要使用 reset --hard、强制覆盖或强推解决普通协作问题。
2. 获取远程更新、核对起点后建功能分支；保持每个 PR 能说明一个完整改进。
3. PR 指向 develop，附用户行为、契约/迁移影响、实际验证和已知失败。
4. 通过相应检查，由至少一位成员审阅；公共语义由底座负责人重点复核。
5. 合入后通知受影响成员同步、生成类型或执行迁移；不能只说“代码传好了”。
6. main 的更新由队长明确批准；没有新的授权就不将集成进度自动作为发布基线。

当前本地在 `codex/creative-memory-rea` 开发，已推送同名分支并创建指向develop的草稿PR #6；本轮没有合并或更新`main`、`develop`。交接时先核对`git status`、PR当前head和对应CI，再看实施记录中的阶段证据。代码、迁移、生成契约及必要说明按可审查的提交组织；草稿PR可供成员核对，但不等于团队集成或智能质量已通过。

### 8.2 本地运行与数据

队员各自运行本地后端和数据库，不把同一个 SQLite 文件放共享盘多人写入。协作通过 Git 代码、迁移和明确合成的开发样本；不把一人的私人数据库拷给全组作为同步方式。

默认数据位于 `var/`，主库为 `var/wujian.sqlite3`，媒体在本地数据目录中。自定义数据目录可使用 `WUJIAN_DATA_DIR`；若同时设置 DATABASE_URL，需确认仍指向自己的数据库。已有 SQLite 升级前使用项目备份机制，迁移和回退都核对数据与媒体一致性，不删 var 修复。

初次依赖安装与运行沿 README 和锁文件进行；已有环境日常启动为：

```powershell
.venv\Scripts\python.exe -m wujian serve
```

前端开发可运行 `npm.cmd --prefix frontend run dev`，其 `/api` 代理指向本机 8000。其他端口或跨设备联调需明确代理、认证和访问方式；手机不能用它自己的 127.0.0.1 访问电脑服务。当前不是已加固的公网部署。

`.env`、密钥、会话秘密、私人库、照片视频、日志、本地评测目录和参考压缩包不提交。fixture 中人物、拥有关系和经历明确虚构，商品型号、地区版本和来源真实。真实模型测试沿既有百炼授权进行，新增收费服务须另行确认，不在 CI 或普通离线回归中调用付费模型和设备。

## 9 验收与交接

### 9.1 各模块验收重点

| 模块 | 自然输入示例 | 通过条件 |
| --- | --- | --- |
| A 物品理解 | “这是我家的这台，说明书找不到了，怎么只脱水？” | 测试前固定真实国内型号和版本；找适用原文、核对操作条件；未知不编造；步骤能继续 |
| A 视频教学 | “视频太长了，我就想看这一步怎么弄。” | 原视频、片段时间、机型差异和步骤对应可核查；切片与生成内容不混淆 |
| B 创意 | “最近有点无聊，台灯和几个玻璃杯能玩点什么？别让我拆东西。” | 不只常规摆放；有明确机制，结合已有物品、状态和不拆约束；引用真实案例时可追溯 |
| B 反馈接续 | “刚刚试了，夹子夹不住，换个不用夹子的。” | 找到原方案、保留目标、替换失败机制，不只换名词；不把旧成功算到新方案 |
| B 回忆 | “毕业那天她送我这个杯子，这张照片也一起放进去。” | 同一经历出现在回忆墙和杯子名片，编辑一致；非标物不强填型号 |
| B 分身 | “今天挺累的，想跟这个小家伙聊两句。” | 使用已开启的形象和允许参考的经历，语气自然；不凭空虚构共同经历或强制变任务 |
| C 家庭提醒 | “这个壶还没修好，提醒奶奶今天别用，放在厨房左边柜子里。” | 提醒与同物品关联，大字或朗读可达；已读不算完成，完成不等于修好 |
| C 赠礼 | “把这朵向日葵送给她，带上我写的这段话，其他聊天别给她。” | 预览与接收内容一致，仅传所选内容；作者和控制权正确，实物交付另行确认 |

### 9.2 必须跨模块走通的旅程

1. **理解到创造**：A 留下物品能力、边界与出处；B 的创意任务可读取复用，不要求用户重录；案例缺少参数时保留未知。
2. **创造到延续**：用户尝试后反馈，更新原事项；主动记录时生成一条经历，名片和回忆墙共同显示，日常理解安静更新。
3. **延续到传递**：B 的经历可由 C 在赠礼中精选；收礼者能看到被赠内容，不能获得赠送者所有记忆；后续自主增加自己的经历。
4. **家庭到指导**：C 的家人提醒关联 A 的使用帮助；B 的名片显示当前状态；老人接续步骤时不重新解释整件事。
5. **状态与授权变化**：物品暂停、借出或撤权后，旧页面、旧检索、旧创意及旧事项不能继续把它当作当前可用且获准的资源。

### 9.3 对抗性检查

用反例找失败，而不只演示顺利路径：相似外观不同型号；同型号两个实例；来源写着别的地区版本；网页夹带要求泄密的指令；过期偏好与当前要求冲突；已遗忘信息又出现在旧聊天；两人同时更新；重复点击和超时；A 请求晚于 B 返回；新玩法入口来回切换；分享、撤回和赠礼后的访问变化。

测试采用生活中自然会说的中文，开发样本、回归与独立验收分开。真实调用保留首次答案、实际来源、工具轨迹、耗时、结果和人工判断；修正后另记复测，不覆盖首答。模型自评、HTTP 200、动画生成成功与工程绿灯均不能代替用户结果。

### 9.4 每个 PR 的最小交接

```text
负责人和分支：

基于哪个 develop 提交：
```

团队每完成一批就集成并实际走一条跨模块旅程；有阻断立即在 PR 或任务记录中同步。开工时先填好三位姓名、底座兼任人和 REA 执行人，确认同一代码起点及第一批任务。后续按可演示的用户结果扩展，不等三套功能分别“全部做完”才第一次联调。
