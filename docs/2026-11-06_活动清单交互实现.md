# 活动清单交互实现（2026-11-06）

## 目标与既有底座

用户先对阿圆说出活动目标，例如「周六四个人去公园野餐，帮我看看带什么」，由主 Agent 整理同一条任务。任务卡打开后，用户可以继续核对和补充物品，而不是进入独立的活动管理系统。

本次界面改动在 `frontend/src/features/TaskBoard.tsx` 和局部样式 `outing-task.css`。复用已有 `TaskRecord`、`interaction/1` 计划中的 `entries`、参与邀请和任务版本，不增加依赖、数据库或另一个 Agent。总管家的任务生成与确认由对应后端能力负责，本文件不把界面存在视为模型已经通过验收。

## 界面与行为

- 活动任务主内容区显示准备清单，手机上也能在对话下方直接操作。右侧或手机下方保留参与邀请和实际结果反馈；移除第二套重复的可编辑清单。
- 每项分别显示有无和准备进度。「有」不表示已装好；「没有」不生成虚假库存；「待确认借用」不表示朋友已经同意；打勾表示用户报告备妥，不表示活动已经完成。
- 「补充一项」允许填写名称、有无、可选的已录入物品、说明和负责人。已有库存关联和普通待购物品可以共存，不要求用户先录入库存才能列清单。
- 修改条目的名称、有无或关联物品，原准备进度重新等待确认；只改说明保留进度。责任人沿用独立分配接口。
- 发起者可编辑项目并分配给自己或已接受邀请的参与者。待接受邀请的人只有摘要和接受入口；参与者只能更新、编辑自己负责的项目，新增项目由自己负责。
- 要朋友负责时，先通过「一起准备」邀请已建立关系的朋友，对方接受后才进入负责人选项。任务共享不会自动授予私人库存、私人回忆或对话的阅读权。
- 已共享的清单可以保留物品名和准备说明，但对参与者隐藏无权读取的 `item_id`。参与者仅改备注时不传隐藏的 `item_id`，防止清掉发起者的实际关联。
- 保存失败保留输入；遇到其他人更新导致版本冲突时重新读取实际清单，供用户核对后再提交。已写入成功但工作区刷新失败时单独提示，不把成功写入显示成失败。

## 接口

| 操作 | 复用或新增接口 |
| --- | --- |
| 读取清单 | `GET /api/tasks/{task_id}/board` |
| 补充项目 | `POST /api/tasks/{task_id}/entries` |
| 修改详情 | `PATCH /api/tasks/{task_id}/entries/{entry_id}/details` |
| 报告备妥或取消备妥 | `PATCH /api/tasks/{task_id}/entries/{entry_id}` |
| 分配责任人 | `PATCH /api/tasks/{task_id}/entries/{entry_id}/assignee` |
| 邀请、接受 | `POST /api/tasks/{task_id}/shares`、`POST /api/tasks/{task_id}/accept` |

新增与修改提交 `expected_version`。项目 ID、最初的 pending 状态和更新人由服务端生成。界面不提交 `ready` 冒充新物品已经备妥。

## 借鉴与验证边界

参考 [Microsoft To Do 官方分配说明](https://support.microsoft.com/en-gb/todo/assign-tasks-in-shared-lists)，把加入共享清单、责任人和实际完成分开；参考 [官方任务管理说明](https://support.microsoft.com/en-us/todo/managing-tasks-in-microsoft-to-do)，把备注、步骤与勾选进度放在任务本身。只采用对应的交互机制，不为此引入另一套任务服务。

前端 TypeScript 与生产构建通过，包含总管家确认卡与根契约生成的 ActionView 类型。隔离测试环境 `tmp/butler-outing-ui/` 使用明确标记为模拟的小林、小雨与合成拥有关系，实际浏览器已检查：

- 4 项清单新增「冰袋两块」后变为 0/5，选“没有”不会制造库存或自动备妥。
- 勾选野餐垫变为 1/5；仅修改说明保持 1/5；修改名称后恢复 0/5 等待重新确认。
- 朋友未接受邀请时没有补充、修改入口且勾选禁用。接受后可自行新增「一盒洗好的葡萄」，不关联私人库存，自动由自己负责；勾选后整体为 1/6，其他人的项目仍不可编辑。
- 发起者可以将饮用水分配给已接受邀请的小雨。朋友视角看不到发起者私人物品卡或可点的物品 ID。
- 在 390×844 手机视口检查了清单与补充表单，内容和保存按钮可见，检查后恢复默认视口。
- 新布局只有一份可编辑清单，移除 Rail 里重复的进度摘要。手机滚动到底后，协作、实际反馈和拍照续聊按钮未被底部导航遮挡。

独立源码对抗审查发现并修复了任务切换后旧异步响应覆盖当前事项、反馈草稿串到其他任务，以及参与者取消可见关联时被误当作省略字段的问题。确认卡二次审查还修复了较旧 GET 响应将已确认状态退回待确认的竞态。所有进度仍来自同一任务记录。

## 总管家确认卡

`ButlerActionCard.tsx` 与局部 `butler-action.css` 供对话和任务共用。展示内容通过 `GET /api/tasks/{id}/action` 获取，由服务端验证草稿；确认或取消提交同一版本号，不直接把 Agent 生成文本当执行结果。

普通准备清单和提醒／赠礼待确认操作分开呈现。待确认操作卡不提供活动邀请或普通清单编辑；确认成功后显示真实状态和回执。网络异常提示结果尚需核实，先重新读取状态，避免把“响应丢失”说成“尚未执行”。赠礼注明数字赠礼与实物交付的区别；提醒注明创建成功不代表对方已阅读或完成。

浏览器实际确认了一条模拟提醒：刷新后仍为 confirmed，并显示同一真实回执；只读 SQLite 核对对应提醒恰为 1 条。浏览器实际取消了一份模拟赠礼：状态 cancelled、result_id 为空、礼物业务表没有新增记录。明细与只读结果保存在 `tmp/butler-outing-ui/ui-verification.json`。

过程中旧验收进程仍运行较早签名版本，读取草稿曾被拒绝。界面只展示错误和重新核对入口，没有确认按钮；更新后端进程并用 canonical writer 重签待确认草稿后通过。本轮没有绕过签名，也没有把旧进程的拒绝当作执行成功。

这些浏览器操作使用准备好的合成待办，证明界面与实际写入路径相接；主 Agent 从自然语言生成草稿和活动清单的智能质量，需结合本轮真实百炼验收记录确认，不能由这些界面检查代替。
