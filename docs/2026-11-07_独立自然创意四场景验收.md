## 共同数据与任务事实

SQL全程只有四件耐用品，没有为口头零料新建物品。四个场景各生成一个task；照片首答及接续始终为同一ID `1ef9f3399b35431ca850bd1b7a99c97a`。最终四个任务所有条目均 pending，没有提议被标成完成；照片合成试摆反馈进入同任务，outcome=unknown，status=in_progress。最终没有 Memory 或 KnowledgeClaim，把当前提议变成个人偏好/设备已验证事实的写入未出现。workspace API也可见这些同一任务；本轮未另外做Chrome视觉验收。

家庭卡片的search_world片段明确标注“Codex编者整理、原视频元数据、未观看”，模型读到了这些内容；这可以证明使用了灵感库，不能说它观看了教程。耳机和摄影首答没有使用该库，不应为了覆盖率编造引用；其新颖性与是否足够有用应由实际内容评判。

## 电视错误的直接证据

首个新来源 `4e31a9a88a7d4f738138c1070469e4ed` 是 YouTube《XIAOMI TV A Pro 32 (2026) - 如何设置屏保》的页面描述，和国内 L55M5-AZ 型号不同，也没有观察视频。最终引用来源 `9c1919f77b264d80b49a565b8d0a961d` 的正文是“如何设置手机大时钟屏幕”，其AI文稿讲手机“桌面和个性化”“时间样式”，不是电视屏保。Agent仍声称目标电视系统内置翻页时钟，并把具体菜单写为 `guidance.basis=general`、`evidence=[]`，任务被保存。

这表明“模型读取过来源”与“来源支持当前方案”仍分离；精确设备步骤可以被标成general而逃开document证据条件。这里不是要求所有创意必须搜索，问题在于已经读到不适用内容，仍给出肯定的型号能力与操作。

耳机具体切换也需纠正：[华为FreeBuds 4E官方支持](https://consumer.huawei.com/cn/support/content/zh-cn16082776/)说明长按切换降噪，或在智慧生活/智慧音频的耳机页面启用；首答的“捏耳机柄/手机快捷开关”没有已读来源支持。本次官方核查发生在首答之后，没有提前喂给 Agent。

## 搜索元数据共同根因的新实证

本轮额外捕获的 `search-provider-trace.jsonl` 补齐了上一轮缺少的原始Responses证据：上游 `web_search_call.action.sources` 确只有type/url，annotations为空；但同一响应的 output_text 有4条或7条“发现标签+URL”，包括官方小米FAQ、精确型号教程。当前归一化忽略整段发现标签与推荐顺序，按原始 sources 排序自动读取首条，分别拿到不同型号YouTube和手机时钟抖音。

这些模型生成的标签不能冒充真实网页标题、步骤证据或型号兼容结论；仍可作为明确标注未读的搜索发现信息，在URL与已完成搜索的sources核对一致时帮助选择原文。证据已交资料发现负责人，未为此额外发搜索请求，也未在独立题首答后重抽答案。

本轮结论：任务持久化、同任务接续、零料轻量接入和未造成功有实际改善；四场景里有能起步的小点子，但创意深度与直接交付仍有限。电视一例的错误能力/菜单指导已足以保持 **NOT_ACCEPTED**，不能用五个 completed 包装成创造价值已验收。
