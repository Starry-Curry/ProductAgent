## 1. 必须理解的产品主线（以下是任务约束，不可丢）

本产品属于天猫 AI 黑客松「智能日常」的 **Product Agent/物品智能服务**，独立于任何其他产品。它面向所有真实物品的购买者、所有者与使用者，不只服务老人，也不是普通库存软件、说明书问答机器人、购物导购或虚拟宠物。

**底层主张：从实体物品创造的真实价值出发，理解人与物品之间的关系，最后改善人的日常生活以及人与人之间的协作、照料与情感联系。**

**四个体验原则：有事时可靠；没事时有趣；长久使用省心；人与人产生真实价值。**

两种自然入口：无需账号、无需先建档的**立即拍照/扫码/发问**；选择保存之后形成**长期物品身份**。购物订单、条码、照片、手动录入都是**证据来源而非所有权或型号的自动证明**。在不知道时明确标未知，在用户确认后才升级事实状态。

产品分类 F1—F12（分类不是 12 个必须独立上线的页面、模型或排期）：

- **F1** 识物、扫码、照片/铭牌 OCR、型号消歧与免注册开始；实物来源不限平台。
- **F2** 具体物品数字身份、个人/家庭物品空间、状态/归属/位置/多件同款/流转记录。
- **F3** 单物品可信问答、使用指导、分步排障、维护与售后；步骤要能执行和验证。
- **F4** 主动探索新奇妙用、真实功能和多物品创意；创意须合理、考虑材料与安全条件、实际尝试和反馈；可选轻游戏化。
- **F5** 围绕真实生活目标调用已有物品做组合规划；既检查兼容性，也检查任务协作；允许得出“不需要购买”。
- **F6** 围绕共享物品的家庭协作：成员、权限、责任人、留言/交接/任务；**A 物品维护照料**；**B 经本人明确同意、基于可靠设备使用信号的温和家人关怀**，绝不由信号缺失推断老人健康异常。
- **F7** 维护、耗材、保修、售后、借出、回收等从取得到流转的持续服务，尽量少让用户重复录入。
- **F8** 已建档的实体物品才能制作数字礼物，附文字/故事/影音/心意；访客可查看，**查看不等于确认收物、收物不等于授权共享后续私密记忆**。
- **F9** 长期物品经历、原作者来源、赠礼故事及可选择的昵称/人格/陪伴，而非每件东西强制拟人。
- **F10** 懂人的 Context：当下目标、技能、偏好、时间地点条件、家庭关系，区分用户显式告知、审慎推断、未知；允许纠错、查看、删除、撤回云端授权。
- **F11** Product Pack、证据引用、版本、Agent Harness、工具与风险控制、评测体系、可信结果。
- **F12** 淘宝/天猫订单、商家售后、IoT 与生态服务是长期方向；实际接口未授权时不得宣传已打通。

必须明确区分 **Product Model（商品型号）/ Product Revision（硬件或规格版本）/ Owned Item（用户手里这一件）/ Purchase Evidence（订单线索）/ Person–Item Relation（购买、拥有、使用、维护、借用、赠送）/ Evidence（事实证据）/ Memory（私人故事）**。同一人购买不代表一定拥有，家庭管理员不默认查看每个人的私人物品，用户已确认不等于传感器已证实。

已讨论的自然核心旅程是：①识物→帮助；②已有物品→妙用发现与组合；③提出目标→盘点已有资源→规划→执行；④家庭物品→任务/维护/协助→处理记录；⑤建档物品→制作礼物→匿名预览→实际接收确认→保留可选择的故事。它们要**以同一具体 Item 与真实关系连接**，不能变成五个彼此割裂的演示页。

导航不要为显得完整而强行加很多 tab。V1.1 的五入口是用户意图参考，不是不可变的页签排版；当前代码导航是「使用帮助、活动准备、家庭事项、发现、礼物与记忆」，物品档案藏在子视图。请做实际可用性检查，提出保留或改善方案，但涉及整个导航逻辑/定位的大改先呈现对照而不是擅自决定。

## 3. 核心技术方向与具体任务

以下是可持续执行的研发 Backlog。**不要求一口气做完全部，但需要完成能证明真实价值的纵向闭环；不要用几页设计文档替代实现。** 每一项交付应包含源码、数据/API 契约、示例、正反面测试、边界标签与验收结果。

### T1. 产品身份、数据底座与安全迁移

建立能说明长期关系的数据模型：`User/GuestSession`, `Household`, `Membership`, `ProductModel/Revision`, `Evidence/Source`, `ProductPack`, `Item`, `ItemIdentityBinding`, `PersonItemRelation`, `Grant/Consent`, `Task`, `MaintenanceEvent`, `ServiceRun`, `RunStep`, `Outcome`, `Capability`, `Constraint`, `Compatibility`, `Recipe/TryRecord`, `Memory/StorySnapshot`, `Gift/Transfer`。

建议从当前 SQLite 关系表/迁移体系逐步改造高频对象、补主键/外键/版本/唯一约束/事务/并发冲突保护；后期需多人部署时再依据访问量选择 PostgreSQL。**没有必要为了“知识图谱”四个字立刻使用 Neo4j。** 对现有 JSON 快照先建立兼容层、迁移模拟、双读核对与回滚演练；未经批准不对运行数据进行破坏性迁移。

优先保证：具体物品的长期身份、访问授权、家庭所有权/使用权区分、故事原作者与后续持有人区分、重复认领和撤销的幂等性、数据导出删除、带权限的附件 URL。若后续公开部署，必须更换 `x-demo-actor` 为服务端认证会话；**本地 Host/Origin 限制不等于公网认证**。

### T2. 真实「扫一扫/拍一下就懂」

设计手机/桌面可工作的扫码+上传照片/相机交互。条码可用 `BarcodeDetector`（环境支持时）及兼容 fallback，扫码结果先识别 GTIN/EAN/UPC 等格式，QR 可能只是网址或营销页，必须核对 URL 安全与目标；铭牌 OCR、视觉模型可作为候选来源。扫码拿到数字**不等于**锁定硬件修订版，更不等于取到官方说明书。

候选匹配输出型号、版本、来源、可解释的不确定项，用户核对标签/接口后才绑定具体 Owned Item；对相似型号、没有标签、手工制作、缺资料、未知物品都要给合理回退。允许匿名临时提问。商品识别候选与物品入库要分两个动作。至少构建 10–20 个真实/合成测试物品样例并注明类别，优先实测 3 个不同品类真物品。缺乏在线 OCR/VLM 密钥时先做可运行的本地扫码/图像上传 + 人工确认骨架，保持 UI 中能力标签真实。

### T3. Product Pack 与来源可追溯的商品知识

设计结构化事实体系：准确型号/版本、来源 URL 或手册页码、检索快照与时间、事实 claims、能力、组件/按钮/接口、兼容要求、风险限制、可执行技能步骤、人工验证状态。将官方事实、社区案例、用户私人经验和 AI 候选推断严格分开；不能用另一型号的官方文档代替本型号。

优先选 3 种跨品类典型物品，形成**型号确认→可信资料→逐步服务→反馈**闭环。可给出资料处理（文本/表格/图片→拆段→抽取→校对→版本化→引用）流水线，但要实装一条至少可复现的资料导入路径。没有权利使用的图片/文章不可抓取后直接公开再分发。

### T4. 从 Harness 雏形升级为有纪律的 Agent

不要以“安装某 Agent 框架”作为交付。建立一个服务端 Task Orchestrator：意图分流 → 最小权限 Context Builder → 选择 Task Skill → 调用只读工具 → 形成候选回答或计划 → 型号/能力/安全/证据核查 → 必要追问 → 用户确认后经领域 API 写入 → 收集反馈/失败处理 → 可追踪 Run。

建议的只读工具：`resolve_item`, `search_product_knowledge`, `get_capabilities`, `list_accessible_items`, `get_actor_context`, `check_constraints`, `get_family_context`, `get_device_signal`。建议的受控写操作：`save_item_binding`, `save_service_outcome`, `create_family_task`, `update_maintenance`, `create_gift_draft`, `confirm_gift_transfer`, `save_memory`, `update_consent`；**模型不能直接执行任意数据库写入、转账、下单或跨人敏感消息发送**。工具要有类型契约、权限、超时、失败码、幂等、最大循环数、拒绝策略，外部网页及说明书作为不可信内容做 prompt-injection 测试。

现有“回答必须等于引用原文”会拒绝正确改写。用结构化**原子断言 claim → 引用片段对齐 → 型号/单位/否定/数量校验 → 未知声明与风险策略**替换或补充，但先通过负向基准再放开自然语言生成。不能把单次另一个 LLM 的“yes”当作唯一安全校验。失败 Trace 用最小必要信息、哈希/脱敏、可撤权；不要默认保存私人完整聊天和图片。

### T5. 真正「懂人」和可控记忆

实现 Context 的五层：用户明确偏好/技能与辅助需求；本人拥有与可使用的物品关系；当前任务情境（人数/地点/时间/预算/限制）；有来源和过期时间的谨慎推断；对家庭成员关系的最小可见上下文。每项记录来源、时间、显式/推断/未知、纠错历史、用途、可见范围及云端授权；不要把用户买过商品推断为正在拥有/喜欢。

Context Builder 根据任务只组装相关内容：问爸爸怎么换滤芯，不要给模型另一个家人的礼物故事。对同一件设备，让新人、熟练用户、需要大字短步骤的老人得到不同解释；商品事实和安全约束始终一致。用户可以一键查看「AI 为什么这么理解我」、纠错、撤回、删除。

长期记忆分开**物品与服务事件 / 人的使用偏好 / 人际故事与被传递快照**；试做反馈先归私人经验，不自动变成全球官方事实。

### T6. 物与物的能力协作、妙用和目标规划

为具体物品建立 `Capability + RequiredInput + Constraint + Evidence + Availability`；任务解析 `Requirement + Resource + Time/Environment/Budget + Preference`。区别**能力协同**（端口、供电、承重、数量、尺寸、材质等兼容）与**任务协同**（一组普通物品配合完成露营、收纳、手作等真实生活目标）。

组合建议要经过「已有物品召回 → 能力/案例候选 → 条件过滤 → 实际缺口 → 步骤计划 → 用户确认/试做 → 反馈」；展示有/缺/待核实，允许“不买任何东西”。趣味发现与实用规划可共用能力模型，但表现不同：发现追求新颖与可尝试，规划追求任务完成与低负担。

至少实现一例新录入物品能触发的真实创意、一例跨三件物品的任务、一例因不兼容/不安全而被拒绝的组合。不必假装已经实现“任意物品任意目标”；在精选场景里把原因讲清，比扩大静态卡片数量重要。

### T7. 家庭与关怀的真实关系逻辑

家庭以具体共享物品为协作单元：谁拥有、谁使用、谁维护、谁被授权查看；带上下文的任务、留言、责任交接、维护事项与处理记录。提醒支持暂停/推迟/完成/撤销和时区等条件；无设备数据不能声称检测出闲置。

关怀 B 类要有长辈本人独立同意、设备数据来源/时间、设备离线、外出、习惯变化、误报控制、提醒对象和撤回路径；输出的是**“值得温和确认的线索”**，不是健康诊断。实现可重放模拟信号与状态机测试，真实设备接入单独标识为未来依赖。

### T8. 礼物、记忆与可选人格

礼物始终绑定已经录入的具体物品（可来自任何购买渠道、自制、二手）。礼物状态建议：草稿→生成分享预览→发出→对方确认收到并认领→交接完成/撤销/失效；公开预览和所有权转移不能混淆。限制重复认领、并发、链接过期、撤销和未选故事曝光。

保留故事**原作者、原始记录、来源快照和新持有人**，仅传被选内容；收礼者后来产生的私人记忆不反向传给送礼人。可选昵称、语音、视频、角色陪伴与礼物仪式感，但不要为了动效牺牲隐私、事实与流转正确性。

### T9. 阿里千问/通义模型真正接入

当前仅有兼容式服务器 API 适配器和零次成功的记录。首先读取阿里云百炼/千问的**当前官方文档**确认地域、模型、视觉能力、支持的 API 格式、限流及价格；使用服务端环境变量，绝不把 key 写到前端或代码仓库，付费前问清额度与授权。用 mock 与真实调用分别验证：有证据的单物品问答、跨品类咨询、被拒绝的危险或错型号用法、模型不可用/超时/429 等。

真实调用产出可脱敏的 trace、消耗 token、延迟、调用状态与质量人工评价；无模型凭证时先完成**密钥到位即可运行**的调用脚本及清晰验收步骤，坚决不把测试替身冒充真实千问。

### T10. FancyTech 可借鉴的质量工程：Skill → Reference → Evaluation → Benchmark

借鉴的是**方法**，不引用或对外传播未经授权的企业内部资料。为单物品帮助、识物、发现、家庭和礼物分别制定轻量 Skill 任务说明书；Reference 包含带出处的商品事实与经人工审核的优劣案例；Evaluation 衡量型号准确率、事实支持率、不安全建议漏放、实际可行性、任务成功、用户反馈、隐私越权和时延/成本；Benchmark 收集正反例并在每次更改模型、Prompt、Pack、工具和规则时回归。把结果标注为离线模拟、人工复核、真实物品实测或在线模型测试。

至少提供一份机器可运行的 benchmark 数据集、一个好案例和一个坏案例分析，以及不同 Prompt/规则版本的同题对比。**不能用回答篇幅、截图漂亮、调用成功次数替代“用户真的把事情做好了”的证据。**

### T11. 工程架构、用户体验与可交付性

沿用现有 Next.js/TypeScript 工程，按业务逐步拆大组件，建立清晰的 `domain → repository → service/tools → API → UI` 层次；避免把可复用业务条件硬编码在 JSX。可根据必要性使用 PostgreSQL、队列、对象存储或图检索，但先拿出具体负载/一致性/查询问题和代价比较，不以技术名词堆栈为目标。

手机 390px 和桌面都要体验完整；新用户第一次打开应清楚知道“拍一下、问一下、发现一下”，无需先管理几十个物品。状态“真实 AI／精选资料／算法规则／演示信号／仍需用户核实”可见且自然，不做欺骗性演示。保持多条旅程之间同一个 Item 的信息贯通。

## 4. 开发优先顺序：按真实闭环推进，不把所有想法当作本周承诺

**第一层｜立即保证稳定与可信：** 先复验基线、记录可复现问题，修明显权限/来源/状态缺口；建阶段验收和基本观测。若模型接入条件已具备，尽早完成一次真实千问在线闭环。

**第二层｜让产品出现不可替代的核心价值：** 在 2–3 件真实代表性物品上做识别候选/身份确认 → 可信 Product Pack → Agent 答案/步骤 → 反馈；做基于真实物品和用户情境的创意/组合，包含拒绝不安全建议。

**第三层｜把理解人、长期关系做实：** 完善 Context 和角色/授权；家庭任务和两类关怀；礼物记忆；数据库关系实体和迁移；必要 UI 调整。

**第四层｜可扩展与展示：** 完整 Eval 回归、错误可追踪、部署身份/数据安全、说明书知识扩展、API 成本控制与演示脚本。长期生态订单、IoT、多 Agent、视频生成/动态人格按依赖另列，不将未授权集成伪装成功。

已有实施文档把 2026-10-20 作为内部验收目标；今天已经 2026-10-17，因此可以在该节点前优先交付**可现场演示的精选真实纵向闭环**，其余保留分阶段技术路线。用户允许任务大、持续开发，但你必须清楚区分“已经运行”和“已设计待实现”。

## 5. 必须有的验收与开发汇报

每个主要模块至少准备：正常成功、信息不足、权限不足/撤回、资料错误/冲突、超时/失败、重复执行/数据一致性这些类型的测试（按模块适用）。验证真实商品资料和模型输出时标具体型号、来源与版本；不得凭设备名称臆测按钮、参数或维修方法。检查 SQL 迁移、赠礼事务、隐藏私密信息、跨角色 API、附件访问和误报降级。真实世界组合要人工确认可行性，不把规则通过等于实物验证。

**每轮交付都要更新两个文件：**

- `DEVELOPMENT_REPORT.md`（给不懂编程的负责人）：这轮前后对比、完成了什么、能在网页上体验什么、哪些仍是 mock、未完成和已知 bug、下一步与需要用户决定的事项；未变更的功能不能再算本轮新成果。
- `REVIEW_HANDOFF.md`（给下一位 Codex/审查者）：最新版本/commit、架构、实体与 API 契约、重点源码、环境配置、测试命令及结果、真实模型调用凭证的**非敏感证据**、回滚办法、负向场景和限制。

再维护 `IMPLEMENTATION_STATUS.md`（按 F1–F12 + T1–T11：已实现/部分实现/模拟/未实现/阻塞 + 证据指针），`CHANGELOG.md`，评测结果与演示样例。每轮输出直接可运行的代码和对应测试，不允许一整个迭代只写文件或重画架构图。

完成一轮后生成干净的审查 ZIP：完整源码、锁文件、测试、`docs`、两份报告、脱敏 Trace/Benchmark/截图；排除 node_modules、.next、.git、.env.local、API key、生产数据库与真实私人资料。标出与上轮基线差异及失败案例，附上清晰的启动说明。不要因为导出而修改业务行为。
