## 已检查并修正的设计问题

| 问题 | 本 RFC 的处理 | 尚未证明的部分 |
| --- | --- | --- |
| 容易把 v1 256 测试和真实请求当 main 的质量保证 | 固定 main/audit/fixed 三提交；历史数据单独标注，承认最终小补丁只离线复验 | 实现分支需重新跑测试、留出集与盲评 |
| 把高置信度、用户确认、官方来源、物理验证混成一个字段 | basis/status/verification/权限独立；作用域和版本明确 | 自然语言机制的语义正确性仍需领域审阅/实测 |
| 资源目录可能演变成万能 JSON 表 | 仅身份/版本/权限；item_state 与原子 assertion 区分 | 七表是草案；完整谓词类型、依赖闭包、环路需服务实现 |
| 旧 Item 没有通用 revision，memory epoch 也不覆盖所有权限 | P1 用内容寻址投影与许可摘要、提交前重新读源授权；P2 才增加持久修订与授权 epoch | 不将虚拟 revision=1 或客户端 epoch 当作并发保护 |
| 仅删除摘要却会从旧故事重新形成同一记忆 | 引入抑制重新提取和遗忘栅栏；恢复旧备份前先应用最新撤销记录 | 第三方副本、备份保留期和实际删除 SLA 未决定 |
| 授权检索后撤权，或派生摘要泄露来源 | 依赖来源权限交集；发送/执行前 policyEpoch 复查 | 多服务并发竞态和日志处理需 L2 集成测试 |
| 创意流程只有提示词和 recipes | 给出三值条件、功能角色图、受限搜索、PlanSpec、反馈与公平盲评 | 组合搜索是否提高惊喜/可实施性仍待人类对照 |
| “不要拍照”被等同“不要视频” | 结构化约束按动作语义；冲突时询问 | 不能靠单个 fixture 证明开放语言理解稳定 |
| 暂停恢复被描述成自动安全 | 区分框架恢复、领域幂等、设备结果不明；要求中途 kill 实验 | 现有 Pi PoC 无中途 kill、写入或真实模型验证 |
| REA / Pi 的名称和兼容性可能过时 | 固定官方项目和查询版本；REA Node 要求与当前 24.16.0 不兼容 | 各原生提供者、具体设备与未来发布需重验 |
| 一个 Node 事务似乎能保证设备恰好一次 | 回执、网关发件箱、租约、回读；不明则停止盲重试 | 不保证无幂等协议的外部世界 exactly-once |
| 数据迁移回滚覆盖切换后的新写入或复活已忘信息 | 先增量映射、单写、保存新写入，恢复先施遗忘栅栏 | 未执行真实数据迁移和备份演练 |

## 本轮验证边界

检查器读取固定提交中的源码片段核验路径/锚点，检查文档内部链接、JSON 示例和夹具；在内存 SQLite 建七表并尝试跨空间引用、非法状态/JSON、冲突来源和重复请求等负例。所有七表都有一个合成画作纵切样例，不为概念堆空表。Mermaid 图做文本语法审阅，未在本轮进行浏览器渲染验收。

夹具一致性检查只检查规格自洽；SQL 约束测试只证明本草案的数据库约束，不证明业务服务授权或语义已经实现。SQL 不能独立阻止跨租户 SELECT、关系 value 内的越权 ID、多跳环路或未经许可的模型发送，这些明确留给领域服务和后续负例。检查器不加载应用、不读 env、不联网、不接触真实数据库。

原 main 没有根 AGENTS/三份状态报告；本分支复用修复分支的协作约定，并增加本轮状态记录，没有覆盖历史报告。已有文档入口和 CHANGELOG 只追加 RFC 链接。未改 src/tests/package/lockfile，没有安装新依赖；所以未重跑业务构建/191 或 256 项测试，不能用本轮检查数冒充业务测试数。

## 下一轮最先验证的风险

1. P1 同信息上下文：读取完整度、跨入口一致性、隐私闭包与 token 成本能否同时达标。
2. P2 更正/遗忘：保留材料时能否阻止已遗忘信息重建，回滚后是否仍遵守撤权。
3. P3 创意：功能角色搜索是否有实际收益；若只有更复杂的代码，必须缩减或改算法，不能以“架构先进”解释失败。
